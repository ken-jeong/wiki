## 요약
**임베디드 리눅스**
- 리눅스 커널과 오픈 소스 구성 요소를 특정 기능을 수행하는 장치에 사용하는 것이다.

## 학습 목표
이 장을 공부한 뒤에는 다음 질문에 답할 수 있어야 한다.
- GNU와 Linux 커널은 각각 어떤 역할을 하는가?
- 임베디드 시스템에서 Linux와 오픈 소스를 사용하는 이유는 무엇인가?
- 개발 PC와 타깃 장치는 어떻게 다르며, 교차 컴파일은 왜 필요한가?
- 부트로더, 커널, C 라이브러리, 응용 프로그램은 어떤 관계인가?
- 전원 인가 후 부트로더와 커널은 어떤 순서로 동작하는가?

## 1. GNU/Linux와 임베디드 리눅스
### 1.1. 등장과 확산 흐름
다음 순서로 GNU/Linux의 발전과 활용 범위의 확대를 설명한다.

| 시기 | 강의의 주요 내용 | 기억할 의미 |
|---|---|---|
| 1983년 | Richard Stallman의 GNU 프로젝트와 자유 소프트웨어 활동 시작 | 운영체제에 필요한 소프트웨어를 자유롭게 사용할 수 있도록 만드는 흐름 |
| 1991년 | Linus Torvalds의 Linux 커널 프로젝트 시작 | UNIX 계열과 유사한 운영체제 커널 등장 |
| GNU와 Linux의 결합 | GNU 소프트웨어와 여러 오픈 소스 구성 요소가 Linux 커널과 결합 | GNU/Linux라는 완전한 운영체제 환경 구성 |
| 1995년 무렵 | 서버 시스템에서 Linux 사용 확대 | 서버로 확산 |
| 2000년 무렵 | 임베디드 시스템에서 Linux 사용 확대 | 다양한 전용 장치로 확산 |
| 2008년 무렵 | 모바일 장치와 휴대전화에서 사용 확대 | 모바일로 확산 |
| 2012년 무렵 | Raspberry Pi, BeagleBone Black 등 저렴하고 확장 가능한 하드웨어 활용 | 개발·학습에 접근하기 쉬운 보드로 확산 |

> 후반부 연도는 강의에서 제시한 확산 흐름을 기억하기 위한 기준이다.
> 각 제품의 정확한 출시 연도를 뜻하는 표로 해석하지 않는다.
> 또한 gcc, gdb, glibc가 모두 1983년에 동시에 만들어졌다는 의미도 아니다.

**보충: GNU 관련 도구의 역할**

| 이름    | 역할                   |
| ----- | -------------------- |
| **GCC**   | 소스 코드를 컴파일하는 컴파일러 모음 |
| **GDB**   | 실행 중인 프로그램을 분석하는 디버거 |
| **glibc** | GNU의 C 라이브러리 구현      |

### 1.2. 임베디드 리눅스의 정의
```
Linux 커널 + 오픈 소스 구성 요소 + 장치에 필요한 응용 프로그램
                         ↓
                 임베디드 리눅스 시스템
```

- **Linux 커널**은 프로세스, 메모리, 장치, 네트워크 등을 관리한다.
- 커널에 라이브러리와 응용 프로그램 등이 결합되어 실제 장치의 기능을 제공한다.

**보충**
- 임베디드 시스템은 공유기의 통신 기능이나 측정 장비의 계측 기능처럼, 제품 안에서 정해진 목적을 수행하는 컴퓨터 시스템이다.
- 따라서 “임베디드 리눅스”를 특정 보드나 단일 제품 이름으로 외우기보다 **시스템을 구성하는 방식**으로 이해하면 쉽다.

### 1.3. Linux와 오픈 소스를 사용하는 장점
| 키워드             | 학습용 풀이                                |
| --------------- | ------------------------------------- |
| 컴포넌트 재사용        | 이미 만들어진 구성 요소를 재사용할 수 있다.             |
| 저비용             | 기존 소프트웨어 활용으로 개발 비용을 줄일 수 있다.         |
| 완전한 통제          | 소스 코드를 확인하고 요구에 맞게 수정할 수 있다.          |
| 새로운 기능의 간편한 테스트 | 기존 구성 요소를 이용해 새 기능을 시험하기 쉽다.          |
| 품질              | 여러 사용자와 개발자가 검토·개선한 결과를 활용할 수 있다.     |
| 보안              | 공개된 코드와 공동 대응을 통해 보안 문제를 분석·개선할 수 있다. |
| 커뮤니티 지원         | 커뮤니티의 문서와 경험을 활용할 수 있다.               |
| 커뮤니티 활동 참여      | 수정과 개선을 커뮤니티에 기여할 수 있다.               |

**보충**
- 여기서 자유 소프트웨어의 `free`는 사용·연구·수정·공유의 자유에 초점이 있다.
- “비용이 전혀 들지 않는다”는 뜻은 아니다.
- 품질과 보안 역시 선택한 구성 요소, 설정, 유지보수에 따라 달라진다.

## 2. 어디에 사용하는가?
### 2.1. 활용 사례
| 분야    | 강의의 예시                                                          |
| ----- | --------------------------------------------------------------- |
| 네트워크  | 무선 공유기                                                          |
| 영상    | 비디오 시스템                                                         |
| 이동·운동 | 자전거 컴퓨터                                                         |
| 로봇    | 로봇 장치                                                           |
| 우주    | SpaceX Starlink 위성, Falcon 9·Falcon Heavy 로켓, 화성 Ingenuity 헬리콥터 |

**학습 포인트**
- Linux는 PC와 서버뿐 아니라 네트워크, 영상, 로봇, 우주 분야의 장치에도 활용된다.
- 예시 사진만으로 해당 장치의 모든 제어 기능을 Linux가 담당한다고 단정하지 않는다.

### 2.2. 과학 계측 장비의 구성
강의 그림에는 다음 요소가 연결되어 있다.

```
카메라 ↔ Linux의 웹 서버 응용 ↔ 장치의 사용자 GUI(Qt)
                    ↕
              MCU ↔ 레이저·모터
                    
PC의 연구·개발 GUI ↔ Linux의 웹 서버 응용
PC의 디버깅 도구   ↔ Linux의 SSH 서버·GDB 서버
```

- Linux 시스템에는 웹 서버 응용, 사용자 GUI, SSH 서버, GDB 서버가 있다.
- 카메라는 웹 서버 응용과 연결되고, 레이저·모터는 MCU를 통해 연결된다.
- 외부 PC에서는 연구·개발용 GUI와 디버깅 기능을 사용할 수 있다.

> 하나의 장치 안에서도 Linux와 MCU가 역할을 나누어 협력할 수 있다.

### 2.3. 엄격한 하드웨어 제어 요구가 있는 의료 장비
```
혈액 감지기·기포 감지기·모터 제어
                ↕
               MCU ↔ 임베디드 Linux의 사용자 GUI(Qt)
                           ↕
                   SSH·GDB 서버 ↔ 디버깅 PC
```

강의의 의료 장비 예시는 하드웨어 제어 시스템과 Linux 시스템을 나눈다.
MCU 쪽에는 혈액 감지기, 기포 감지기, 모터 제어가 연결되고, Linux 쪽에는 사용자 GUI와 디버깅용 서버가 배치된다.

**보충 해석**
- 제어 요구가 엄격한 부분과 화면·통신 등의 기능을 분리하는 설계로 이해할 수 있다.
- 이 그림만으로 구체적인 제어 주기나 실시간 성능 수치를 알 수는 없다.

## 3. 임베디드 하드웨어와 Linux 지원
### 3.1. CPU 아키텍처
**CPU 아키텍처**
- 프로세서의 명령어 체계와 동작 구조

Linux 커널이 다양한 32비트·64비트 아키텍처를 지원한다.

| 아키텍처                        | 특징·용도                       |
| --------------------------- | --------------------------- |
| x86, x86-64                 | PC 및 멀티미디어·산업용 임베디드 시스템     |
| ARM                         | 매우 다양한 SoC에서 사용             |
| RISC-V                      | 자유로운 명령어 집합을 기반으로 성장하는 아키텍처 |
| PowerPC                     | 주로 실시간·산업용 응용               |
| MIPS                        | 주로 네트워크 응용                  |
| MicroBlaze, Nios II         | FPGA에 구현하는 소프트 코어           |
| ARC, m68k, Xtensa, SuperH 등 | 그 밖의 아키텍처                   |
- **SoC(System on Chip)**: CPU와 여러 주변 기능을 하나의 칩에 통합한 것

**소프트 코어**
- FPGA의 논리 자원을 사용해 구현하는 프로세서 코어
- ==MicroBlaze==, Nios II #3-2/임베디드시스템/출제

이 표는 **강의에 제시된 목록**이며, 현재의 커널 버전별 지원 현황을 판정하는 표는 아니다.

### 3.2. 통신 버스와 네트워크
| 구분        | 강의에서 제시한 항목                         |
| --------- | ----------------------------------- |
| 통신 버스     | I2C, SPI, wire, SDIO, PCI, USB, CAN |
| 연결 기술     | Ethernet, Wi-Fi, Bluetooth, CAN     |
| 네트워크 프로토콜 | IPv4, IPv6, TCP, UDP                |
| 네트워크 기능   | 방화벽, 고급 라우팅, 멀티캐스트                  |
==CAN 통신== #3-2/임베디드시스템/출제
- 자동차 분야에 주로 사용된다.

> Linux의 장점은 여러 CPU에서 실행되는 것뿐 아니라,
> 다양한 주변장치와 통신 기능을 활용할 수 있다는 데 있다.

## 4. 임베디드 리눅스 시스템의 구성
### 4.1. 소프트웨어 구성 요소
**크로스 컴파일 툴체인**
- 개발 머신에서 실행되며 타깃에서 실행할 코드를 생성

**부트로더**
- 하드웨어에 의해 시작되어 기본 초기화 후 커널을 적재·실행

==리눅스 커널== #3-2/임베디드시스템/출제
- 프로세스·메모리 관리, 네트워크 스택, 디바이스 드라이버 등을 제공

==C 라이브러리== #3-2/임베디드시스템/출제
- C 함수들을 제공하고 사용자 공간 응용과 커널 사이의 인터페이스 역할 수행

**기타 라이브러리·응용**
- 제3자 소프트웨어나 직접 만든 프로그램으로 제품 기능 구현

### 4.2. 개발 PC와 타깃 장치
- **호스트(Host)**: 컴파일러와 디버거 등 개발 도구를 실행하는 개발 PC
- **타깃(Target)**: 만들어진 소프트웨어를 실제로 실행하는 임베디드 장치

```
개발 PC: x86-64                         타깃 장치: ARM64
┌─────────────────────┐              ┌─────────────────────┐
│ 소스 코드 + 툴체인    │ → 빌드 결과 → │ 부트로더·커널·응용 등 │
└─────────────────────┘              └─────────────────────┘
      개발 도구 실행                         제품 코드 실행
```

**교차 컴파일의 핵심**: 컴파일러가 실행되는 환경과, 생성된 코드가 실행될 환경이 다르다.

**보충 예시**
- x86-64 PC에서 실행되는 ARM64용 교차 컴파일러는 ARM64 장치에서 실행할 코드를 만든다.
- “컴파일러가 실행되는 CPU”와 “생성된 프로그램이 실행되는 CPU”를 구분해야 한다.

### 4.3. 실행 중의 계층 구조
```
사용자 공간    응용 프로그램
                 ↓
              라이브러리
                 ↓
              C 라이브러리
                 ↓
커널 공간      Linux 커널
              ├─ 프로세스·메모리 관리
              ├─ 네트워킹
              ├─ 디바이스 드라이버
              └─ 파일시스템
                 ↓
               하드웨어

부팅 단계      부트로더 → 커널로 제어 전달
```

**보충**
- 사용자 공간은 응용 프로그램이 실행되는 영역이며, 커널 공간은 운영체제의 핵심 기능이 실행되는 영역이다.
- 응용이 커널 기능을 요청하는 통로를 **시스템 콜(system call)**이라고 한다.
- 위 그림은 대표적인 계층 관계를 단순화한 것이며, C 라이브러리의 모든 함수가 매번 커널을 호출한다는 뜻은 아니다.

**헷갈리지 않기**
- 툴체인은 개발 환경의 도구이고, 부트로더는 부팅 과정의 구성 요소다.
- 이 둘을 응용 프로그램 아래에서 계속 실행되는 일반 라이브러리처럼 이해하면 안 된다.

### 4.4. 개발 결과물 읽기
| 강의 그림의 표기 | 의미                 | 생성·배치 관계                 |
| --------- | ------------------ | ------------------------ |
| BLD       | 부트로더               | 부트로더 소스에서 빌드             |
| Kernel    | Linux 커널           | 커널 소스에서 빌드               |
| DTS       | Device Tree Source | 하드웨어 구성을 기술하는 소스         |
| DTB       | Device Tree Blob   | DTS를 변환한 바이너리 형태         |
| RFS       | Root File System   | 응용 프로그램 등이 들어가는 루트 파일시스템 |

**보충**
- DTB는 커널이 하드웨어 구성을 파악하는 데 쓰는 데이터다.
- RFS에는 일반적으로 응용뿐 아니라 라이브러리와 설정 파일 등도 포함된다.
- 각 결과물을 모두 같은 컴파일러 하나로 만드는 것은 아니며, 결과물에 맞는 빌드·변환 도구를 사용한다.

## 5. 부팅 과정: 순서와 담당자 연결하기
### 5.1. 강의 흐름도 전체 연결
```
[부트로더 단계]
ROM 기반 부트로더
    ↓
U-Boot로 이동
    ↓
DTB를 RAM에 적재
    ↓
커널 바이너리를 RAM에 적재
    ↓
커널로 제어 전달

[커널 단계]
커널 실행 시작
    ↓
CPU 설정
    ↓
RAM에 있는 디바이스 트리 해석
    ↓
발견한 장치를 위한 함수 실행
    ↓
init 프로세스 생성
    ↓
idle 상태 / 이후 실행 중에도 커널 기능 제공
```

이 순서는 강의 흐름도를 연결한 **개략적인 부팅 흐름**이다.
실제 하드웨어의 세부 부팅 단계 전체를 나열한 것은 아니다.

### 5.2. 부트로더의 역할
1. ROM 기반 부트로더에서 시작한다.
2. U-Boot로 실행을 넘긴다.
3. 디바이스 트리 바이너리(DTB)를 RAM에 올린다.
4. 커널 바이너리를 RAM에 올린다.
5. 커널로 실행 제어를 넘긴다.

**이해 포인트**
- 저장된 커널 파일을 RAM에 올리는 일과, 커널을 실제로 실행하는 일은 구분된다.

**보충**
- U-Boot는 부트로더의 한 종류다.
- 모든 임베디드 Linux 시스템이 반드시 같은 부트로더나 동일한 부팅 순서를 사용하는 것은 아니다.

### 5.3. 커널의 역할
1. 커널 실행을 시작한다.
2. CPU를 설정한다.
3. RAM에 적재된 디바이스 트리를 해석한다.
4. 발견한 장치에 필요한 함수를 실행한다.
5. `init` 프로세스를 생성한다.

**보충**
- `init`은 사용자 공간의 시작점이 되는 프로세스이며, 이후 서비스와 응용을 시작하는 기반이 된다.
- 강의 그림에는 루트 파일시스템 준비 등의 세부 단계가 생략되어 있다.

### 5.4. 부팅 후에도 커널은 계속 동작한다
강의 마지막 그림은 `Sits idle*`로 끝난다.
별표의 상세 설명은 자료에 제시되어 있지 않다.

**보충**
- 이것을 “커널이 종료된다”로 외우면 안 된다.
- 실행할 작업이 없을 때는 idle 상태에 들어갈 수 있지만, 부팅 후에도 커널은 시스템 콜과 인터럽트 등에 대응하며 프로세스·메모리·장치·네트워크를 관리한다.

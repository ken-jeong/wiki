> **학습 목표**
> 부트로더의 역할을 이해하고,
> BIOS·UEFI·임베디드 부팅 구조를 비교하며,
> QEMU에서 U-Boot의 환경변수 저장과 네트워크 파일 전송 흐름을 설명할 수 있다.

## 1. 먼저 전체 흐름 잡기
운영체제 커널도 하나의 프로그램이다.
실행하려면 먼저 하드웨어를 준비하고, 커널을 메모리에 올려야 한다.
이 준비 과정을 담당하는 코드가 부트로더다.

```
전원 켜짐 / 리셋
    ↓
초기 부팅 코드·펌웨어 실행
    ↓
필요한 하드웨어 및 메모리 초기화
    ↓
부트로더가 커널을 메모리에 적재
    ↓
커널로 실행 제어 전달
```

**가장 중요한 질문은 두 가지다.**
1. 지금 실행되는 코드는 어디에 저장되어 있고, 어디에서 실행되는가?
2. 다음 단계의 코드를 실행하려면 어떤 준비가 필요한가?

이 질문으로 보면 BIOS의 2단계 부팅과 임베디드의 2단계 부팅이 쉽게 구분된다.

## 2. 부트로더의 역할
**부트로더**
- 프로세서에서 최초로 실행되는 코드
- 다만 뒤에 나오는 실제 부팅 구조에서는 **BIOS·UEFI 펌웨어나 프로세서 내부 ROM 코드가 먼저 실행될 수 있다.**
- 따라서 전체 부팅 과정에서 각 코드의 역할을 구분해서 이해해야 한다.

| 역할 | 하는 일 |
|---|---|
| 하드웨어 초기화 | 다음 단계 실행에 필요한 기본 하드웨어를 준비한다. |
| 커널 적재 | 플래시 저장장치 또는 네트워크에서 커널을 읽어 메모리에 올린다. |
| 압축 해제 | 압축된 실행 이미지가 있다면 필요한 형태로 풀어 준다. |
| 실행 제어 전달 | 준비된 커널 또는 응용 프로그램을 실행한다. |
| 부팅 메뉴 제공 | 실행할 운영체제 등을 선택하게 한다. |
| 개발·진단 기능 | 셸과 명령어로 데이터 적재, 메모리 검사, 테스트 등을 수행한다. |

> **기억할 문장**
> 부트로더는 다음 프로그램이 실행될 수 있도록 준비하고, 그 프로그램으로 제어를 넘긴다.

## 3. 세 가지 부팅 구조 비교
| 항목         | 기존 BIOS             | UEFI              | 임베디드 ROM 기반              |
| ---------- | ------------------- | ----------------- | ------------------------ |
| 초기 실행 주체   | BIOS 펌웨어            | UEFI 펌웨어          | 프로세서 내부 ROM 코드           |
| 다음 코드의 위치  | MBR의 부팅 코드          | ESP의 EFI 바이너리     | 벤더가 정한 부트 매체·위치          |
| 자료의 주요 제약  | MBR 코드 영역 446바이트    | ESP·EFI 형식에 따른 적재 | 외부 DRAM 미초기화, 내부 SRAM 크기 |
| 부팅을 나누는 이유 | 작은 코드 영역에서 큰 로더로 확장 | 펌웨어가 EFI 파일을 적재   | SRAM에서 시작해 DRAM으로 확장     |

**BIOS의 2단계는 MBR 공간 제약**,
**임베디드의 2단계는 초기 메모리 상태와 SRAM 크기 제약**으로 이해하자.

### 3.1. 기존 x86 BIOS 부팅
**BIOS (Basic Input Output System)**
- 기존 BIOS는 플랫폼 펌웨어로서 플래시 메모리에 저장되며, RAM 초기화와 초기 부팅을 담당한다.
- 런타임 서비스도 제공하지만 자료에서는 많이 사용되지 않는다.

```
BIOS
  │ RAM 초기화, 저장장치의 부팅 코드 적재
  ▼
Stage 1 부트로더
  │ MBR에 들어 있는 작은 코드
  │ Stage 2 적재
  ▼
Stage 2 부트로더
  │ 파일시스템 해석, 커널 이미지 적재
  ▼
커널
```

#### MBR과 2단계 부팅
**MBR (Master Boot Record)**
- 저장장치의 첫 번째 섹터에 위치한다.
- 파티션 테이블을 포함하며, 부트로더 코드가 들어갈 수 있는 영역은 **최대 446바이트**다.
- 이 공간에 모든 부팅 기능을 담기 어려우므로 부트로더를 두 단계로 나눈다.

| 구분 | Stage 1 | Stage 2 |
|---|---|---|
| 크기 | 446바이트 이내의 작은 코드 | 상대적으로 큰 코드 |
| 핵심 역할 | Stage 2를 찾아 적재 | 커널을 찾아 적재 |
| 위치·기능 | MBR의 코드 영역 | 자료의 구조에서는 파일시스템과 별도로 고정 오프셋에 저장 |
| 파일시스템 처리 | Stage 2를 쉽게 찾는 데 집중 | 파일시스템을 지원해 커널 파일을 읽음 |

**왜 Stage 2를 고정 오프셋에 두는가?**
- 작은 Stage 1이 복잡한 파일 탐색 없이 위치를 알고 읽을 수 있도록 하기 위해서다.
- 모든 구현의 저장 배치가 같다는 뜻은 아니다.

### 3.2. UEFI 부팅
**UEFI (Unified Extensible Firmware Interface)**
- UEFI는 운영체제와 펌웨어 사이의 인터페이스를 정의한다.
- 2005~2006년 무렵 등장한 새로운 펌웨어 인터페이스이다.

```
UEFI 펌웨어
    ↓ EFI 시스템 파티션에서 EFI 바이너리 적재
EFI 부트로더
    ↓ 커널 적재
커널
```

EFI 부트 코드를 포함한 리눅스 커널은 펌웨어가 직접 적재할 수도 있다.

**펌웨어**
- 부팅 기능과 운영체제용 런타임 서비스를 제공한다.
- 플래시 메모리에 저장된다.

**ESP (EFI System Partition)**
- EFI 바이너리를 저장하는 특수 파티션이다.
- ESP는 **FAT 파일시스템**으로 포맷된다.
- MBR 파티션 방식에서는 타입 `0xEF`, GPT에서는 특정 GUID로 ESP를 구별한다.
- 자료는 `/efi/boot/` 아래의 EFI 파일 경로를 예로 제시한다.

> **핵심 차이**
> BIOS 구조는 MBR의 작은 코드에서 출발하고,
> UEFI 구조는 펌웨어가 ESP의 EFI 바이너리를 읽어 실행한다.

### 3.3. 임베디드 플랫폼 부팅
대부분의 임베디드 프로세서는 내부에 **ROM 코드**를 갖는다.

- 프로세서 벤더가 작성하고 칩 내부에 내장한다.
- 자료의 ROM 코드는 변경하거나 업데이트할 수 없다.
- 동작 방식은 프로세서 데이터시트에 설명된다.
- NAND/NOR 플래시, USB, SD 카드, eMMC 등에서 정해진 위치·형식의 부트로더를 찾아 적재한다.
- **외부 RAM이 초기화되기 전에도 실행할 수 있다.**

```
프로세서 내부 ROM 코드
    ↓ 작은 부트로더를 내부 SRAM에 적재
1단계 부트로더: 내부 SRAM에서 실행
    ↓ 외부 DRAM 초기화, 2단계 부트로더 적재
2단계 부트로더: 외부 DRAM에서 실행
    ↓ 커널 적재 및 실행
커널
```

#### 왜 임베디드에서도 두 단계로 나눌까?
1. 처음에는 외부 DRAM이 초기화되지 않았다.
2. 따라서 초기 부트로더는 내부 SRAM을 이용한다.
3. 내부 SRAM은 크기가 작아 큰 부트로더를 담기 어렵다.
4. 작은 1단계가 외부 DRAM을 초기화한다.
5. 이후 큰 2단계 부트로더가 외부 DRAM에서 실행된다.

> **암기 연결**
> ROM → SRAM의 작은 부트로더 → DRAM 초기화 → DRAM의 큰 부트로더

## 4. GRUB과 U-Boot
### 4.1. 두 부트로더의 특징
| 항목       | GRUB                                  | U-Boot                              |
| -------- | ------------------------------------- | ----------------------------------- |
| 이름·성격    | Grand Unified Bootloader,<br>GNU 프로젝트 | 임베디드에서 널리 사용되는 부트로더                 |
| 대표 사용 환경 | x86 Linux 배포판                         | ARM, ARM64, RISC-V, PowerPC, MIPS 등 |
| 플랫폼 지원   | x86 Legacy BIOS·UEFI 및 다른 아키텍처        | 여러 임베디드 아키텍처 및 x86의 UEFI 기능         |
| 자료의 강조점  | 다양한 파일시스템, 메뉴, 셸, 네트워크 커널 적재          | 보드별 설정, 하드웨어 지원, 임베디드 개발            |

U-Boot는 보통 SoC·SoM·보드 벤더가 제공하며, 자료에 제시된 라이선스는 **GPLv2**다.
버전 이름은 `YYYY.MM` 형식이며, 실습에서는 `v2023.01`을 사용한다.

### 4.2. U-Boot 설정과 빌드의 관계
U-Boot는 **Kconfig 기반 설정 시스템**을 사용한다.

```
configs/의 보드별 기본 설정
    ↓ make BOARDNAME_defconfig
.config 생성
    ↓ make menuconfig
필요한 옵션 조정
    ↓ make
U-Boot 빌드
```

| 항목 | 의미 |
|---|---|
| `configs/` | 보드별 기본 설정 파일이 있는 디렉터리 |
| `BOARDNAME_defconfig` | 특정 보드에 맞는 기본 설정 |
| `.config` | 실제 빌드에 사용할 설정 |
| `make menuconfig` | 메뉴로 설정을 수정하는 명령 |

설정에는 CPU 종류, 필요한 드라이버, 포함할 U-Boot 기능 등이 들어간다.

**주의할 구분**
- `.config`는 **빌드할 때 사용할 설정**이다.
- 뒤에서 다룰 `ipaddr`, `serverip`, `foo` 등은 **실행 중 U-Boot가 사용하는 환경변수**다.

### 4.3. 실행 시작점과 소스 위치
| 항목                           | 역할                       |
| ---------------------------- | ------------------------ |
| `arch/u-boot-elf.lds`        | 링커 스크립트 예시. 실행 진입점 등을 지정 |
| `CONFIG_PLATFORM_ELFENTRY`   | 플랫폼의 ELF 진입점 관련 설정       |
| 최상위 `Kconfig`                | 해당 설정 옵션의 정의 위치          |
| `_start`                     | 자료에서 살펴보는 실행 시작 심볼       |
| `arch/arm/cpu/armv7/start.S` | ARMv7 초기 시작 코드의 위치       |

이 부분의 학습 목적은 **“실행 이미지의 진입점이 어떤 설정과 시작 코드로 연결되는가”**를 이해하는 것이다.

## 실습 1: U-Boot 빌드와 QEMU 실행
> 아래 셸 명령은 강의의 Linux 호스트 환경을 기준으로 한다.
> 코드 블록에서 `$`와 `=>` 프롬프트 표시는 생략했다.
> `bash` 블록은 호스트 터미널, `text` 블록은 U-Boot 프롬프트에 입력한다.

### 1. 소스와 보드 설정
```sh
git clone https://gitlab.denx.de/u-boot/u-boot
cd u-boot
git checkout v2023.01
```

```sh
export CROSS_COMPILE=arm-linux-

make vexpress_ca9x4_defconfig
make menuconfig
```
- `CROSS_COMPILE`: ARM용 크로스 컴파일러 명령의 접두사다. 자료는 `arm-linux-`를 사용하며 해당 도구체인이 설치되어 있어야 한다.
- `vexpress_ca9x4_defconfig`: 실습 대상인 ARM Vexpress Cortex-A9 보드 설정이다.

### 2. menuconfig에서 바꾸는 항목
| 설정                               | 값·동작  | 목적                 |
| -------------------------------- | ----- | ------------------ |
| `CONFIG_ENV_IS_IN_FLASH`         | 해제    | 플래시 기반 환경변수 저장 해제  |
| `CONFIG_ENV_IS_IN_FAT`           | 활성화   | FAT 파일시스템에 환경변수 저장 |
| `CONFIG_ENV_FAT_INTERFACE`       | `mmc` | 환경변수를 저장할 장치 종류    |
| `CONFIG_ENV_FAT_DEVICE_AND_PART` | `0:1` | 장치 0의 첫 번째 파티션 사용  |
| `CONFIG_CMD_EDITENV`             | 활성화   | 환경변수 편집 명령 지원      |
| `CONFIG_CMD_BOOTD`               | 활성화   | `bootd` 명령 지원      |

**뒤의 SD 카드 실습과 연결**
- 환경변수를 FAT에 저장하도록 설정했기 때문에 SD 이미지의 첫 번째 파티션을 FAT16으로 만든다.

### 3. 의존성 설치와 빌드
```sh
sudo apt update

sudo apt install \
	libssl-dev \
	device-tree-compiler \
	swig \
	python3-dev \
	python3-setuptools

make
```

자료의 빌드 결과물은 `u-boot`, `u-boot.bin`이다.
이후 QEMU 명령에서는 `u-boot`를 사용한다.

### 4. QEMU 실행
```sh
sudo apt install qemu-system-arm

qemu-system-arm \
	-M vexpress-a9 \
	-m 128M \
	-nographic \
	-kernel u-boot
```

| 옵션 | 의미 |
|---|---|
| `-M vexpress-a9` | 에뮬레이션할 보드 지정 |
| `-m 128M` | 에뮬레이션 메모리 128MB 지정 |
| `-nographic` | 그래픽 창 없이 터미널에서 사용 |
| `-kernel u-boot` | 이 실습에서는 U-Boot 바이너리를 직접 적재·실행 |

자료의 3초 자동 부팅 대기 시간 안에 키를 누르면 `=>` 프롬프트가 나온다.
```
=> help
```

- `Ctrl+a`를 누른 뒤 `h`: QEMU 제어 도움말
- `Ctrl+a`를 누른 뒤 `x`: QEMU 종료

> **혼동 주의**
> 옵션 이름이 `-kernel`이어도 이 명령에서 실행하는 파일은 리눅스 커널이 아니라 `u-boot`다.
> 또한 이 방식은 U-Boot를 직접 실행하므로 실제 보드의 ROM부터 이어지는 전체 부팅 과정을 재현하는 것은 아니다.

## 실습 2: SD 이미지와 환경변수 저장
### 1. SD 이미지 생성
```sh
# 0으로 채운 약 1GiB 크기의 이미지 파일을 만든다.
dd if=/dev/zero of=sd.img bs=1M count=1024

cfdisk sd.img
```

`cfdisk`에서는 `dos` 레이블을 선택하고 아래 세 개의 primary 파티션을 만든 뒤 `Write`로 저장한다.

| 파티션 | 크기 | 설정·용도 |
|---|---|---|
| 1 | 64MB | FAT16 타입, bootable, 부팅 관련 파일·환경변수용 |
| 2 | 8MB | Linux 타입, 루트 파일시스템용 |
| 3 | 나머지 | Linux 타입, 데이터 파일시스템용 |

**파티션 타입 지정과 포맷은 서로 다른 작업이다.**
이 실습에서는 이후 첫 번째 파티션에 실제 FAT16 파일시스템을 만든다.
자료에는 2·3번 파티션의 포맷 및 커널·루트 파일시스템 배치 과정은 제시되지 않는다.

### 2. 이미지 파일을 loop 장치로 연결
```sh
sudo losetup -f --show --partscan sd.img
```

| 옵션 | 의미 |
|---|---|
| `-f` | 사용 가능한 loop 장치를 찾음 |
| `--show` | 선택된 장치 경로를 출력 |
| `--partscan` | 이미지의 파티션을 검색해 파티션별 장치 생성 |

```sh
sudo dmesg
```
```
[ 5064.705780] loop0: detected capacity change from 0 to 2097152
[ 5064.706181] loop0: p1 p2 p3
```

예를 들어 출력이 `/dev/loop0`이면 첫 번째 파티션은 `/dev/loop0p1`이다.
**실제 출력된 번호를 사용해야 한다.**

```sh
sudo mkfs.vfat \
	-F 16 \
	-n BOOT /dev/loop0p1
```
- `-F 16`: FAT16으로 포맷
- `-n BOOT`: 파일시스템 레이블을 `BOOT`로 지정

- `losetup -d`: 이미지와 loop 장치의 연결 해제
```sh
sudo losetup -d /dev/loop0
```

### 3. SD 이미지를 연결하고 환경변수 저장 확인
```sh
qemu-system-arm \
	-M vexpress-a9 \
	-m 128M \
	-nographic \
	-kernel u-boot \
	-sd sd.img
```

U-Boot에서 다음 순서로 실행한다.
1. `setenv foo bar`: 현재 환경변수 `foo`를 `bar`로 설정
2. `saveenv`: 환경변수를 설정된 영구 저장소에 저장
3. `reset`: 재부팅
```
=> setenv foo bar
=> saveenv
=> reset
```

재부팅 후 자동 부팅을 중단하고 확인한다.
- `printenv foo`: 저장된 값 확인
```
=> printenv foo
```
```
foo=bar
```

> **핵심**
> 값을 바꾸는 것과 영구 저장하는 것은 다르다.
> 재부팅 후에도 값이 남는지 확인해야 저장 실습이 완료된다.

## 실습 3: 호스트와 QEMU 네트워크 연결
### 1. 네트워크 구조
```
호스트 Linux                        QEMU 속 U-Boot
TAP 인터페이스                      에뮬레이션 NIC
192.168.76.1/24  ←────────────────→  192.168.76.100
TFTP 서버 측                       파일을 요청하는 측
```

- **TAP**: 호스트 쪽의 소프트웨어 네트워크 인터페이스.
- **NIC**: 에뮬레이션된 보드에 추가하는 네트워크 장치.
- `ipaddr`: U-Boot 자신의 IP 주소.
- `serverip`: 파일을 제공하는 서버의 IP 주소.

### 2. 호스트 인터페이스 설정 스크립트
`qemu-myifup` 파일을 아래 내용으로 만든다.
```sh
cat << 'EOF' > qemu-myifup
#!/bin/sh
ip addr replace 192.168.76.1/24 dev "$1"
ip link set "$1" up
EOF
```
`$1`은 QEMU가 스크립트에 전달한 인터페이스 이름이다.

```sh
chmod +x qemu-myifup

sudo qemu-system-arm \
	-M vexpress-a9 \
	-m 128M \
	-nographic \
	-kernel u-boot \
	-sd sd.img \
	-net tap,script=./qemu-myifup \
	-net nic
```

호스트에서 `ip a`로 확인한다.
강의의 예시 출력은 `tap0`에 `192.168.76.1/24`가 설정된 상태다.
```sh
ip a
```
```
5: tap0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UNKNOWN group default qlen 1000
	link/ether 8a:c6:da:bc:b1:58 brd ff:ff:ff:ff:ff:ff
	inet 192.168.76.1/24 scope global tap0
		valid_lft forever preferred_lft forever
	inet6 fe80::88c6:daff:febc:b158/64 scope link
		valid_lft forever preferred_lft forever
```

### 3. U-Boot 주소 설정과 통신 확인
```
=> setenv ipaddr 192.168.76.100
=> setenv serverip 192.168.76.1
=> saveenv
=> ping 192.168.76.1
```
```
host 192.168.76.1 is alive
```

**이 단계의 확인 대상은 네트워크 연결이다.**
다음 단계에서 파일 전송을 확인한다.

## 실습 4: TFTP로 파일을 RAM에 적재
**TFTP (Trivial File Transfer Protocol)**

이 실습의 목적은 개발 PC에 있는 파일을 네트워크로 받아 **U-Boot가 사용하는 RAM에 적재하는 것**이다.

### 1. 호스트 준비
```sh
sudo apt install tftpd-hpa
```

자료에서 사용하는 TFTP 디렉터리는 `/srv/tftp`다.
여기에 내용이 있는 `textfile.txt`를 만든다.
```sh
cd /srv/tftp

echo "This is a sample text." | sudo tee textfile.txt

sudo chmod 644 textfile.txt
```

### 2. 메모리 위치 확인과 전송
1. 보드 정보와 DRAM 정보 확인
```
=> bdinfo
```
```
boot_params = 0x60002000
DRAM bank   = 0x00000000
-> start    = 0x60000000
-> size     = 0x08000000
```

2. 서버 파일을 받아 해당 RAM 주소에 적재
	- DRAM 시작 주소는 `0x60000000`이며, 전송 테스트에는 `0x61000000`을 사용한다.
```
=> tftp 0x61000000 textfile.txt
```

3. 해당 주소의 메모리 내용 표시
```
=> md 0x61000000
```
```
61000000: 73696854 20736920 61732061 656c706d This is a sample
61000010: 78657420 000a2e74 00000000 00000000  text...........
```

```
호스트 /srv/tftp/textfile.txt
              ↓ TFTP 전송
U-Boot RAM의 0x61000000
              ↓ md 명령
수신한 내용 확인
```

`0x61000000`은 `0x60000000`에서 **16MiB 뒤**의 주소다.
이 주소는 강의 보드의 예시이며 다른 보드에서도 그대로 사용할 수 있다는 뜻은 아니다.

> **확인할 결과**
> 전송이 성공하고, `md`로 파일의 내용이 메모리에 들어온 것을 확인한다.
> 이 과정은 파일 적재 실습이며 커널 실행까지 수행하는 실습은 아니다.

### 3. TAP 실행이 어려울 때 자료의 대안
MobaXterm에서 TAP 방식의 QEMU 실행이 안 될 때 다음을 제안한다.
1. VirtualBox 콘솔 내부의 터미널에서 실행한다.
2. `-net tap` 대신 QEMU의 사용자 네트워크를 사용한다.

사용자 네트워크 방식의 명령:
```sh
sudo qemu-system-arm \
	-M vexpress-a9 \
	-m 128M \
	-nographic \
	-kernel u-boot \
	-sd sd.img \
	-net user,tftp=/srv/tftp \
	-net nic
```

U-Boot 주소 설정:
```
=> setenv ipaddr 10.0.2.15
=> setenv serverip 10.0.2.2
```

이 명령은 `tftp=/srv/tftp`로 QEMU 사용자 네트워크의 TFTP 제공 디렉터리를 지정한다.
**TAP 실습의 주소와 사용자 네트워크 실습의 주소를 섞지 말자.**

| 방식 | U-Boot `ipaddr` | U-Boot `serverip` |
|---|---|---|
| TAP | `192.168.76.100` | `192.168.76.1` |
| 사용자 네트워크 | `10.0.2.15` | `10.0.2.2` |

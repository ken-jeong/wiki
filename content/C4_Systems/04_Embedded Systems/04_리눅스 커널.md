## 1. 먼저 잡아야 할 전체 흐름
커널은 하드웨어 자원을 관리한다.
커널을 직접 사용하려면 대상 장치에 맞게 기능을 설정하고 빌드한 뒤, 부트로더로 메모리에 올려 실행한다.

1. **소스 준비**: 사용할 커널 버전의 소스를 확보한다.
2. **빌드 환경 설정**: 대상 CPU와 크로스 컴파일러를 지정한다.
3. **기능 설정**: 기본 설정을 불러오고 필요한 옵션을 조정한다.
4. **컴파일**: 커널 이미지, DTB, 모듈 등을 만든다.
5. **적재·부팅**: U-Boot가 커널 이미지와 DTB를 RAM에 올리고 커널을 시작한다.
6. **동작 확인**: 콘솔과 커널 로그로 진행 상태를 확인한다.

이 강의의 실습 대상은 **ARM VExpress 보드 환경**이며, QEMU로 실행한다.

## 2. 커널은 무엇을 하는가?
### 2.1. 세 가지 역할
**커널 (Kernel)**
- 응용 프로그램과 하드웨어 사이에서 자원 사용을 관리한다.

| 역할         | 의미                                            |
| ---------- | --------------------------------------------- |
| **하드웨어 자원 관리** | CPU, 메모리, 입출력 장치를 관리한다.                       |
| **인터페이스 제공**   | 응용 프로그램과 라이브러리가 하드웨어 자원을 사용할 수 있도록 API를 제공한다. |
| **동시 접근 관리**   | 여러 프로그램이 같은 자원을 함께 사용할 때 접근과 사용을 조정한다.        |

### 2.2. 시스템 콜: 사용자 공간과 커널의 접점
**시스템 콜 (System Call)**
- 사용자 공간에서 커널 기능을 요청하는 인터페이스다.
- 주요 기능
	- 파일·장치 조작, 네트워킹, 프로세스 간 통신에 사용한다.
	- 프로세스 관리, 메모리 매핑, 타이머, 스레드, 동기화 기능도 포함한다.
- C 라이브러리 함수가 시스템 콜을 감싸 제공한다.

**호출 관계**
- ==응용 프로그램 → C 라이브러리의 호출 인터페이스 → 시스템 콜 → 커널 → 하드웨어==
- *다만 모든 C 라이브러리 함수가 시스템 콜을 수행하는 것은 아니다.*

### 2.3. 의사 파일 시스템: 커널 정보를 파일처럼 보기
**의사 파일 시스템 (Pseudo File System)**
- 디스크에 저장한 일반 파일 대신, **커널이 제공하는 정보를 디렉터리와 파일 형태로 보여주는 인터페이스**다.
- 정보는 커널에 의해 생성·갱신된다.

| 구분        | 마운트 위치  | 주요 내용                  | 암기 포인트       |
| --------- | ------- | ---------------------- | ------------ |
| **proc**  | `/proc` | 프로세스 정보, 메모리 관리 파라미터 등 | 프로세스·운영체제 정보 |
| **sysfs** | `/sys`  | 장치와 관련된 커널 프레임워크의 정보   | 장치 구조·정보     |

**구분**:
- 시스템 콜은 커널 기능을 요청하는 접점이다.
- `/proc`·`/sys`는 커널 정보를 파일 형태로 접하는 방법이다.

## 3. 커널 버전과 소스 구조
### 3.1. Mainline, Stable, LTS
| 구분       | 학습용 의미                                                    |
| -------- | --------------------------------------------------------- |
| Mainline | 새로운 개발 내용이 통합되는 주 개발 계열. 강의에서는 Torvalds가 릴리스하는 버전으로 소개한다. |
| Stable   | 릴리스된 커널의 수정 사항을 관리하는 계열                                   |
| LTS      | Long Term Support. 장기간 유지보수하는 커널 계열                       |

실습에서는 **`linux-6.1.y` 계열을 선택**한다.

### 3.2. 소스가 커도 실행 이미지가 같은 크기는 아니다
강의의 v5.18 예시는 약 **8만 파일, 3,500만 줄, 1.3GiB의 소스**와 **수 MB 수준의 커널 이미지**를 대비한다.

소스 트리에는 다양한 아키텍처와 장치의 코드가 함께 들어 있다.
설정 과정에서 대상 환경에 필요한 기능을 선택하므로, **전체 소스의 크기와 실제 빌드 결과물의 크기를 구분**해야 한다.

### 3.3. 자주 볼 디렉터리와 파일
| 이름                                            | 살펴볼 내용                                |
| --------------------------------------------- | ------------------------------------- |

| `arch/`                                       | 아키텍처별 코드. 약 11.6%                     |
| `fs/`                                         | 파일시스템                                 |
| `net/`                                        | 네트워킹                                  |
| `mm/`                                         | 메모리 관리                                |
| `kernel/`                                     | 커널 핵심 기능                              |
| `include/`                                    | 헤더 파일                                 |
| `Documentation/`                              | 문서                                    |
| `Kconfig`                                     | 설정 옵션과 의존 관계 정의                       |

**구분**:
- `Kconfig`는 선택 가능한 옵션의 정의이다.
- `.config`는 선택 결과이다.

## 4. 크로스 컴파일 환경
### 4.1. `ARCH`와 `CROSS_COMPILE`의 차이
**크로스 컴파일**
- 빌드하는 컴퓨터와 다른 대상 환경에서 실행할 코드를 만드는 것이다.

| 설정 | 답하는 질문 | 예시 |
|---|---|---|
| `ARCH` | 어떤 CPU 아키텍처용으로 만들 것인가? | `arm`, `arm64`, `riscv` |
| `CROSS_COMPILE` | 어떤 접두사의 도구 체인을 사용할 것인가? | `arm-linux-gnueabi-` |
| `PATH` | 컴파일러 실행 파일을 어디에서 찾을 것인가? | 도구 체인의 `bin/` 경로 추가 |

강의의 GCC 호출 형태는 `$(CROSS_COMPILE)gcc`다.
```text
CROSS_COMPILE=arm-linux-gnueabi-
컴파일러 이름=arm-linux-gnueabi-gcc
```

**접두사의 마지막 `-`도 포함한다.**
설치된 실행 파일이 `arm-linux-gcc`라면 접두사는 `arm-linux-`여야 한다.
강의에는 여러 접두사 예시가 나오므로 실제 설치한 도구의 이름과 맞춰야 한다.

### 4.2. 두 가지 전달 방법
```sh
# 방법 1: 명령마다 전달
make ARCH=arm CROSS_COMPILE=arm-linux- vexpress_defconfig
```

```sh
# 방법 2: 현재 셸의 환경변수로 지정
export ARCH=arm
export CROSS_COMPILE=arm-linux-
make vexpress_defconfig
```

도구 체인의 `bin/` 디렉터리가 `PATH`에 있어야 한다.
강의의 `/home/c2kp/x-tools/.../bin/` 경로는 실습 환경의 예시이므로 자신의 설치 경로에 맞춘다.

## 5. 커널 기능 설정
### 5.1. 기본 설정에서 세부 설정으로
```sh
# 강의의 Debian/Ubuntu 환경에서 필요한 패키지
sudo apt install bc libncurses-dev

# 사용 가능한 타깃과 도움말 확인
make help

# VExpress용 기본 설정으로 .config 생성
make vexpress_defconfig

# 메뉴에서 세부 옵션 조정
make menuconfig
```

`menuconfig`
- 그래픽 데스크톱 없이 터미널에서 사용할 수 있다.
- 검색과 숫자 단축키를 이용하면 옵션 위치로 빠르게 이동할 수 있다.

### 5.2. 내장 기능과 모듈
| 구분    | 내장(built-in)     | 모듈(module)         |
| ----- | ---------------- | ------------------ |
| 설정값   | `y`              | `m`                |
| 저장 형태 | 커널 이미지에 포함       | 별도의 `.ko` 파일       |
| 사용 시점 | 커널 시작 단계에서 사용 가능 | 모듈 파일을 읽어 적재한 뒤 사용 |
| 특징    | 커널과 함께 적재됨       | 동적으로 적재·해제할 수 있음   |

**생각할 문제**: 파일시스템에 접근하는 데 꼭 필요한 기능을 그 파일시스템 안의 모듈로만 둔다면, 그 모듈을 먼저 읽을 수 있을까?

강의는 이 문제를 설명하기 위해 초기 부팅 단계에서 모듈을 사용할 수 없다고 단순화한다. 여기서는 특히 **initramfs 없이 부팅하는 실습 조건**에 연결해 이해한다. 초기 부팅용 파일시스템에 모듈을 담는 경우까지 일반화하지 않는다.

### 5.3. 옵션 타입과 `.config` 표현
| 타입         | 가능한 값·예시                            | 의미          |
| ---------- | ----------------------------------- | ----------- |
| `bool`     | `y`, 비활성화                           | 포함 여부       |
| `tristate` | `y`, `m`, 비활성화                      | 내장·모듈·제외 선택 |
| `int`      | 정수                                  | 수치 설정       |
| `hex`      | `CONFIG_PAGE_OFFSET=0xC0000000`     | 16진수 설정     |
| `string`   | `CONFIG_LOCALVERSION="-no-network"` | 문자열 설정      |

`.config`
- 설정 결과를 저장하는 텍스트 파일이다.
- 항목에는 `CONFIG_` 접두사가 붙으며, 빌드 시스템이 이 값을 사용한다.
```text
CONFIG_ISO9660_FS=m
CONFIG_JOLIET=y
# CONFIG_VFAT_FS is not set
```
- `=y`: 커널 이미지에 포함
- `=m`: 모듈로 빌드
- `# ... is not set`: 비활성화

강의에서는 **`.config`를 직접 편집하지 않고 설정 도구를 사용**하도록 안내한다.
- `CONFIG_GCC_PLUGINS` 비활성화
- `CONFIG_DEVTMPFS_MOUNT` 활성화

### 5.4. 옵션 의존성: `depends on`과 `select`
**`depends on`: 선택의 전제 조건**
```text
config B
    depends on A
```

강의의 단순화된 예시에서는 A가 활성화되어야 B가 나타나고 선택할 수 있다.
**A를 켠다고 B가 자동으로 켜지는 것은 아니다.**

**`select`: 다른 옵션의 활성화**
```text
config A
    select B
```

A를 활성화하면 B도 활성화되도록 지정한다.

**암기**
- `depends on`은 “선택하려면 필요”
- `select`는 “선택하면 함께 활성화”

### 5.5 강의에서 조정하는 옵션
- `CONFIG_GCC_PLUGINS`: 비활성화
- `CONFIG_DEVTMPFS_MOUNT`: 활성화

이는 **강의 실습에서 지정한 설정**이며, 모든 커널 빌드에 공통으로 적용할 규칙은 아니다.

## 6. 컴파일과 결과물
### 6.1 병렬 빌드
앞에서 지정한 `ARCH`, `CROSS_COMPILE` 환경변수가 유지되는 셸에서 실행한다.
```sh
make -j$(nproc)
```
- `nproc`: 사용 가능한 처리 장치 수 확인
- `$(nproc)`: 출력값을 명령에 넣는 셸 표현
- `-j`: 동시에 실행할 빌드 작업 수 지정
- `make -j20`: 작업 수를 20으로 직접 지정한 예시

### 6.2 무엇이 만들어지는가?
| 결과물        | 역할                                 | 강의의 예시                                         |
| ---------- | ---------------------------------- | ---------------------------------------------- |
| `Image`    | 압축되지 않은 부팅용 커널 이미지                 | `arch/<arch>/boot/Image`                       |
| 압축된 커널 이미지 | 대상 플랫폼의 부팅에 사용                     | ARM `zImage`, x86 `bzImage`, RISC-V `Image.gz` |
| `.dtb`     | 컴파일된 장치 트리. 대상 하드웨어 정보를 전달         | `vexpress-v2p-ca9.dtb`                         |
| `.ko`      | 커널 모듈 파일                           | 소스 트리의 해당 기능 위치에 생성                            |
| `vmlinux`  | 압축되지 않은 ELF 형식 커널. 강의에서는 디버깅용으로 설명 | 소스 트리 최상위                                      |

**이 실습의 부팅 입력은 `zImage`와 DTB다.**
`vmlinux`와 `zImage`를 혼동하지 않는다.
이미지 이름과 DTB 경로는 아키텍처·소스 버전에 따라 달라질 수 있다.

### 6.3. 빌드 파일 청소
| 명령               | 삭제 범위                            | `.config` 보존 |
| ---------------- | -------------------------------- | ------------ |
| `make clean`     | 생성된 파일 대부분. 일부 빌드 지원 파일은 유지      | 예            |
| `make mrproper`  | 생성 파일, 설정 파일, 여러 백업 파일           | 아니요          |
| `make distclean` | `mrproper` 범위와 편집기 백업·패치 잔여 파일 등 | 아니요          |

**복습 포인트**
- 설정을 유지한 채 빌드 결과물을 정리하려면 `clean`
- `mrproper`와 `distclean`은 설정도 지운다.

## 7. U-Boot로 커널 적재·부팅
### 7.1 역할을 먼저 구분하기
| 구성 요소      | 실습에서 하는 일               |
| ---------- | ----------------------- |
| QEMU       | VExpress-A9 하드웨어 환경 실행  |
| U-Boot     | 커널·DTB를 RAM에 적재하고 커널 실행 |
| TFTP 서버    | 네트워크로 커널·DTB 파일 제공      |
| `zImage`   | 실행할 커널                  |
| DTB        | 대상 하드웨어 정보              |
| `bootargs` | 커널에 전달할 명령행 인자          |
| `bootcmd`  | U-Boot의 자동 부팅 명령        |

**전체 순서**
- QEMU에서 U-Boot 실행 → TFTP로 파일 적재 → `bootz`로 커널 시작 → 커널의 루트 파일시스템 접근 단계

### 7.2 호스트에서 QEMU 실행
> 다음 명령은 기존 `u-boot`, `sd.img`, TAP 설정 스크립트와 TFTP 서버가 준비된 강의 환경을 전제로 한다.
```sh
cd ~/u-boot &&
sudo qemu-system-arm \
  -machine vexpress-a9 \
  -m 128M \
  -nographic \
  -kernel u-boot \
  -drive file=sd.img,if=sd,format=raw \
  -nic tap,model=lan9118,script=./qemu-myifup
```
여기서 QEMU의 `-kernel u-boot`는 **U-Boot를 실행하기 위한 지정**이다.
Linux 커널은 이후 U-Boot에서 적재한다.

### 7.3. 호스트에서 부팅 파일 준비
커널 소스 최상위 디렉터리에서 실행하는 형태로 경로를 정리했다.
```sh
ls -l arch/arm/boot/zImage
ls -l arch/arm/boot/dts/*.dtb

sudo cp arch/arm/boot/zImage /srv/tftp/
sudo cp arch/arm/boot/dts/vexpress-v2p-ca9.dtb /srv/tftp/
```
강의의 DTB 경로를 기준으로 했다.
실제 생성 위치가 다르면 해당 파일 경로를 사용한다.

### 7.4. U-Boot 프롬프트에서 부팅
아래는 **U-Boot 명령**이다.
```text
setenv bootargs console=ttyAMA0
saveenv

tftp 0x61000000 zImage
tftp 0x62000000 vexpress-v2p-ca9.dtb
bootz 0x61000000 - 0x62000000
```

| 항목 | 의미 |
|---|---|
| `0x61000000` | 강의에서 커널 이미지를 적재하는 RAM 주소 |
| `0x62000000` | 강의에서 DTB를 적재하는 RAM 주소 |
| `bootz`의 첫 번째 인자 | `zImage`가 있는 주소 |
| 가운데 `-` | initramfs를 전달하지 않음 |
| 마지막 인자 | DTB가 있는 주소 |

이 주소들은 **강의의 보드 메모리 배치에 맞춘 값**이다.

### 7.5. 자동 부팅 명령 저장
```text
setenv bootcmd 'tftp 0x61000000 zImage; tftp 0x62000000 vexpress-v2p-ca9.dtb; bootz 0x61000000 - 0x62000000'
saveenv
reset
```
- `bootcmd`: 파일 적재와 커널 시작 명령을 묶는다.
- `saveenv`: 환경변수를 저장한다.
- `reset`: 재시작하여 부팅을 확인한다.

### 7.6. 커널이 시작된 뒤 panic이 발생하는 이유
강의는 **커널이 부팅되다가 최종적으로 panic이 발생하는 단계**까지 진행한다.

실습 명령을 보면 커널과 DTB는 전달하지만, `bootargs`에는 콘솔만 지정하고 initramfs도 전달하지 않는다.
따라서 **루트 파일시스템을 사용할 수 있는 구성이 부족한 것이 원인 후보**다.
원문은 최종 panic 메시지를 제시하지 않으므로 정확한 원인은 실제 로그로 확인해야 한다.

**구분**: 커널이 실행되어 로그를 출력하는 것과, 루트 파일시스템을 사용해 사용자 공간까지 시작하는 것은 서로 다른 부팅 단계다.

## 8. 커널 명령행과 로그
### 8.1. 커널 명령행 인자
| 인자          | 역할                      | 강의 예시                                |
| ----------- | ----------------------- | ------------------------------------ |
| `console=`  | 커널 메시지를 보낼 콘솔 지정        | `console=ttyAMA0` 또는 `console=ttyS0` |
| `root=`     | 루트 파일시스템이 있는 장치 지정      | `root=/dev/mmcblk0p2`                |
| `rootwait`  | 루트 장치가 준비될 때까지 기다리도록 지정 | `rootwait`                           |
| `loglevel=` | 콘솔에 표시할 커널 로그 수준 지정     | `loglevel=5`                         |

강의의 일반 예시:
```text
console=ttyS0 root=/dev/mmcblk0p2 rootwait
```

U-Boot에서는 이 문자열을 **`bootargs` 환경변수로 전달**한다.
실제 VExpress 실습의 콘솔은 `ttyAMA0`이므로 일반 예시의 `ttyS0`과 구분한다.

**주의**: `root=`는 사용할 루트 장치를 지정한다. 루트 파일시스템 자체를 만들어 주는 명령은 아니다.

### 8.2. 커널 로그 읽기와 쓰기
Linux 사용자 공간이 실행된 뒤 커널 로그를 확인한다.
```sh
sudo dmesg
```

강의에서는 사용자 공간에서 `/dev/kmsg`를 통해 커널 로그에 메시지를 넣는 방법도 보여준다.
```sh
sudo sh -c 'echo "Debu" > /dev/kmsg'
sudo dmesg
```

| 구분 | 핵심 역할 |
|---|---|
| `console=` | 부팅 중 메시지를 표시할 위치 지정 |
| `dmesg` | Linux 사용자 공간에서 커널 로그 확인 |
| `/dev/kmsg`에 쓰기 | 사용자 공간에서 커널 로그에 메시지 추가 |

강의의 panic 단계에서는 사용자 공간에 도달하지 못할 수 있으므로, 먼저 **직렬 콘솔에 나타난 부팅 로그**를 확인한다.

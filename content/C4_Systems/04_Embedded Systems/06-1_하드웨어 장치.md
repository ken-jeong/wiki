> Linux가 하드웨어를 어떻게 표현하고,
> 드라이버를 어떻게 적재하며,
> 하드웨어 정보를 어떻게 전달받는지 설명한다.

## 0. 먼저 전체 흐름 잡기
이 강의는 다음 세 질문으로 연결된다.

| 질문                          | 핵심 개념                        |
| --------------------------- | ---------------------------- |
| 응용 프로그램은 장치에 어떻게 접근하는가?     | 소프트웨어 스택, `/dev`, `/sys`, 소켓 |
| 필요한 드라이버 코드는 어떻게 커널에 들어오는가? | 커널 모듈, `insmod`, `modprobe`  |
| 커널은 장치의 존재와 연결 정보를 어떻게 아는가? | Device Tree, 버스의 자동 발견       |

**핵심 연결**
- 하드웨어 정보로 장치를 파악하고
- → 적합한 드라이버와 연결하고
- → 커널 서브시스템을 통해 → 사용자 공간에 기능을 제공한다.

## 1. 장치 접근을 위한 소프트웨어 스택
### 1.1. 계층별 역할
```text
응용 프로그램
  ↓ 라이브러리를 사용하거나 직접 접근
커널 / 사용자 공간 인터페이스
  ↓
드라이버 서브시스템
  ↓
디바이스 드라이버
  ↓
버스 서브시스템
  ↓
버스 컨트롤러 드라이버
  ↓
버스 컨트롤러 ↔ 버스에 연결된 장치
```

| 계층 | 담당 역할 | 이해할 때의 질문 |
|---|---|---|
| 응용 / 라이브러리 | 사용자 공간에서 장치 기능 요청 | 무엇을 하고 싶은가? |
| 드라이버 서브시스템 | 같은 종류의 장치에 공통 인터페이스 제공 | 어떤 종류의 기능인가? |
| 디바이스 드라이버 | 특정 장치의 동작 제어 | 이 장치를 어떻게 조작하는가? |
| 버스 서브시스템 | I2C, SPI, USB, PCI 등의 접근 API 제공 | 어떤 통신 규칙으로 전달하는가? |
| 버스 컨트롤러 드라이버 | 실제 버스 컨트롤러 구동 | 이 컨트롤러로 어떻게 전송하는가? |

**GPIO 확장기 예**
- GPIO 기능을 요청하면 GPIO 서브시스템과 확장기 드라이버를 거치고,
- I2C 서브시스템 및 I2C 컨트롤러 드라이버를 통해 실제 확장기에 접근한다.

> **구별하기**
> 디바이스 드라이버는 ‘연결된 장치’를,
> 버스 컨트롤러 드라이버는 ‘통신을 담당하는 컨트롤러’를 제어한다.

### 1.2. 커널 서브시스템과 장치 클래스
| 서브시스템 / 클래스 | 대상                            |
| ----------- | ----------------------------- |
| 네트워킹 스택     | Ethernet, WiFi, CAN, 802.15.4 |
| GPIO        | 범용 입출력                        |
| Video4Linux | 카메라, 비디오 인코더·디코더              |
| DRM         | 디스플레이 컨트롤러, GPU               |
| ALSA        | 오디오                           |
| IIO         | ADC, DAC, 자이로스코프, 센서          |
| MTD         | 플래시 메모리                       |
| PWM         | 펄스 폭 변조                       |
| 입력 서브시스템    | 키보드, 마우스, 터치스크린, 조이스틱         |
| Watchdog    | 시스템 감시                        |
| RTC         | 실시간 클럭                        |
| remoteproc  | 보조 프로세서                       |
| crypto      | 암호화 가속기                       |
| hwmon       | 하드웨어 감시 센서                    |
| block layer | 블록 저장장치                       |

**장치 종류마다 기능을 공통으로 다루는 서브시스템이 있다.**

## 2. 사용자 공간에서 장치에 접근하기
### 2.1. 세 가지 인터페이스
| 인터페이스            | 주된 목적                        | 예                   |
| ---------------- | ---------------------------- | ------------------- |
| `/dev`의 디바이스 노드  | 장치 기능과 데이터에 접근               | 직렬 포트, 카메라, 저장장치    |
| sysfs, 보통 `/sys` | 장치의 속성, 연결 관계, 상태 확인 및 일부 제어 | 드라이버 연결, LED·PWM 속성 |
| 네트워크 소켓과 관련 API  | 네트워크 기능 사용                   | 네트워크 통신             |

**기억할 문장**
- `/dev`는 장치에 접근하는 통로,
- `/sys`는 장치의 속성과 구조를 보여 주는 창이다.

일부 장치는 sysfs를 통해 기능을 제어한다.
따라서 `/sys`를 단순한 ‘읽기 전용 정보’로 생각하면 안 된다.
또한 모든 장치에 `/dev` 노드가 필요한 것은 아니다.

### 2.2. 문자 디바이스와 블록 디바이스
| 구분         | 문자 디바이스                 | 블록 디바이스                |
| ---------- | ----------------------- | ---------------------- |
| 기본적인 접근 모델 | 바이트 단위 입출력 등 장치별 인터페이스  | 고정 크기 블록 단위 데이터 접근     |
| 대표 예       | 직렬 포트, 터미널, 오디오, 비디오 입력 | 하드디스크, USB 저장장치, SD 카드 |
| `mknod` 타입 | `c`                     | `b`                    |

> **이해 보충**
> 문자 디바이스를 직렬 포트 같은 ‘끝없는 바이트 스트림’으로 설명하지만, 모든 문자 디바이스가 똑같은 스트림 동작을 하는 것은 아니다.
> 핵심은 블록 장치와 구분되는 장치 인터페이스라는 점이다.

커널은 디바이스 노드를 다음 조합으로 구별한다.
```text
디바이스 타입(문자 / 블록) + major 번호 + minor 번호
```
- **Major**: 자료에서는 장치의 카테고리로 설명한다. 커널에서 해당 장치를 처리하는 드라이버 계열을 찾는 기준으로 이해한다.
- **Minor**: 해당 계열 안의 개별 장치 등을 구별한다.

### 2.3. 디바이스 파일과 생성 방식
장치 파일도 `open()`, `read()`, `write()`, `close()` 같은 파일 API를 통해 사용할 수 있다.
자료의 예는 `/dev/ttyS0`를 열고 문자열을 쓰는 코드다.

수동 생성 명령의 형식:
```sh
mknod /dev/<device> [c|b] <major> <minor>
```

위 코드는 형식 설명용이다.
`[c|b]`에서는 문자 장치면 `c`, 블록 장치면 `b`를 선택한다.

| 구성 요소 | 역할 |
|---|---|
| `mknod` | 지정한 타입과 번호의 디바이스 노드를 수동 생성 |
| `devtmpfs` | 마운트되면 커널이 디바이스 노드를 생성하는 데 사용 |
| `udev` | 장치 등장·제거 이벤트를 받아 규칙에 따라 처리하는 데몬 |
| `mdev` | BusyBox에 포함된 경량 장치 관리 도구 |

udev 규칙 파일 위치: `/lib/udev/rules.d`, `/etc/udev/rules.d`

> **이해 보충**
> `mknod`로 노드를 만든다고 하드웨어가 생기거나 드라이버가 적재되는 것은 아니다.
> 노드는 접근을 위한 입구다.

### 2.4. 대표적인 `/dev` 경로
| 장치          | 경로 패턴                                        |
| ----------- | -------------------------------------------- |
| 직렬 포트       | `/dev/ttyS*`, `/dev/ttyUSB*`, `/dev/ttyACM*` |
| GPIO 컨트롤러   | `/dev/gpiochipX`                             |
| 블록 저장장치     | `/dev/sd*`, `/dev/mmcblk*`, `/dev/nvme*`     |
| 플래시 메모리     | `/dev/mtd*`                                  |
| 디스플레이 / GPU | `/dev/dri/*`                                 |
| 오디오         | `/dev/snd/*`                                 |
| 카메라         | `/dev/video*`                                |
| Watchdog    | `/dev/watchdog*`                             |
| 입력장치        | `/dev/input/*`                               |

### 2.5. sysfs 구조 읽기
sysfs는 같은 장치를 버스, 클래스, 실제 연결 구조 등 여러 관점에서 보여 준다.

| 경로 | 의미 |
|---|---|
| `/sys/devices/` | 시스템의 장치 계층 |
| `/sys/bus/` | 버스 종류별 분류 |
| `/sys/class/` | 기능·클래스별 분류: input, leds, pwm 등 |
| `/sys/block/` | 블록 장치에 대한 심볼릭 링크 |
| `/sys/dev/block/` | major:minor 기준 블록 장치 링크 |
| `/sys/dev/char/` | major:minor 기준 문자 장치 링크 |
| `/sys/firmware/` | 펌웨어 관련 정보 |
| `/sys/firmware/devicetree/` | Device Tree를 디렉터리·파일로 표현 |
| `/sys/fs/` | 파일시스템 관련 속성 |
| `/sys/kernel/` | 커널 서브시스템 관련 속성 |
| `/sys/module/` | 커널 모듈 정보 |
| `/sys/power/` | 전력 관리 관련 속성 |

**I2C 장치 예**:
```text
/sys/bus/i2c/
├── drivers/             # I2C 장치 드라이버
└── devices/             # I2C 장치
    └── 0-002a/
        ├── driver      # 연결된 드라이버를 가리키는 심볼릭 링크
        └── of_node     # 장치를 설명하는 Device Tree 노드 링크
```
`0-002a`는 I2C 버스 0의 주소 `0x2a`인 장치를 나타내는 식으로 읽는다.

자료에서 제시한 sysfs 접근 예:
- LED: `/sys/class/leds`
- PWM: `/sys/class/pwm`
- IIO: `/sys/bus/iio`

### 2.6. GPIO 접근
권장하는 방식은 **문자 디바이스 기반 GPIO 인터페이스와 libgpiod**다.

| 항목 | 내용 |
|---|---|
| 장치 노드 | `/dev/gpiochipX` |
| 라이브러리 | `libgpiod`, C 라이브러리 |
| `gpiodetect` | GPIO 칩 확인 |
| `gpioget` | GPIO 값 읽기 |
| `gpioset` | GPIO 값 설정 |

자료의 예전 sysfs GPIO 경로는 `/sys/class/gpios`로 적혀 있다.
**이해 보충**: 통상적인 경로 표기는 `/sys/class/gpio`다.

## 3. 커널 모듈
### 3.1. 왜 모듈로 나누는가?
커널 모듈은 실행 중인 커널에 적재할 수 있는 코드다.
자료에서는 특히 드라이버를 모듈로 사용하는 경우를 다룬다.

1. 필요한 기능을 분리해 커널 이미지 크기를 줄인다.
2. 하드웨어가 감지되면 필요한 드라이버를 적재할 수 있다.
3. 드라이버 개발 중 재부팅 없이 수정·빌드·시험하는 흐름을 지원한다.

| 항목 | 내용 |
|---|---|
| 파일 확장자 | `.ko`, Kernel Object |
| 설치 위치 | `/lib/modules/<kernel-version>/` |
| `modules.dep` | 모듈 간 의존성 정보 |
| `modules.alias` | 장치 식별 정보 등과 모듈을 연결하는 별칭 정보 |
| `modules.symbols` | 모듈의 심볼 관련 정보 |
| `modules.builtin` | 커널에 내장된 모듈에 관한 정보 |

자료의 자동 적재 그림은 **장치 식별 정보 → 모듈 별칭과 매칭 → 필요한 모듈 적재**라는 흐름으로 이해한다. 의존 모듈 처리에는 `modules.dep`가 사용된다.

### 3.2. 모듈 관리 명령 비교
| 명령                           | 용도           | 인자 / 특징                |
| ---------------------------- | ------------ | ---------------------- |
| `modinfo /path/to/module.ko` | 모듈 정보 확인     | 모듈 파일 지정               |
| `lsmod`                      | 현재 적재된 모듈 목록 | 실행 중 상태 확인             |
| `insmod /path/to/module.ko`  | 모듈 적재        | 파일 경로 지정, 의존성 자동 처리 없음 |
| `rmmod <module-name>`        | 모듈 제거        | 모듈 이름 지정               |
| `modprobe <module-name>`     | 모듈 적재        | 이름 지정, 의존성 자동 처리       |
| `modprobe -r <module-name>`  | 모듈 제거        | 의존 관계를 고려하는 제거 도구      |

**가장 중요한 비교**
- `insmod`는 지정한 파일을 적재하고,
- `modprobe`는 모듈 이름으로 찾아 의존성까지 처리한다.

> **표현 보충**
> ‘완전 경로 필요’는 `insmod`에서 모듈 파일을 지정한다는 뜻으로 이해한다.
> `./usb-storage.ko`처럼 상대 경로도 사용된다.
> `rmmod`에는 파일 경로가 아닌 모듈 이름을 전달한다.

### 3.3. 모듈 파라미터 전달
예제 파라미터는 `usb-storage`의 `delay_use`다.

**적재 시 지정**:
```sh
insmod ./usb-storage.ko delay_use=0
modprobe usb-storage delay_use=0
```

**설정 파일에 지정**
- `/etc/modprobe.d/` 아래 설정 파일 등에 다음 내용을 둔다.
- 자료는 `/etc/modprobe.conf`도 함께 제시한다.
```text
options usb-storage delay_use=0
```

**커널에 내장한 경우**: 커널 명령행으로 전달한다.
```text
usb-storage.delay_use=0
```

**실행 중 확인·변경**:
```text
/sys/module/<name>/parameters/<parameter>
```

자료의 변경 예:
```sh
echo 0 > /sys/module/usb_storage/parameters/delay_use
```

> **이해 보충**
> 실행 중 변경 가능 여부는 각 파라미터의 지원 여부와 쓰기 권한에 달려 있다.
> 모든 모듈 파라미터를 항상 변경할 수 있다는 뜻은 아니다.

## 4. 디바이스 트리
### 4.1. 왜 필요한가?
커널이 장치를 구동하려면 ‘어떤 장치가 어디에 있고, 무엇과 연결되어 있는가’를 알아야 한다.
하지만 모든 하드웨어가 자신의 정보를 자동으로 알려 주지는 않는다.

| 하드웨어 정보 전달 방식     | 설명                         |
| ----------------- | -------------------------- |
| OS / 부트로더의 C 자료구조 | 과거 임베디드 Linux, U-Boot에서 사용 |
| ACPI 테이블          | x86 시스템 등에서 펌웨어 테이블로 제공    |
| Device Tree       | 여러 임베디드 CPU 아키텍처에서 사용      |

**디바이스 트리**
- 하드웨어 구성과 연결 관계를 표현하는 트리 자료구조

### 4.2. `.dts`, `.dtsi`, `.dtb` 구별
```text
SoC / 공통 하드웨어 정의(.dtsi)
        +
보드별 정의 및 속성 덮어쓰기(.dts)
        ↓ 빌드 과정에서 dtc로 컴파일
Device Tree Blob(.dtb)
```

| 이름 | 의미 | 역할 |
|---|---|---|
| `.dts` | Device Tree Source | 최종 보드 구성을 기술하는 소스 |
| `.dtsi` | 포함되는 소스 파일 | SoC 수준 또는 여러 보드의 공통 정의 |
| `dtc` | Device Tree Compiler | 소스를 컴파일 |
| `.dtb` | Device Tree Blob | 컴파일된 바이너리 표현 |

소스 위치의 일반적인 형태:
```text
arch/<ARCH>/boot/dts/<vendor>/
```

Linux 6.5 이전 ARM 32비트의 경로로 `arch/arm/boot/dts`도 제시한다.
Device Tree는 Linux 외에 U-Boot, Barebox, TF-A 등에서도 사용된다.

### 4.3. 기본 문법 읽기
| 요소           | 의미                               |
| ------------ | -------------------------------- |
| 노드           | 보통 하나의 장치 또는 IP 블록               |
| 자식 노드        | 하위 장치나 하위 구성 요소                  |
| 속성, property | 장치의 특성 및 연결 정보                   |
| 문자열 값        | `compatible = "vendor,model";` 등 |
| `<...>`      | 셀 값 표현, 자료 예에서는 32비트 값           |
| `[...]`      | 바이트 배열 표현                        |
| 값 없는 속성      | 존재 여부로 의미를 나타내는 속성               |
| 라벨 및 `&라벨`   | 다른 노드를 참조하거나 기존 노드를 지정           |
| phandle      | 다른 노드를 가리키는 참조에 사용되는 식별자         |

노드 선언은 다음처럼 읽는다.
```dts
label: node-name@unit-address {
    property-name = <value>;
};
```

**학습용 예제**
- 아래는 노드와 참조 문법을 설명하는 예이며, 특정 보드용 완성 파일은 아니다.
```dts
/* SoC 공통 정의의 일부 */
serial0: serial@5c000000 {
    compatible = "st,stm32h7-uart";
    reg = <0x5c000000 0x400>;
    status = "disabled";
};

/* 보드별 정의에서 같은 노드를 참조 */
&serial0 {
    status = "okay";
};
```
- `serial0:`는 다른 곳에서 참조할 수 있는 라벨이다.
- `serial@5c000000`은 노드 이름과 unit address다.
- `&serial0`로 기존 노드를 지정해 속성을 덮어쓴다.
- 이 예의 `reg`는 부모가 주소·크기 각각 한 셀을 사용하는 상황을 가정한다.

### 4.4. Device Tree가 기술하는 범위
**하드웨어의 구성과 통합 관계는 Device Tree에, 구체적인 동작 제어는 드라이버 코드에 둔다.**

| Device Tree에 기술 | 드라이버 코드에서 처리 |
|---|---|
| 장치 종류와 식별 정보 | 장치를 동작시키는 절차 |
| 레지스터 주소와 범위 | 레지스터를 읽고 쓰는 로직 |
| IRQ, DMA, 클록, 리셋 연결 | 해당 자원을 사용한 실제 동작 |
| 보드에서 사용하는 장치와 핀 연결 | 장치 기능의 구체적인 구현 |

자료는 Device Tree가 OS와 무관하게 하드웨어를 기술한다는 점을 강조한다. 또한 원하는 하드웨어를 임의로 만들어 내는 설정이 아니라, 실제 보드의 구성을 설명하는 자료다.

### 4.5. `compatible`: 어떤 드라이버와 연결할까?
`compatible`은 드라이버 매칭에 사용하는 문자열 목록이다.

```dts
compatible = "st,stm32mp1-dwmac", "snps,dwmac-4.20a";
```

**구체적인 장치 → 더 일반적인 호환 장치** 순서로 적는다.

일반적인 형태는 `"vendor,model"`이다. 자료에는 `"gpio-keys"`, `"regulator-fixed"`처럼 공급업체 접두사가 없는 예도 있다.

```text
Device Tree의 compatible 문자열
        ↕ 매칭
드라이버의 struct of_device_id[] 테이블
        ↓
해당 장치와 드라이버의 연결
```

> **이해 보충**
> `compatible`은 ‘어느 드라이버를 사용할지 찾는 단서’다.
> 문자열이 존재한다고 드라이버 코드 자체가 생기거나 장치 초기화 성공이 보장되는 것은 아니다.

### 4.6. `reg`: 주소의 의미는 부모 버스에 달려 있다
| 장치의 맥락    | `reg`의 의미          | 자료 기반 예                   |
| --------- | ------------------ | ------------------------- |
| 메모리 매핑 장치 | 레지스터 영역의 시작 주소와 크기 | `reg = <0x50027000 0x4>;` |
| I2C 장치    | I2C 버스상의 장치 주소     | `reg = <0x39>;`           |
| SPI 장치    | 칩 선택 번호            | `reg = <0>;`              |

여러 레지스터 영역이 있으면 여러 항목을 기술한다.

```dts
reg = <0x50027000 0x4>, <0x500273f0 0x10>;
```

**시험에서 구별할 점**: `reg`를 항상 ‘메모리 주소 + 크기’로 읽으면 안 된다.

> **이해 보충**
> 셀의 개수와 주소 해석은 부모 노드의 `#address-cells`, `#size-cells` 및 버스 규칙에 따른다.
> 버스 주소와 CPU 물리 주소 사이에 변환이 있을 수도 있다.
> 위의 메모리 예는 자료의 단순한 주소·크기 쌍을 설명한다.

### 4.7. `status`: 이 보드에서 사용하는 장치인가?
| 값                | 자료에서의 의미      |
| ---------------- | ------------- |
| `"okay"`, `"ok"` | 사용 가능한 장치로 표시 |
| `"disabled"`     | 비활성화된 장치로 표시  |

자주 나오는 구성 방식:
1. SoC의 `.dtsi`에서 외부 연결 장치를 `"disabled"`로 정의한다.
2. 보드의 `.dts`에서 실제 사용하는 장치를 `"okay"`로 덮어쓴다.

> **구별하기**
> `status = "okay"`는 현재 데이터 전송 중이라는 뜻이 아니다.
> 해당 장치를 사용할 수 있도록 기술했다는 뜻이다.
> 실제 동작에는 드라이버와 다른 자원 설정도 필요하다.

### 4.8. 공유 자원과 Pin-muxing
여러 장치는 다음 자원을 다른 하드웨어 블록에서 제공받거나 공유한다.
- 인터럽트 선
- 클록 컨트롤러
- DMA 컨트롤러
- 리셋 컨트롤러

Device Tree는 이 연결 관계를 기술한다.

**Pin-muxing**은 하나의 물리 핀을 GPIO, UART, SPI, I2C 등 여러 기능 중 하나로 연결하는 것이다.
SoC의 pinmux controller가 이를 제어한다.

```text
물리 핀
  └─ 선택된 설정에 따라 GPIO / UART / SPI / I2C 등의 기능에 연결
```

Device Tree에는 가능한 핀 구성과 각 장치가 사용하는 핀 구성을 기술한다.

> **이해 보충**
> 컨트롤러를 활성화하는 것과 그 신호가 보드의 올바른 핀으로 나오게 하는 것은 별개의 설정이다.
> 장치를 사용할 때 두 부분을 함께 이해해야 한다.

### 4.9. 문법 검사와 의미 검사
| 구분                | 확인하는 것                     |
| ----------------- | -------------------------- |
| `dtc`             | 자료에서 강조하는 소스 문법 검사와 컴파일    |
| YAML 바인딩 / 스키마 검사 | 장치에 필요한 속성, 값의 형식 등 의미적 제약 |

자료의 검증 명령:
```sh
make dt_binding_check
make dtbs_check
make DT_SCHEMA_FILES=path/to/specific/yaml dtbs_check
```

- `dt_binding_check`: 바인딩 스키마 검사
- `dtbs_check`: Device Tree를 바인딩 스키마에 대조해 검사
- `DT_SCHEMA_FILES=...`: 특정 스키마로 검사 범위 지정

**기억할 문장**
- ‘컴파일된다’와 ‘장치 설명이 올바르다’는 서로 다른 확인이다.
- 자료의 핵심은 `dtc`만으로 YAML 바인딩 수준의 유효성 검증을 대신할 수 없다는 것이다.

## 5. 장치 발견
USB와 PCI에는 장치 발견 메커니즘이 있다.
버스에서 장치를 열거하고 식별 정보를 읽어 드라이버와 연결한다.

| 항목 | Device Tree를 이용한 설명 | USB / PCI의 자동 발견 |
|---|---|---|
| 정보의 주요 출처 | 외부에서 제공하는 하드웨어 기술 | 버스의 발견·열거 메커니즘 |
| 드라이버 매칭 단서 | `compatible` 등 | Vendor ID, Product ID, 장치 클래스·서브클래스 등 |
| 자료의 확인 방법 | sysfs의 Device Tree 및 장치 연결 정보 | `lsusb`, `lspci` |

```sh
lsusb
lspci
```

**장치 발견 ≠ 드라이버 지원 ≠ 정상 동작**
장치 목록에 나타나더라도 적합한 드라이버가 없으면 해당 기능을 사용할 수 없다.

## 6. 개념을 하나로 연결해 보기
### I2C 장치가 응용 프로그램에 기능을 제공하기까지
아래는 강의의 여러 부분을 연결한 **학습용 흐름**이다.
실제 사용자 인터페이스는 장치 종류에 따라 달라진다.

1. **하드웨어 기술**: Device Tree에 부모 I2C 버스, 장치 주소 `reg`, 종류 `compatible` 등을 적는다.
2. **드라이버 연결**: 커널이 장치 정보와 드라이버의 지원 목록을 매칭한다.
3. **드라이버 코드 준비**: 드라이버가 모듈이면 필요한 모듈과 의존 모듈을 적재한다. 내장 드라이버라면 별도 모듈 적재가 필요 없다.
4. **장치 구동**: 디바이스 드라이버가 I2C 서브시스템과 컨트롤러 드라이버를 통해 통신한다.
5. **기능 노출**: 장치 클래스에 맞는 `/dev`, sysfs 등의 인터페이스를 제공한다.
6. **사용자 공간 접근**: 응용이 라이브러리 또는 표준 인터페이스로 기능을 사용한다.

이때 sysfs의 `driver` 링크로 연결된 드라이버를, `of_node` 링크로 해당 Device Tree 노드를 추적할 수 있다.

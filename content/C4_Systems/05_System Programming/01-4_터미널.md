## 1. 먼저 전체 구조 잡기
핵심은 **프로세스를 어떻게 묶고, 터미널과 연결하며, 생성과 종료를 관리하는가**이다.

```text
세션(Session, SID)
├─ 프로세스 그룹 A(PGID) ← 터미널의 현재 전위 그룹
│  ├─ 프로세스(PID)
│  └─ 프로세스(PID)
├─ 프로세스 그룹 B(PGID) ← 후위 그룹
│  └─ 프로세스(PID)
└─ 프로세스 그룹 C(PGID) ← 후위 그룹
   └─ 프로세스(PID)
```

- **프로세스**: 실행 중인 프로그램의 단위
- **프로세스 그룹**: 신호 전달과 셸의 작업 제어를 위해 프로세스를 묶는 단위
- **세션**: 하나 이상의 프로세스 그룹을 묶는 단위
- **제어 터미널**: 세션의 작업과 사용자 입력을 연결하는 터미널

**부모·자식 관계와 그룹 소속은 서로 다른 관계다.**
부모·자식 관계는 누가 생성했는지를 나타내고, PGID와 SID는 어떤 그룹과 세션에 속하는지를 나타낸다.

### 1.1. 식별자 비교
| 식별자      | 의미                    | 읽는 방법                   |
| -------- | --------------------- | ----------------------- |
| **PID**  | 프로세스 ID               | 이 프로세스는 누구인가?           |
| PPID     | 부모 프로세스 ID            | 누가 이 프로세스를 생성했는가?       |
| **PGID** | 프로세스 그룹 ID            | 어떤 작업 그룹에 속하는가?         |
| **SID**  | 세션 ID                 | 어떤 세션에 속하는가?            |
| TPGID    | 터미널의 현재 전위 프로세스 그룹 ID | 지금 터미널 입력을 받을 그룹은 무엇인가? |

## 2. 프로세스 그룹
> 여러 프로세스를 하나의 작업으로 다루기

### 2.1. 정의와 리더
**프로세스 그룹** (Process Group)
- 하나 이상의 프로세스로 이루어지며, 고유한 PGID를 갖는다.

**프로세스 그룹 리더**
- 조건: `PID == PGID`
	- 예를 들어 PID가 200인 프로세스가 PGID 200인 그룹의 리더가 될 수 있다.
- 그룹 리더가 종료되어도 그룹에 다른 프로세스가 남아 있으면 그룹은 유지된다. 즉, **리더의 수명과 그룹의 수명은 같지 않다.**

### 2.2. 왜 필요한가?
셸에서 파이프라인으로 연결한 명령은 보통 하나의 프로세스 그룹으로 관리한다.
```sh
proc1 | proc2 &
proc3 | proc4 | proc5
```

작업 제어를 사용하는 셸에서 위 예제의 관계는 다음과 같다.

| 명령 | 그룹 구성 | 실행 위치 |
|---|---|---|
| `proc1 \| proc2 &` | `proc1`, `proc2`가 같은 그룹 | 후위(background) |
| `proc3 \| proc4 \| proc5` | 세 프로세스가 같은 그룹 | 전위(foreground) |

이렇게 묶으면 터미널에서 발생한 신호를 전위 작업 전체에 전달할 수 있다.

### 2.3. 관련 함수
```c
#include <unistd.h>

int   setpgid(pid_t pid, pid_t pgid);
pid_t getpgid(pid_t pid);
int   setpgrp(void);
pid_t getpgrp(void);
```

| 호출 | 의미 |
|---|---|
| `setpgid(pid, pgid)` | 지정한 프로세스의 PGID를 설정 |
| `setpgid(0, pgid)` | 호출한 프로세스 자신의 PGID를 설정 |
| `setpgid(pid, 0)` | 지정한 프로세스의 PID를 PGID로 사용 |
| `setpgid(0, 0)` | 자신의 PID를 PGID로 사용하여 자신이 그룹 리더가 됨 |
| `getpgid(pid)` | 지정한 프로세스의 PGID 조회 |
| `getpgid(0)` | 자신의 PGID 조회 |
| `setpgrp()` | 자료의 인자 없는 형태에서는 `setpgid(0, 0)`과 같은 역할 |
| `getpgrp()` | `getpgid(0)`과 같은 역할 |

**설정 제약**
- 프로세스는 자신 또는 자신의 자식에 대해서만 PGID를 설정할 수 있다.
- 자식이 이미 `exec()`를 수행한 뒤에는 부모가 그 자식의 PGID를 바꿀 수 없다.
- **보충**: 이것만이 모든 제약은 아니다. 세션 경계를 넘어 그룹을 옮길 수 없고 세션 리더의 PGID도 바꿀 수 없다.

> `pid = 0`은 **대상으로 자신을 선택**, `pgid = 0`은 **대상 프로세스의 PID를 그룹 ID로 선택**한다.

## 3. 세션
> 프로세스 그룹들을 묶기

### 3.1. 세션과 제어 터미널
**세션** (Session)
- 하나 이상의 프로세스 그룹으로 이루어진다.
- 각 프로세스 그룹은 하나의 세션에 속한다.

**터미널과 연결된 세션**
- 전위 그룹 하나와 여러 후위 그룹을 구분하여 작업을 관리한다.

> **보충**
> 자료의 “각 세션은 하나의 제어 단말기를 가진다”는 표현은 **세션은 최대 하나의 제어 터미널을 가질 수 있다**로 이해해야 한다.
> 제어 터미널이 없는 세션도 있으며, `setsid()` 직후가 그 예다.
> 후위 그룹도 반드시 존재해야 하는 것은 아니다.

### 3.2. `setsid()`의 효과
```c
#include <unistd.h>

pid_t setsid(void);
```

호출에 성공하면 다음 변화가 함께 일어난다.
1. 새로운 세션을 만든다.
2. 호출한 프로세스가 새 세션의 리더가 된다.
3. 새로운 프로세스 그룹을 만들고 그 리더가 된다.
4. 제어 터미널이 없는 상태가 된다.

```text
setsid() 성공 직후
PID == PGID == SID

새 세션의 구성원: 호출한 프로세스 하나
새 그룹의 구성원: 호출한 프로세스 하나
제어 터미널: 없음
```

반환값은 성공 시 새 SID, 실패 시 `-1`이다.

### 3.3. 왜 `fork()` 후 자식이 호출하는가?
**프로세스 그룹 리더는 `setsid()`를 호출하여 새 세션을 만들 수 없다.**

```text
기존 프로세스
  │ fork()
  ├─ 부모: 종료
  └─ 자식: setsid() 호출
```

새 자식은 부모의 PGID를 상속하지만 자신의 PID는 새로 받으므로 그룹 리더가 아니다.
따라서 이 자식이 `setsid()`를 호출하도록 구성한다.

> 핵심 원인은 **자식이 그룹 리더가 아니라는 점**이다.
> 부모의 종료 자체가 `setsid()` 성공 조건인 것은 아니다.

### 3.4. 세션 ID 조회
```c
#include <unistd.h>

pid_t getsid(pid_t pid);
```

| 호출 | 의미 |
|---|---|
| `getsid(pid)` | 지정한 프로세스의 SID 조회 |
| `getsid(0)` | 자신의 SID 조회 |

오류가 발생하면 `-1`을 반환한다.

## 4. 제어 터미널과 전위·후위 작업
**제어 터미널** (controlling terminal)
- 세션과 연결된 터미널 또는 의사 터미널

### 4.1. 주요 용어
| 용어                           | 의미                           |
| ---------------------------- | ---------------------------- |
| 제어 프로세스(controlling process) | 제어 터미널과의 연결을 설정한 세션 리더       |
| `/dev/tty`                   | 호출한 프로세스의 제어 터미널을 가리키는 특수 파일 |
| 전위 프로세스 그룹                   | 터미널의 현재 전위 PGID와 일치하는 그룹     |
| 후위 프로세스 그룹                   | 해당 터미널에서 현재 전위 그룹이 아닌 그룹     |

**보충**: 제어 터미널이 없는 프로세스에서는 `/dev/tty`를 통한 접근이 실패할 수 있다.

### 4.2. 터미널 입력과 신호
| 상황                         | 결과                               |
| -------------------------- | -------------------------------- |
| 전위 그룹이 터미널 입력을 읽음          | 정상적으로 입력 가능                      |
| 후위 그룹이 터미널 입력을 읽으려 함       | 일반적인 작업 제어 환경에서 `SIGTTIN`에 의해 정지 |
| 터미널에서 인터럽트 발생, 보통 `Ctrl+C` | 전위 그룹 전체에 `SIGINT` 전달            |
| 터미널에서 quit 발생, 보통 `Ctrl+\` | 전위 그룹 전체에 `SIGQUIT` 전달           |
| 터미널 연결 끊김(hang-up)         | 자료에서는 제어 프로세스로의 `SIGHUP` 전달로 설명  |

> **보충**
> 후위 입력에서의 `SIGTTIN` 정지는 기본 동작 기준이다.
> 신호 처리 설정이나 고아 프로세스 그룹 여부에 따라 읽기 오류로 처리되는 예외도 있다.

### 4.3. 강의 예제: `cat > temp &`가 멈추는 이유
```sh
cat > temp &
```

1. `&` 때문에 `cat`이 후위 작업으로 실행된다.
2. `> temp`는 **표준 출력**을 파일로 바꾼다.
3. **표준 입력은 여전히 터미널**에 연결되어 있다.
4. `cat`이 터미널 입력을 읽으려 하므로 정지한다.

```text
후위 cat
  ├─ 표준 입력: 터미널 ← 읽으려 하면 정지
  └─ 표준 출력: temp 파일
```

```sh
fg
```

`fg`로 해당 작업을 전위로 가져오면 실행을 재개하고 터미널 입력을 받을 수 있다.

> 자주 하는 실수: **출력 리다이렉션을 했다고 입력까지 바뀌는 것은 아니다.**

### 4.4 `ps -xj` 출력 읽기
강의 예제에서 중요한 값만 추리면 다음과 같다.

| 프로세스 | PID | PGID | SID | TPGID | 상태 |
|---|---:|---:|---:|---:|---|
| `bash` | 13336 | 13336 | 13335 | 16870 | S |
| `cat` | 16869 | 16869 | 13335 | 16870 | T |
| `ps -xj` | 16870 | 16870 | 13335 | 16870 | R |
| 첫 번째 `more` | 16871 | 16870 | 13335 | 16870 | S |
| 두 번째 `more` | 16872 | 16870 | 13335 | 16870 | S |

읽는 순서는 **SID → PGID → TPGID → 상태**다.

- 모두 SID가 `13335`이므로 같은 세션이다.
- `ps`와 두 `more`는 PGID가 `16870`이므로 같은 그룹이다.
- 터미널의 TPGID가 `16870`이므로 이 파이프라인이 현재 전위 작업이다.
- `cat`의 PGID는 TPGID와 다르므로 후위 작업이고, `T`는 정지 상태다.
- 셸도 명령 실행을 기다리는 이 순간에는 전위 그룹이 아니다. 전위 그룹은 작업 전환에 따라 바뀐다.

## 5. 터미널 로그인과 프로세스 계층
### 5.1. 전통적인 터미널 로그인 흐름
```text
init(PID 1)
  │ fork(): 터미널별 자식 생성
  ▼
자식 프로세스
  │ exec()
  ▼
getty
  │ setsid(), 터미널 열기, 사용자 이름 입력 대기
  │ exec()
  ▼
login
  │ 비밀번호 확인, 홈 디렉터리 이동, 터미널 소유권·환경 설정
  │ exec()
  ▼
로그인 셸
  │ fork() + exec()
  ▼
사용자 명령들
```

로그아웃하여 해당 자식이 종료되면 `init`은 `SIGCHLD`를 받고 종료를 처리한 뒤, 다시 로그인을 받을 수 있도록 과정을 반복한다.

### 5.2. `fork()`와 `exec()`를 구별하기
| 동작       | 역할                  | PID 관점          |
| -------- | ------------------- | --------------- |
| `fork()` | 자식 프로세스 생성          | 자식은 새로운 PID를 받음 |
| `exec()` | 현재 프로세스의 실행 프로그램 교체 | 기존 PID를 유지      |

따라서 `getty → login → shell`이 `exec()`로 이어진다면, 프로그램 이름이 바뀌어도 같은 프로세스의 PID가 유지된다.

### 5.3. `init`의 역할
`init`은 다음과 같이 설명된다.
- PID가 `1`인 프로세스.
- 커널의 부트스트랩 이후 실행된다.
- 시스템 초기화를 수행하며 슈퍼유저 권한을 가진 사용자 프로세스다.
- 부모를 잃은 자식을 인계받고 종료 정보를 회수한다.

`pstree -p`를 이용하면 PID와 함께 부모·자식 계층을 볼 수 있다.

> **보충**
> 위 로그인 절차와 `/etc/rc*`, `/etc/ttys`는 자료의 전통적인 시스템 모델이다.
> 초기화 프로그램과 로그인 구성은 시스템마다 다를 수 있다.

## 6. 환경변수: 프로세스에 실행 환경 전달하기
### 6.1. 환경의 구조
**환경 (environment)**
- `이름=값` 형태의 문자열 모음이다.
```text
"USER=sjcho\0"
"SHELL=/bin/bash\0"
"TERM=vt100\0"
```

구조적으로는 **문자열 포인터 배열**이며 다음 두 종료 표시를 구별해야 한다.
- 각 문자열 끝: 널 문자 `\0`
- 포인터 배열 끝: 널 포인터 `NULL`
```text
envp[0] ──> "USER=sjcho\0"
envp[1] ──> "SHELL=/bin/bash\0"
envp[2] ──> "TERM=vt100\0"
envp[3] = NULL
```

### 6.2. 인자와 환경변수의 차이
강의 예제 실행:
```sh
./execl_test2 123 456
```

```text
argc = 3
argv[0] = "./execl_test2"
argv[1] = "123"
argv[2] = "456"
argv[3] = NULL

envp에는 "USER=...", "PATH=..." 등의 환경 문자열이 들어간다.
```

| 구분 | 명령행 인자 `argv` | 환경 `envp` |
|---|---|---|
| 전달 내용 | 프로그램에 직접 지정한 인자 | 실행 환경 설정 |
| 문자열 예 | `"123"` | `"USER=sjcho"` |
| 첫 항목 | 관례적으로 프로그램 이름 | 환경변수 문자열 |
| 배열 끝 | `NULL` | `NULL` |

자료에서는 다음 형태로 환경을 받는다.
```c
int main(int argc, char *argv[], char *envp[])
```

**보충**
- 세 번째 인자인 `envp`는 여러 Unix 환경에서 지원하는 형태이며, 이식성이 필요한 C 코드에서는 `getenv()` 등으로 접근하는 편이 적절하다.

### 6.3. 환경변수 조회
```c
#include <stdlib.h>

char *getenv(const char *name);
```

```c
const char *user = getenv("USER");
```

- 조회할 때는 `"USER"`처럼 이름만 전달한다.
- 반환값은 `"sjcho"`처럼 값 부분이다.
- **보충**: 해당 변수가 없으면 `NULL`을 반환하므로 사용 전에 확인한다.

### 6.4. 환경의 전달
로그인 셸의 설정 파일에서 정한 환경을 이후 실행되는 프로세스가 이용한다.

**보충**
- 셸 변수와 환경변수는 구별해야 한다.
- Bash에서는 `export`된 변수가 자식 프로그램의 환경으로 전달된다.

```sh
export STUDY_MODE=process
```

- `fork()`로 만든 자식은 부모의 환경을 상속한다.
- `exec()` 계열 함수 중 `execle()`와 `execve()`는 전달할 환경 배열을 명시할 수 있다.
- **보충**: 자식이 자신의 환경을 바꿔도 부모의 환경이 함께 바뀌지는 않는다.

```c
execle(path, arg0, /* ... */, (char *)0, envp);
execve(path, argv, envp);
```

| 함수 | 인자 전달 | 환경 전달 |
|---|---|---|
| `execle()` | 인자를 목록으로 나열 | 마지막에 `envp` 지정 |
| `execve()` | `argv` 배열 | `envp` 배열 |

자료의 `.login`, `.bash_profile`, `.bashrc`는 셸 설정 파일의 예다.
**보충**: 파일을 읽는 조건은 셸과 로그인·대화형 실행 여부에 따라 다르다.

## 7. 좀비와 부모의 조기 종료
| 구분        | 좀비 프로세스                | 고아 프로세스       |
| --------- | ---------------------- | ------------- |
| 핵심 조건     | 자식이 종료했지만 회수되지 않음      | 부모가 먼저 종료함    |
| 자식의 실행 상태 | 이미 종료                  | 계속 실행 중일 수 있음 |
| 핵심 문제     | 종료 정보가 남아 있음           | 부모 관계가 바뀜     |
| 처리        | 부모가 `wait()` 계열 함수로 회수 | 다른 프로세스가 인계받음 |
> **좀비는 종료 정보 회수 문제, 고아는 부모 상실 문제**

### 7.1. 좀비 프로세스
```text
자식 종료
  ↓
부모가 아직 wait 계열 함수를 호출하여 종료 정보를 회수하지 않음
  ↓
좀비 상태
  ↓
부모가 wait / waitpid로 회수
  ↓
남아 있던 종료 정보 제거
```

좀비는 **이미 종료했지만 부모가 종료 정보를 회수하지 않은 프로세스**다.

커널은 부모가 확인할 수 있도록 다음 정보를 보관한다.
- PID
- 종료 상태
- CPU 사용 시간 등의 자원 사용 정보

> **보충**
> 슬라이드 96의 “커널 자원이 없는 프로세스”는 실행에 쓰던 대부분의 자원이 해제되었다는 뜻으로 이해해야 한다.
> 종료 정보와 프로세스 관리 정보 일부는 남는다.

### 7.2. 고아 프로세스
부모는 실행 중인 자식이 있어도 종료할 수 있다.
자료에서는 남은 자식을 `init(PID 1)`이 인계받는다고 설명한다.

이후 자식이 종료하면 `init`이 `wait()` 계열 함수를 호출해 종료 정보를 회수하므로 좀비가 계속 쌓이는 것을 막는다.

**보충**
- Linux에서는 설정된 서브리퍼(subreaper)가 인계받는 경우도 있다.
- 자료를 학습할 때는 먼저 “부모가 종료하면 다른 프로세스가 자식을 인계받아 회수한다”는 원리를 이해하면 된다.

## 8. 데몬 생성 코드 이해하기
데몬은 사용자 터미널과 분리되어 지속적으로 작업하는 프로세스다.
강의는 `fork()`와 `setsid()`를 이용한 전통적인 분리 과정을 보여준다.

### 예제
```c
int main(int argc, char *argv[]) {
    int pid;

    pid = fork();
    if (pid < 0) {         // fork 에러: 로그 남기고 종료
        perror("fork error : ");
        exit(0);
    } else if (pid > 0) {  // 부모 프로세스: 로그 남기고 종료
        printf("child process : [%d] - parent process : [%d] \n", pid, getpid());
        exit(0);
    } else if (pid == 0) {
        printf("process : [%d]\n", getpid());
    }

    signal(SIGHUP, SIG_IGN);  // 터미널 종료 시 signal의 영향을 받지 않도록
    close(0); close(1); close(2);
    chdir("/");               // 실행 위치를 root로 변경
    setsid();                 // 새로운 세션 부여

    while (1) {
        if ((pid = fork()) < 0) {  // daemon이 죽었을 경우 다시 실행
            printf("fork error : restart daemon");
        } else if (pid == 0) {
            break;
        } else if (pid > 0) {
            wait(&ret);
        }
        sleep(10);  // 10초마다 체크
    }
}
```

### 8.1. 앞부분: 부모와 분리
```text
fork()
├─ 실패: 오류 처리 후 종료
├─ 부모: 자식 PID를 출력하고 종료
└─ 자식: 이후 초기화 계속
```

`fork()` 반환값을 기준으로 분기한다.

| 반환값 | 실행 주체·결과 |
|---|---|
| `< 0` | 생성 실패 |
| `> 0` | 부모에서 실행, 반환값은 자식 PID |
| `== 0` | 자식에서 실행 |

### 8.2. 뒷부분: 강의 코드의 각 동작
| 코드                        | 목적                  |
| ------------------------- | ------------------- |
| `signal(SIGHUP, SIG_IGN)` | `SIGHUP`을 무시하도록 설정  |
| `close(0)`                | 표준 입력 닫기            |
| `close(1)`                | 표준 출력 닫기            |
| `close(2)`                | 표준 오류 닫기            |
| `chdir("/")`              | 작업 디렉터리를 루트로 변경     |
| `setsid()`                | 새 세션 생성, 제어 터미널과 분리 |

### 8.3. 마지막 반복문: 작업 자식의 재실행
자료의 마지막 루프는 감독 역할을 하는 프로세스와 실제 작업을 하는 자식을 나누는 구조다.

```text
감독 프로세스
  │ fork()
  ├─ 자식: break로 루프를 빠져나가 실제 작업 부분으로 진행
  └─ 감독: wait()로 자식 종료 대기
           ↓
         10초 대기
           ↓
         다시 fork()
```

**읽을 때 주의할 점**
- `wait()`가 자식 종료까지 기다리므로, 자식이 살아 있는 동안 10초마다 상태를 검사하는 구조가 아니다.
- 자식이 종료하면 10초 대기 후 다시 자식을 생성한다.
- 이 루프가 재생성하는 대상은 **작업 자식**이다. 감독 프로세스 자체가 종료되면 이 코드만으로 복구되지 않는다.
- 자식은 `break` 이후 실제 작업을 실행해야 한다. 자료에는 그 작업 부분이 제시되어 있지 않다.

### 8.4. 예제 코드의 보완점
다음은 강의 코드 이해를 위한 **보충**이며 완성된 데몬 구현은 아니다.

- `fork()`, `close()`, `chdir()`, `setsid()` 등의 선언을 위해 `<unistd.h>`가 필요하다.
- `wait()`에는 `<sys/wait.h>`가 필요하며, 자료에 나온 `ret`도 선언해야 한다.
- 표준 출력과 표준 오류를 닫은 뒤에는 `printf()`로 로그를 정상 출력할 수 없다. 로그 파일이나 별도 로깅 수단이 필요하다.
- 파일 디스크립터 `0`, `1`, `2`는 단순히 닫는 대신 `/dev/null` 등에 연결하는 방법도 사용한다.
- `setsid()`, `chdir()`, `fork()`, `wait()` 등의 실패와 반환값을 처리해야 한다.
- `SIGHUP`을 무시하는 것과 새 세션을 만드는 것은 별개 동작이다. 터미널과의 분리는 `setsid()`의 효과로 이해한다.

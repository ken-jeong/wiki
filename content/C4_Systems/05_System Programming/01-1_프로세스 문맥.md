> **핵심 질문**: 운영체제는 실행 중인 프로그램을 어떻게 관리하고, 잠시 멈췄다가 다시 실행할까?
>
> **한 문장 답**: 프로세스마다 자원과 실행 상태인 **문맥(context)** 을 관리하고, CPU를 넘길 때 문맥을 저장·복원한다.

## 학습 순서
1. **정체**: 프로그램과 프로세스는 무엇이 다른가?
2. **공간**: 코드와 변수는 어디에 저장되는가?
3. **관리**: 운영체제는 프로세스의 어떤 정보를 기억하는가?
4. **전환**: 실행을 중단했다가 어떻게 이어 가는가?
5. **상태**: CPU나 입출력을 기다리는 동안 어떤 상태가 되는가?

## 1. 프로그램과 프로세스
### 1.1. 프로세스의 정의
**프로세스는 실행 중인 프로그램의 한 인스턴스다.**

| 관점 | 프로세스의 의미 |
|---|---|
| 실행 | 수행 중인 프로그램 |
| 환경 | 프로그램을 실행하는 데 필요한 실행 환경 |
| 스케줄링 | CPU를 배정받는 실행 단위 |
| 구성 | 제어 흐름과 주소 공간의 집합 |
| 자원 | CPU 시간, 메모리, 파일, 입출력 장치 등을 사용하는 객체 |

**제어 흐름**
- “어떤 명령을 실행하고 있고, 다음에 어디로 갈 것인가”를 뜻한다.

**주소 공간**
- “프로그램이 사용하는 코드와 데이터가 어떤 주소에 놓이는가”와 관련된다.

### 1.2. 프로그램과 프로세스의 차이
| 구분       | 프로그램                    | 프로세스                     |
| -------- | ----------------------- | ------------------------ |
| 의미       | 실행할 명령과 데이터가 담긴 파일      | 그 프로그램이 실행 중인 인스턴스       |
| 예        | 컴파일된 실행 파일 `a.out`      | `a.out`을 실행해서 생긴 실행 주체   |
| 실행 위치·상태 | 그 자체로는 실행 위치나 대기 상태가 없음 | 현재 명령 위치, 레지스터, 상태 등이 있음 |
| 운영체제 관리  | 파일로 관리                  | PID와 태스크 관리 정보로 관리       |

```text
소스 코드 test.c
      |
      | gcc: 컴파일·링크
      v
실행 파일 a.out (강의 예: ELF 형식)
      |
      | 프로그램 실행 및 실행 환경 구성
      v
프로세스: 코드 + 데이터 + 스택 + 힙 + 실행·관리 정보
```

같은 실행 파일을 여러 번 실행하면 여러 프로세스가 생길 수 있다.
같은 코드를 사용하더라도 각 프로세스의 실행 위치와 데이터 상태는 다를 수 있다.

## 2. 프로세스 식별자
### 2.1. PID와 부모 프로세스
- **PID(Process ID)**: 프로세스를 식별하는 번호
- **PPID(Parent Process ID)**: 부모 프로세스의 PID
- 부모·자식 관계는 프로세스 생성 관계를 나타낸다

### 2.2. 식별자 조회 함수
관련 헤더는 `<unistd.h>`이며, 강의 예제에서는 `<sys/types.h>`도 포함한다.

| 함수          | 반환형     | 조회하는 값    | 기억할 질문                   |
| ----------- | ------- | --------- | ------------------------ |
| `getpid()`  | `pid_t` | 자신의 PID   | 나는 어느 프로세스인가?            |
| `getppid()` | `pid_t` | 부모 PID    | 누가 나를 생성했는가?             |
| `getuid()`  | `uid_t` | 실제 사용자 ID | 실제 사용자는 누구인가?            |
| `geteuid()` | `uid_t` | 유효 사용자 ID | 권한 판단에 쓰이는 사용자 ID는 무엇인가? |
| `getgid()`  | `gid_t` | 실제 그룹 ID  | 실제 그룹은 무엇인가?             |
| `getegid()` | `gid_t` | 유효 그룹 ID  | 권한 판단에 쓰이는 그룹 ID는 무엇인가?  |

## 3. 프로세스의 메모리 구조
### 3.1. 네 가지 주요 영역
> [[프로세스 메모리 레이아웃]]

개념적 배치는 다음과 같다.

```text
높은 주소
+----------------------------+
| 명령행 인자·환경 변수       |
+----------------------------+
| Stack: 지역 변수·호출 정보  |
|              ↓             |
|                            |
|              ↑             |
| Heap: 동적 할당 메모리      |
+----------------------------+
| BSS: 초기화되지 않은 데이터 |
+----------------------------+
| Data: 초기값이 있는 데이터  |
+----------------------------+
| Text: 실행 코드            |
+----------------------------+
낮은 주소
```

| 영역 | 저장 내용 | 강의 예제와 연결 |
|---|---|---|
| **Text** | 실행할 기계어 명령 | `main`, `func1`, `func2`의 코드 |
| **Data** | 초기값이 있는 전역·정적 변수 | 초기값을 지정한 전역 변수 |
| **BSS** | 초기화되지 않았거나 0으로 초기화되는 전역·정적 변수 | `int glob1, glob2;` |
| **Heap** | 동적으로 할당한 메모리 | `malloc(16)`이 확보한 공간 |
| **Stack** | 지역 변수, 인자, 복귀 주소 등 함수 호출 정보 | `m_local1`, `f1_local1`, `f2_local1` |

강의는 Data와 BSS를 넓은 의미의 데이터 영역으로 묶어 설명한다.
BSS의 전역 변수는 실행 전에 0으로 초기화되므로, “초기화되지 않은 영역”을 “쓰레기 값이 들어 있는 영역”으로 이해하면 안 된다.

### 3.2. 주소 출력 예제
강의 예제는 `main()`에서 `func1()`을, `func1()`에서 `func2()`를 호출하고 각 변수·함수의 주소를 출력한다.

```text
main() 호출 프레임
  └─ func1() 호출 프레임
       └─ func2() 호출 프레임
```

관찰할 내용은 세 가지다.
1. **함수 코드와 전역 변수, 동적 할당 공간, 지역 변수의 위치가 구분된다.**
2. 강의의 실행 결과에서는 함수 호출이 깊어질수록 지역 변수의 주소가 낮아진다. 이는 예시 환경에서 스택이 낮은 주소 방향으로 자라는 모습을 보여 준다.
3. 정확한 주소 숫자를 암기하기보다 **각 주소가 어느 영역에 속하는지** 설명할 수 있어야 한다.

특히 다음 구분이 중요하다.
```c
int *dynamic_addr;          // 지역 포인터 변수 자체: 강의 모델에서는 Stack
dynamic_addr = malloc(16);  // 포인터가 가리키는 할당 공간: Heap
```
- `&dynamic_addr`: 포인터 변수 자체의 주소.
- `dynamic_addr`: 동적으로 할당받은 공간의 주소.

> **주의**
> 그림의 주소와 성장 방향은 강의의 환경을 설명하는 모델이다.
> 실제 배치와 지역 변수의 저장 방식은 아키텍처, 컴파일러, 최적화 등에 따라 달라질 수 있다.
> 또한 Text는 코드가 놓인 영역이지, 명령을 실행할 때마다 공간이 계속 늘어나는 영역이 아니다.

### 3.3. 스택 프레임
**스택 프레임** (Stack Frame)
- **함수 호출 한 번에 대응하는 호출 정보 묶음이다.**

32비트 x86 예시에서는 다음 항목을 보여 준다.

| 항목 | 역할 |
|---|---|
| 인자(arguments) | 호출한 함수에 전달할 값 |
| 복귀 주소(return address) | 함수가 끝났을 때 돌아갈 위치 |
| 저장된 `ebp` | 이전 함수의 스택 프레임을 찾는 기준 |
| 지역 변수 | 해당 함수가 실행 중 사용할 값 |

`ebp`는 강의 예시에서 스택 프레임의 기준 주소로 쓰이는 레지스터다.

**함수 호출 → 새 프레임 사용 → 함수 실행 → 복귀 주소로 돌아감**의 흐름으로 이해하면 된다.
인자 위치와 레지스터 사용 방식은 호출 규약에 따라 달라질 수 있다.

### 3.4. 사용자 스택과 커널 스택
| 구분    | 사용자 스택                        | 커널 스택                  |
| ----- | ----------------------------- | ---------------------- |
| 사용 상황 | 사용자 코드의 함수 실행                 | 시스템 호출 등 커널 코드 실행      |
| 담는 정보 | 지역 변수, 인자, 이전 프레임 정보, 복귀 주소 등 | 커널 실행에 필요한 호출·실행 정보    |
| 공통점   | 실행 후 돌아갈 위치와 호출 상태를 유지        | 실행 후 돌아갈 위치와 호출 상태를 유지 |

사용자 함수 실행과 커널 내부 실행은 각각 필요한 스택을 사용한다는 점을 기억한다.

## 4. 프로세스 문맥
**문맥** (Context)
- **커널이 관리하는 태스크의 자원과 제어 흐름에 관한 정보의 집합이다.**
- **프로세스를 관리하고, 중단한 실행을 다시 이어 가기 위해 필요한 정보**다.

| 문맥                            | 답하는 질문                    | 주요 내용                        |
| ----------------------------- | ------------------------- | ---------------------------- |
| **하드웨어 문맥(Hardware Context)** | CPU에서 어디까지 실행했는가?         | 명령 위치, 스택 포인터, 레지스터, 플래그 등   |
| **메모리 문맥(Memory Context)**    | 어떤 주소 공간을 사용하는가?          | 코드·데이터·스택, 메모리 영역·주소 변환 정보 등 |
| **시스템 문맥(System Context)**    | 누구이며, 어떤 상태이고, 무엇을 사용하는가? | PID, 상태, 우선순위, 관계, 파일, 시그널 등 |

**암기 연결**
- 하드웨어 = CPU 실행 상태
- 메모리 = 주소 공간
- 시스템 = 관리 정보

## 5. 하드웨어 문맥
### 5.1. 왜 CPU 상태를 저장해야 할까?
시분할 시스템에서는 여러 태스크가 CPU를 번갈아 사용한다.
태스크가 중단되었다가 다시 CPU를 받으면 **중단했던 위치와 상태에서 이어서 실행**해야 한다.

```text
시간 →
CPU: [태스크 A 실행] [태스크 B 실행] [태스크 C 실행] [태스크 A 재개]
         상태 저장                                  상태 복원
```

**시간 할당량 (time quantum)**
- 태스크에 배정하는 CPU 실행 시간의 단위다.

### 5.2. 저장하는 하드웨어 상태
32비트 x86 레지스터를 역할 중심으로 정리하면 다음과 같다.

| 종류 | 예 | 의미 |
|---|---|---|
| 명령 포인터 | `eip` | 다음에 실행할 명령 위치 |
| 스택 포인터 | `esp` | 현재 스택 위치 |
| 상태 플래그 | `eflags` | 연산·CPU 상태 |
| 범용 레지스터 | `eax`, `ebx`, `ecx`, `edx`, `esi`, `edi` 등 | 계산 중인 값과 임시 데이터 |
| 세그먼트 관련 | `cs`, `ds`, `ss` 등 | 세그먼트 관련 실행 환경 |
| 제어 관련 | `cr0`, `cr3`, `LDTR`, `TR` 등 | CPU·주소 변환 관련 제어 정보 |

**TSS (Task State Segment)**
- **명령 위치뿐 아니라 실행에 필요한 CPU 상태를 보존한다.**

> 하드웨어 자료구조 관점에서는 TSS로 정의된다.
> 현대 운영체제 관점에서는 소프트웨어 문맥 교환 방식으로 정의된다.

### 5.3. 문맥 교환
**문맥 교환 (Context Switch)**
- 현재 태스크의 실행 상태를 저장하고, 다른 태스크의 상태를 복원하여 실행 주체를 바꾸는 과정이다.

1. 태스크 A가 실행 중이다.
2. 커널이 실행 주체를 바꿔야 하는 상황을 처리한다.
3. A의 재개에 필요한 상태를 저장한다.
4. 스케줄러가 실행할 태스크 B를 선택한다.
5. B의 실행에 필요한 문맥을 복원한다.
6. B가 자신의 실행 위치에서 수행을 이어 간다.
7. 나중에 A가 선택되면 A도 저장된 위치에서 재개한다.

```text
A 실행
  → A 상태 저장
  → B 상태 복원
  → B 실행
  → B 상태 저장
  → A 상태 복원
  → A 실행 재개
```

### 5.4. 의사코드
아래 코드는 강의의 제어 흐름을 설명하기 위한 **의사코드**이며 실제 호출 가능한 API가 아니다.
```c
if (save_context()) {
    /* 실행할 다른 태스크 선택 */
    restore_context(new_task);
    /* 이 교환 경로에서는 일반 함수처럼 여기로 돌아오지 않음 */
}
/* 기존 태스크가 복원되면 실행을 이어 가는 지점 */
```

- 저장 후 다른 태스크로 넘어가는 경로와, 나중에 복원되어 재개하는 경로를 구분한다.
- `restore_context()`를 일반 함수 호출처럼 “일을 마치고 바로 다음 줄로 돌아오는 함수”로 생각하면 흐름을 이해하기 어렵다.
- 강의는 x86에서 정수 반환값을 `eax`에 두는 규약을 이용해 이 제어 흐름을 설명한다.

### 5.5. 문맥 교환의 비용
문맥 교환에는 저장·복원 등 관리 작업이 필요하다.
이 시간에는 사용자 프로그램의 본래 작업이 진행되지 않으므로 **오버헤드**가 발생한다.

강의는 빠른 교환의 필요성과 하드웨어 지원의 예로 shadow register를 언급한다.

**보충·구분**
- 시스템 호출이나 인터럽트로 커널에 진입했다고 해서 반드시 다른 프로세스로 바뀌는 것은 아니다.
- 같은 프로세스로 돌아올 수도 있다.
- **사용자/커널 실행 수준의 전환**과 **실행 태스크를 바꾸는 문맥 교환**은 구분해서 이해한다.

## 6. 메모리 문맥
### 6.1. 생성 전후 그림의 의미
PID 11인 부모 프로세스에서 PID 12인 자식 프로세스가 생기는 모습을 보여 준다.
```text
fork() 전
부모 PID 11 → 부모의 메모리 문맥 → Text / Data / Stack

fork() 후
부모 PID 11 → 부모의 메모리 문맥 → 부모 Data / Stack
자식 PID 12 → 자식의 메모리 문맥 → 자식 Data / Stack
                         └─ 코드 영역은 공유 가능
```

핵심은 다음과 같다.
- 자식은 부모와 다른 PID를 가진 별도의 프로세스다.
- 부모와 자식은 각각 자신의 주소 공간을 가진다.
- 생성 직후 메모리 내용은 같을 수 있어도, 이후 각자의 일반적인 변수 변경은 독립적이다.

### cf. 보충
논리적 독립과 실제 복사 시점
- Linux의 `fork()`는 쓰기 시 복사(Copy-on-Write, COW)를 사용한다.
- 따라서 “별도 주소 공간”이라고 해서 생성 순간 모든 물리 메모리를 즉시 복사한다는 뜻은 아니다.
- 페이지를 공유하다가 쓰기가 필요할 때 복사할 수 있다.
- [Linux man-pages: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

**기억할 구분**
- 주소 공간이 독립적이라는 설명과 물리 메모리의 복사 시점에 관한 설명은 서로 다른 층위의 이야기다.

## 7. 시스템 문맥
### 7.1. `task_struct`가 관리하는 것
`task_struct`
- Linux에서 태스크 관리 정보를 담는 핵심 자료구조다.
- 파일·메모리·시그널 자료구조 등을 **연결하여 관리**한다. 모든 정보가 하나의 구조체 안에 직접 들어 있다고 이해할 필요는 없다.

| 정보 범주 | 내용 또는 강의에 등장하는 이름 |
|---|---|
| 식별 정보 | PID, 사용자·그룹 관련 ID |
| 상태 | 실행 가능, 수면, 정지, 좀비 등 |
| 가족·연결 관계 | 부모·자식, 다른 태스크와의 연결 |
| 스케줄링 | 정책, 우선순위, 재스케줄 필요 여부 |
| 메모리 | `mm_struct` 등 메모리 관리 정보 |
| 파일·파일시스템 | `files_struct`, `fs_struct` |
| 시그널 | 시그널 관련 정보, 대기·차단 여부 |
| 실행 상태 | 스레드·하드웨어 상태 관련 정보 |
| 기타 | 수행 시간, 실행 파일 이름, 자원 제한, 종료 코드 등 |

### 7.2. 태스크 목록과 실행·대기 큐
운영체제는 관리 목적에 따라 태스크들을 연결한다.

| 구조 | 목적 |
|---|---|
| 전체 태스크 목록 | 존재하는 태스크들을 관리 |
| 실행 큐(`run_queue`) | CPU를 배정할 실행 가능한 태스크들을 관리 |
| 대기 큐(`wait_queue`) | 특정 조건이나 사건을 기다리는 태스크들을 관리 |

`next_task`, `prev_task`, `next_run`, `prev_run` 같은 연결 필드와 리스트 연산이 나온다.

| 리스트 연산 | 의미 |
|---|---|
| `list_add(n, p)` | 지정 위치에 노드 삽입 |
| `list_add_tail(n, h)` | 리스트 끝에 노드 삽입 |
| `list_del(p)` | 노드 제거 |
| `list_empty(p)` | 비어 있는지 확인 |
| `list_for_each(p, h)` | 리스트 순회 |

> **주의**
> 이 자료에는 과거 Linux의 구조체 필드와 구현 방식이 포함되어 있다.

## 8. 프로세스 상태와 상태 전이
### cf. 7상태 프로세스 모델
![[7-state_Process_Model.png]]

### 8.1. 세 가지 기본 상태
| 상태               | 의미                      | 실행하지 못하는 이유     |
| ---------------- | ----------------------- | --------------- |
| **Ready: 준비**    | 실행할 준비가 되어 CPU를 기다림     | CPU를 배정받지 못함    |
| **Running: 실행**  | CPU에서 명령을 수행 중          | 현재 실행 중         |
| **Sleep: 수면·대기** | 입출력 완료나 자원 등 특정 조건을 기다림 | 필요한 조건이 충족되지 않음 |
**가장 중요한 차이**: Ready는 **CPU를 기다리고**, Sleep은 **사건·조건을 기다린다**.

### 8.2. 주요 전이
```text
Ready --스케줄러가 선택--> Running
Running --CPU 양보·선점--> Ready
Running --입출력·잠금 등 대기 필요--> Sleep
Sleep --입출력 완료·깨움·조건 충족--> Ready
Running --exit--> Zombie --부모의 wait로 종료 정보 회수--> 정리
```

| 상황 | 전이 | 이해할 점 |
|---|---|---|
| 실행 대상으로 선택됨 | Ready → Running | CPU를 받음 |
| CPU를 다른 태스크에 넘김 | Running → Ready | 실행은 가능하지만 CPU를 내려놓음 |
| 필요한 사건을 기다림 | Running → Sleep | 기다리는 동안 CPU를 사용하지 않음 |
| 기다리던 사건이 발생함 | Sleep → Ready | 실행 가능해졌지만 CPU를 즉시 받는 것은 아님 |
| 실행을 종료함 | Running → Zombie | 종료 정보가 회수되기를 기다리는 단계 |

**시험 포인트**
- 일반적인 상태 모델에서 깨운 태스크는 곧바로 Running이 되는 것이 아니라 **Ready가 되어 스케줄링을 기다린다**.

### 8.3. 좀비와 중단 상태
- **Zombie**: 실행은 끝났지만 부모가 종료 정보를 회수하기 전인 상태. 다시 CPU를 받아 계산하는 상태가 아니다.
- **Suspended Ready**: 강의의 swap 모델에서 실행 조건은 갖췄으나 메모리 밖으로 내보내진 상태
- **Suspended Sleep**: 강의의 swap 모델에서 대기 중이면서 메모리 밖으로 내보내진 상태

`Sleep`은 “사건을 기다림”, `Suspended`는 강의 그림에서 “swap으로 실행에 필요한 메모리가 밖으로 나감”이라는 서로 다른 구분이다.

> **주의**
> 이 상태 그림은 UNIX의 개념 모델이다.
> 강의에 나오는 `TASK_RUNNING` 같은 Linux 내부 상태 이름과 개념적 Ready/Running 상태를 일대일로 대응시키지 않는다.
> 강의가 열거하는 다른 상태에는 `TASK_ZOMBIE`, 인터럽트 가능·불가능 수면, `TASK_STOPPED` 등이 있다.

### 8.4. 사용자 수준 실행과 커널 수준 실행
실행 상태는 **어떤 수준의 코드를 실행하는가**에 따라 다시 나뉜다.

| 실행 수준 | 내용 |
|---|---|
| 사용자 수준 실행 | 사용자 프로그램 코드 실행 |
| 커널 수준 실행 | 시스템 호출, 인터럽트 처리 등 커널 코드 실행 |

```text
사용자 프로그램 실행
      |
      | 시스템 호출 또는 인터럽트
      v
커널 코드 실행
      |
      +-- 처리가 끝남 ------------------> 사용자 실행으로 복귀
      +-- 기다려야 함 ------------------> Sleep
      +-- 다른 태스크를 실행하도록 결정 --> 스케줄링·문맥 교환
```

즉, **Running은 사용자 코드만 실행하는 상태를 뜻하지 않는다.**
커널 수준에서도 실행 중일 수 있다.

## 9. 하나의 상황으로 연결하기
다음은 강의 개념들을 연결하기 위한 학습용 예시다.

1. 프로그램을 실행하면 코드·데이터와 실행 환경을 가진 프로세스가 생긴다.
2. 운영체제는 PID와 상태, 메모리·파일 정보 등을 관리한다.
3. Ready 상태의 프로세스가 선택되면 Running이 된다.
4. 함수 호출 시 사용자 스택에 호출 정보를 유지한다.
5. 입출력을 요청하면 시스템 호출을 통해 커널 코드가 실행된다.
6. 입출력 완료를 기다려야 하면 Sleep 상태가 된다.
7. 커널은 현재 실행 상태를 보존하고 다른 실행 가능한 태스크로 문맥을 교환한다.
8. 입출력이 끝나면 대기 중이던 프로세스는 Ready가 된다.
9. 다시 선택되면 저장된 문맥을 복원하여 실행을 이어 간다.
10. 실행 종료 후 부모가 종료 정보를 회수하면 좀비로 남아 있던 정보도 정리된다.

이 과정을 설명할 때 **메모리 영역**, **세 종류의 문맥**, **상태 전이**를 함께 연결하면 단원 전체가 하나의 흐름으로 이해된다.

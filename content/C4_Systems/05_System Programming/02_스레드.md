## 1. 먼저 잡아야 할 핵심
**프로세스**는 자원을 소유하는 실행 중인 프로그램이고,
**스레드**는 그 프로세스 안에서 실행되는 흐름이다.

- 같은 프로세스의 스레드는 코드, 전역 데이터, 힙, 열린 파일 등의 자원을 공유한다.
- 각 스레드는 실행 위치와 호출 상태를 유지하기 위해 자신의 레지스터와 스택을 가진다.
- 스레드는 응답성, 처리량, 멀티프로세서 활용에 도움이 된다.
- 자원을 공유하기 때문에 경쟁 상태와 교착 상태를 주의해야 한다.
- 실제 병렬 실행 가능 여부는 사용자 스레드가 커널 실행 문맥에 어떻게 매핑되는지에 달려 있다.

**학습 순서**
- 프로세스와 스레드 구분 → 공유/개별 자원 구분 → 사용 목적 → 매핑 모델 비교 → 동기화 필요성 이해

## 2. 프로세스
**프로세스** (Process)
- **실행 중인 프로그램의 인스턴스**다.
- 프로그램이 어디까지 실행되었는지 나타내는 상태와 실행에 필요한 자원을 함께 관리한다.
- 자원을 담는 **컨테이너(Container)** 역할이다.

### 2.1. 프로세스 정보
| 분류        | 프로세스가 관리하는 정보·자원                   |
| --------- | ---------------------------------- |
| 식별·권한     | 프로세스 ID, 프로세스 그룹 ID, 사용자 ID, 그룹 ID |
| 실행 환경     | 환경 변수, 작업 디렉터리                     |
| 메모리       | 프로그램 명령어, 스택, 힙, 공유 라이브러리          |
| CPU 실행 상태 | 레지스터, 실행 위치 등                      |
| 입출력·통신    | 파일 디스크립터, 파이프, 메시지 큐, 공유 메모리 등     |
| 기타 제어 정보  | 시그널 처리 방식, 세마포어 등                  |

### 2.2. 프로세스 문맥
**문맥** (Context)
- 실행을 중단했다가 이어서 실행하기 위해 필요한 정보

| 구분          | 그림의 구성 요소                            | 이해할 점                    |
| ----------- | ------------------------------------ | ------------------------ |
| **하드웨어 문맥** | `eip`, `sp`, `eflags`, `eax`, `cs` 등 | CPU에서 어디까지, 어떤 상태로 실행했는가 |
| **메모리 문맥**  | 세그먼트 테이블, 페이지 테이블, 메모리·디스크와의 연결      | 실행에 필요한 주소 공간이 어떻게 구성되는가 |
| **시스템 문맥**  | 태스크 구조, 파일 테이블 등                     | 운영체제가 관리하는 프로세스 정보       |

> 문맥은 레지스터만 뜻하지 않는다.
> 실행 상태와 자원 관리 정보를 함께 생각한다.

## 3. 스레드
**스레드** (Thread)
- **프로세스의 실행 단위이자 실행 흐름**이다.
- 하나의 프로세스에 스레드가 하나면 단일 스레드, 여러 개면 다중 스레드 프로세스다.

### 3.1. 무엇을 공유하고, 무엇을 따로 가지는가?
> ==스레드가 공유하는 것== #3-2/UNIX시스템프로그래밍/출제 (O/X)

| 같은 프로세스에서 공유하는 것 | 스레드마다 따로 유지하는 것         |
| ---------------- | ----------------------- |
| 주소 공간            | 스택과 스택 포인터(SP)          |
| 코드 영역            | 프로그램 카운터(PC)와 레지스터      |
| 전역 데이터·힙         | 스케줄링 속성: 정책·우선순위 등      |
| 열린 파일 등 프로세스 자원  | 스레드별 시그널 관련 상태          |
| 프로세스 ID          | 스레드 고유 데이터(TSD), 스레드 ID |

왜 스택과 레지스터는 따로 필요한가?
- 각 스레드는 서로 다른 함수를 실행하거나, 같은 함수의 다른 위치를 실행할 수 있다.
- 따라서 다음 실행 위치, 함수 호출 이력, 계산 중인 값을 개별적으로 유지해야 한다.

**보충**
- ‘스택이 개별적’이라는 말은 ‘다른 스레드에서 절대 접근할 수 없다’는 뜻은 아니다.
- 같은 주소 공간을 사용하므로 스택의 주소를 다른 스레드에 넘긴 경우에도 접근 시점과 수명에 주의해야 한다.

**보충**
- 시그널 상태는 모두 같은 단위로 관리되지 않는다.
- 시그널 마스크는 스레드별로 유지되지만, 시그널 처리 방식은 프로세스에서 공유하며 pending 상태에는 프로세스 단위와 스레드 단위가 있다.
- 강의의 스레드별 시그널 항목을 모든 시그널 정보가 독립적이라는 뜻으로 외우지 않는다.

### 3.2. 일반 함수 호출과 스레드 생성
| 일반 함수 호출                   | 스레드 생성                           |
| -------------------------- | -------------------------------- |
| 기존 실행 흐름이 호출한 함수로 이동한다.    | 별도의 실행 흐름이 생긴다.                  |
| 호출한 함수가 반환하면 다음 문장을 실행한다.  | 생성한 쪽과 생성된 스레드가 각각 실행을 진행할 수 있다. |
| 함수 호출 자체가 새 스레드를 만들지는 않는다. | 새 스레드의 실행 상태와 스택 등이 필요하다.        |

**[보충 예시]**
```text
일반 함수 호출
main: A 실행 → f() 실행 → f() 반환 → B 실행

스레드 생성
main:   A 실행 → 스레드 생성 → B 실행 ...
새 스레드:                  f() 실행 ...
```

> 스레드를 생성했다는 사실만으로 어느 쪽이 먼저 실행될지는 확정되지 않는다.

## 4. 프로세스·스레드·함수 호출 비교
| 비교 항목    | `fork()`로 만든 프로세스 | 같은 프로세스의 스레드           | 일반 함수 호출              |
| -------- | ----------------- | ---------------------- | --------------------- |
| 변수       | 부모의 변수 값을 복사받음    | 전역 변수 등 공유             | 같은 실행 흐름의 전역 변수 사용    |
| 식별자      | 새로운 프로세스 ID       | 프로세스 ID 공유, 스레드 ID는 개별 | 기존 프로세스·스레드 ID 유지     |
| 데이터 전달   | 파이프·공유 메모리 등 IPC  | 공유 변수 등 이용, 동기화 주의     | 인자·반환값·공유 변수 등        |
| CPU 하나   | 동시성 가능            | 동시성 가능                 | 해당 실행 흐름에서는 순차 실행     |
| CPU 여러 개 | 병렬 실행 가능          | 커널 매핑 모델에 따라 병렬 실행 가능  | 함수 호출 자체로는 병렬 실행되지 않음 |

**보충**
- `fork()`의 ‘복사’는 논리적인 주소 공간 분리로 이해한다.
- 일반적인 구현은 Copy-on-Write를 활용할 수 있으므로, 생성 순간에 모든 메모리를 실제로 복사한다고 단정하지 않는다.
- 또한 명시적으로 설정한 공유 메모리는 별도로 공유할 수 있다.

### 4.1. 동시성과 병렬성
**보충**
- **동시성** (Concurrency): 여러 작업이 일정 기간 동안 번갈아 진행될 수 있다. CPU가 하나여도 가능하다.
- **병렬성** (Parallelism): 여러 작업이 실제로 같은 시점에 실행된다. 여러 실행 코어가 필요하다.

**기억할 문장**
- 스레드가 여러 개라는 사실과, 여러 코어에서 동시에 실행된다는 사실은 다르다.

## 5. 스레드를 사용하는 이유
| 이유           | 설명                             | 기대 효과                |
| ------------ | ------------------------------ | -------------------- |
| 자연스러운 동시성 표현 | 서로 독립적으로 진행할 작업을 실행 흐름으로 분리    | 프로그램 역할을 나누기 쉬움      |
| 멀티프로세서 활용    | 병렬 실행 가능한 부분을 여러 CPU에서 처리      | 실행 성능 향상 가능          |
| 자원 공유·협력     | 같은 주소 공간에서 데이터를 전달             | IPC에 비해 통신 부담 감소 가능  |
| 생성 비용 절감     | 자원을 공유하는 스레드를 생성               | 프로세스를 자주 만드는 비용 완화   |
| 처리량 향상       | 여러 클라이언트 요청을 나누어 처리            | 서버가 더 많은 요청을 처리할 가능성 |
| I/O와 계산의 중첩  | 한 스레드가 I/O를 기다리는 동안 다른 스레드가 계산 | 대기 시간 활용             |

### 5.1. 생성 비용 실험
강의는 `fork()`와 `pthread_create()`를 이용한 **50,000회 생성 시간**을 비교한다.
단위는 초이며, 최적화 플래그를 사용하지 않은 실험이다.
표에 나온 환경에서는 스레드 생성의 경과 시간(`real`)이 프로세스 생성보다 짧다.

**보충**
- 이 결과는 ‘스레드 생성이 더 가벼울 수 있다’는 근거다.
- 특정 수치나 배율을 모든 운영체제·프로그램에 적용하거나, 스레드를 늘리면 항상 빨라진다고 결론 내리면 안 된다.
- 생성·문맥 교환·동기화 비용도 고려해야 한다.

## 6. 활용 사례
### 6.1. 워드 프로세서
강의 그림은 키보드 입력, 문서 처리, 디스크 접근이 있는 프로그램을 보여주고, 단일 스레드일 때의 문제를 묻는다.

**보충: 역할 분리 예시**

| 역할 | 작업 |
|---|---|
| 입력·화면 담당 | 키 입력 처리, 화면 반응 |
| 문서 처리 담당 | 문서 배치 계산 등 |
| 저장 담당 | 디스크에 문서 저장 |

단일 스레드가 오래 걸리는 저장이나 계산을 수행하면 입력 처리가 지연될 수 있다.
역할을 나누면 다른 작업을 진행할 여지가 생긴다. 단, 실제 효과는 스레딩 모델과 작업 구성에 따라 달라진다.

### 6.2. 다중 스레드 웹 서버
강의의 서버는 **Dispatcher와 Worker**로 역할을 나눈다.

| 구성 요소          | 역할                        |
| -------------- | ------------------------- |
| Dispatcher 스레드 | 요청을 받아 Worker에게 넘긴다.      |
| Worker 스레드     | 요청을 처리하고 응답을 반환한다.        |
| 웹 페이지 캐시       | 필요한 페이지가 있으면 디스크 접근을 줄인다. |

요청 처리 흐름은 다음과 같다.
1. Dispatcher가 다음 요청을 받는다.
2. 요청을 Worker에게 넘긴다.
3. Worker가 캐시에서 페이지를 찾는다.
4. 캐시에 없으면 디스크에서 읽는다.
5. 페이지를 응답으로 반환하고 다음 작업을 기다린다.

강의의 의사코드를 역할 중심으로 풀면 다음과 같다.
```text
Dispatcher:
  반복:
    다음 요청 받기
    작업 전달하기

Worker:
  반복:
    작업 기다리기
    캐시 조회하기
    캐시에 없으면 디스크에서 읽기
    페이지 반환하기
```

**핵심**
- 요청을 받는 역할과 처리하는 역할을 나누어, 하나의 요청을 처리하는 동안 다른 요청도 진행할 수 있게 한다.
- 공유 캐시와 작업 전달 부분에서는 동기화가 필요하다.

## 7. 스레딩 모델
> 사용자 스레드와 커널 실행 문맥의 연결

### 7.1. 비교할 기준
유저 레벨에서 관리하는 스레드가 **커널이 스케줄링하는 실행 문맥 몇 개에 연결되는가**를 비교한다.

| 모델                 | 매핑               | 관리 방식                                   | 여러 코어에서 병렬 실행            |
| ------------------ | ---------------- | --------------------------------------- | ------------------------ |
| **유저 레벨**<br>(ULT) | **다대일**<br>(N:1) | 사용자 공간 라이브러리가 여러 스레드를 관리, 커널에는 실행 문맥 하나 | 이 모델의 한 프로세스 내에서는 불가     |
| **커널 레벨**<br>(KLT) | **일대일**<br>(1:1) | 각 사용자 스레드에 커널 실행 문맥 하나                  | 가능                       |
| **혼합형 스레드**        | **다대다**<br>(N:M) | 여러 사용자 스레드를 여러 커널 실행 문맥에 배치             | 가능, 커널 실행 문맥 수 등의 제약을 받음 |

> 유저 레벨 스레드를 N:1, 커널 레벨 스레드를 1:1의 대표 모델로 설명한다.
> 여기서 ‘가능’은 실제 작업의 병렬 실행을 보장한다는 뜻이 아니다.

### 7.2. 유저 레벨 스레드 (ULT)
스레드 생성·관리·스케줄링을 사용자 공간의 런타임 라이브러리가 수행한다.
이 라이브러리는 특권 명령이나 커널 기능에 직접 접근할 수 없다.

- **장점**: 라이브러리가 작업 특성에 맞춰 스케줄링할 수 있다. 사용자 공간에서 수행하는 스레드 전환·동기화는 커널 진입 부담을 줄일 수 있다. 이식성이 좋다.
- **한계**: 커널에는 실행 흐름 하나로 보인다. 따라서 여러 사용자 스레드를 여러 CPU에 동시에 배치할 수 없다.
- **I/O 문제**: 하나의 스레드가 블로킹 I/O를 호출하면 커널 실행 문맥이 막혀 다른 사용자 스레드도 진행하지 못할 수 있다.

**왜 여러 코어를 못 쓰는가?**
- 커널이 스케줄링할 수 있는 실행 문맥이 하나이기 때문이다.
- 사용자 라이브러리에 스레드가 여러 개 있어도 커널은 각각을 독립적으로 배치할 수 없다.

### 7.3. 커널 레벨 스레드 (KLT)
각 스레드를 개별 커널 실행 문맥에 매핑한다.
커널이 각 실행 흐름을 구분하여 스케줄링할 수 있다.

- **장점**: 여러 CPU에서 병렬 실행할 수 있다. 확장성, 응답성, 처리량을 높일 수 있다.
- **단점**: 커널 관여와 문맥 교환에 비용이 든다. 강의는 운영체제별 API에 따른 이식성 부담도 지적한다.
- **결론**: 유저 레벨 스레드의 한계를 완화하지만, 모든 프로그램에서 최선은 아니다.

**보충**
- 한 스레드가 I/O를 기다리더라도 다른 실행 가능한 스레드를 커널이 스케줄링할 수 있다.
- 다만 필요한 락을 대기 중인 스레드가 보유하고 있다면 다른 스레드도 진행이 막힐 수 있다.

### 7.4. 혼합형 스레드 (Hybrid Thread)
유저 레벨과 커널 레벨을 결합한 **M:N 매핑**이다.
사용자 스레드 수와 커널 스레드 수가 같을 필요가 없다.

| 개념 | 강의의 설명 |
|---|---|
| 스레드 풀(Thread Pool) | 커널 스레드를 유지·재사용하여 반복 생성·소멸 부담을 줄임 |
| Worker 스레드 | 풀에 지속적으로 존재하며 사용자 스레드의 실행을 맡는 커널 스레드 |
| Scheduler Activation | 운영체제가 유저 레벨 라이브러리에 알리고, 라이브러리가 재스케줄링 필요 여부를 판단하는 기법 |

**보충 예시**
- 사용자 스레드 100개를 커널 스레드 4개에 배치한다면, 많은 논리적 작업을 관리하면서 커널 스레드를 재사용할 수 있다.
- 이 구성에서 동시에 실행 중인 사용자 스레드는 최대 4개이며, 실제 병렬 실행 수는 사용 가능한 코어 등에도 제한된다.

**보충**
- 스레드 풀과 M:N 매핑은 같은 개념이 아니다.
- 일반적인 1:1 스레딩 환경에서도 작업을 처리하는 스레드 풀을 사용할 수 있다.
- 강의에서는 혼합형 모델의 비용 절감 방법으로 풀을 소개한다.

### 7.5. 모델을 외우는 세 질문
1. **누가 스레드를 관리하는가?** 사용자 라이브러리, 커널, 또는 둘의 협력인가?
2. **커널이 실행 흐름을 몇 개 구분하는가?** 하나인가, 사용자 스레드마다 하나인가, 여러 개인가?
3. **그 결과는 무엇인가?** 병렬성, 블로킹 I/O의 영향, 관리 비용이 어떻게 달라지는가?

## 8. 스레드 프로그래밍의 함정
[[프로세싱#2. 병행 처리 / 동시 처리 (Concurrent Processing)|병행 처리]]의 ==종류, 필요성, 문제점, 해결 방법== #3-2/UNIX시스템프로그래밍/출제

| 문제            | 발생 이유                          | 학습할 대응 방향                |
| ------------- | ------------------------------ | ------------------------ |
| 설계 복잡성 증가     | 실행 순서와 공유 데이터 접근을 함께 고려해야 함    | 작업 역할과 공유 자원을 명확히 함      |
| 디버깅·테스트 어려움   | 실행 순서와 CPU 환경에 따라 문제가 달라질 수 있음 | 한 번 정상 실행된 것으로 판단하지 않음   |
| 경쟁 상태         | 공유 데이터를 여러 실행 흐름이 동기화 없이 변경    | 필요한 접근 구간을 동기화           |
| 교착 상태         | 자원을 잠그는 과정에서 서로를 기다릴 수 있음      | 락 획득 순서를 주의              |
| 안전하지 않은 라이브러리 | 동시 호출을 고려하지 않은 내부 상태가 있을 수 있음  | thread-safe 여부와 사용 조건 확인 |

단일 프로세서에서 정상 동작하던 프로그램도 SMP 환경에서 실패할 수 있다.
SMP는 여러 프로세서가 메모리 등을 공유하는 대칭형 다중 처리 환경을 뜻한다.

### 8.1. 경쟁 상태
**경쟁 상태** (Race Condition)
- **공유 데이터에 대한 접근·변경 순서에 따라 결과가 달라지는 상황**이다.

#### 강의 그림: 인쇄 스풀러 디렉터리
그림에서 `out = 4`는 다음 출력 위치, `in = 7`은 다음 등록 위치를 가리킨다. Process A와 B가 모두 7번 위치에 작업을 등록하려는 상황이다.

**보충: 그림을 실행 순서로 풀어 쓴 예시**

| 순서 | Process A | Process B | 결과 |
|---|---|---|---|
| 1 | `in`을 읽어 7을 얻음 | | A는 7번이 비었다고 판단 |
| 2 | | `in`을 읽어 7을 얻음 | B도 7번이 비었다고 판단 |
| 3 | 7번에 작업 A 등록, `in = 8` | | A 등록 |
| 4 | | 7번에 작업 B 등록, `in = 8` | 작업 A를 덮어쓸 수 있음 |

문제는 단순히 ‘마지막 값’만이 아니다.
**빈 위치 확인 → 작업 등록 → 다음 위치 갱신**이라는 일련의 동작을 두 실행 흐름이 겹쳐 수행하는 데 있다.

#### 더 간단한 이해용 예시
**보충**
- 공유 카운터가 0일 때 두 스레드가 각각 1을 더한다고 하자.
- 다음 표는 동기화 없는 읽기·계산·쓰기를 설명하기 위한 개념 예시다.

| 순서 | 스레드 A | 스레드 B |
|---|---|---|
| 1 | 카운터 0 읽기 | |
| 2 | | 카운터 0 읽기 |
| 3 | 1 계산 후 저장 | |
| 4 | | 1 계산 후 저장 |

기대한 결과는 2이지만, 한쪽의 갱신이 사라져 1이 될 수 있다.

**해결 원리**
- 함께 보호해야 할 공유 데이터 접근을 동기화한다.

**보충**
- 스풀러의 확인·등록·갱신 구간에는 뮤텍스 등으로 상호 배제를 적용할 수 있고, 단순 카운터에는 원자적 증가 연산을 사용할 수 있다.

### 8.2. 교착 상태 (Deadlock)
**보충: 락 순서 주의를 설명하는 예시**
- 스레드 A: 락 X를 가진 채 락 Y를 기다린다.
- 스레드 B: 락 Y를 가진 채 락 X를 기다린다.
- 상대가 보유한 락을 기다리므로 둘 다 진행하지 못한다.

락이 여러 개 필요한 코드에서는 **일관된 락 획득 순서**가 중요한 예방 방법이다.

### 8.3. 스레드 안전성과 재진입성
동시 실행에 안전하지 않은 라이브러리를 주의한다.

> 두 용어는 관련 있지만 동일하지 않다.

**스레드 안전성 (Thread Safety)** #3-2/UNIX시스템프로그래밍/출제 (O/X)
- 여러 스레드가 동시에 호출해도 정해진 조건에서 올바르게 동작함

**재진입성** (Reentrant)
- 이전 호출이 끝나기 전에 다시 진입해도 올바르게 동작함

내부 락으로 동시 호출을 보호하는 함수가 재진입에도 안전하다고 단정할 수는 없다.
라이브러리의 사용 조건을 확인해야 한다.

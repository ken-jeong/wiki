## 요약
- **서블릿**: HTTP 요청을 동적으로 처리하는 자바 서버 컴포넌트
- **서블릿 컨테이너**: 생명 주기와 요청·응답 처리를 관리한다.

### URL 매핑
- `web.xml`: 외부 XML 설정
- `@WebServlet(urlPatterns = "/hello")` 클래스의 애너테이션 설정 (서블릿 3.0)
	- 또는 `url-pattern`?
- `/jspbook/hello`: 컨텍스트 경로는 `/jspbook`, 서블릿 매핑은 `/hello`

### `HttpServlet` 클래스 작성
- `init()`: 인스턴스 최초 초기화 시 1번 호출
- `service()`: 요청마다 호출되어 `doGet()`·`doPost()` 등으로 분기
	- `doGet()`: GET 요청(조회) 처리, 분기할 때 호출
	- `doPost()`: POST 요청(등록/데이터 전송) 처리, 분기할 때 호출
- `destroy()`: 서블릿을 종료할 때 1번 호출

### `HttpServletRequest request`
- 클라이언트가 보낸 HTTP 요청 정보를 서블릿에 전달한다.
- 파라미터 메서드
	- `getParameter("name")`: 단일 파라미터 반환 (반드시 `String`, 없으면 `null`)
	- `getParameterValues("name")`: 같은 이름으로 전달된 여러 파라미터 값을 반환
- 요청 주소 메서드
	- `getRequestURL()`: 스킴·호스트·포트 포함 URL
	- `getRequestURI()`: 경로 부분

### `HttpServletResponse response`
- 서버가 클라이언트로 보낼 응답을 구성한다.
- 한글 인코딩 메서드
	1. `setContentType()`: 응답 콘텐츠 타입과 문자 인코딩을 지정
	2. `getWriter()`: 문자 데이터를 출력하기 위한 `PrintWriter`를 반환
- 리다이렉트 메서드
	- `sendRedirect()`: 리다이렉트 응답을 보내 클라이언트가 지정된 URL을 다시 요청

## 1. 먼저 전체 흐름 잡기
**서블릿 (Servlet)**
- HTTP 요청을 처리하는 자바 서버 프로그램
- 컨테이너가 생성·실행·종료를 관리한다.

브라우저가 요청을 보내면 **컨테이너가 URL에 맞는 서블릿(Servlet)을 찾고**, 서블릿이 요청을 처리해 응답한다.

```text
브라우저의 HTTP 요청
    ↓
서블릿 컨테이너: URL 매핑 확인
    ↓
서블릿: service() → doGet() 또는 doPost()
    ↓
요청 데이터 읽기 → 필요한 작업 수행 → 응답 작성
    ↓
브라우저가 HTTP 응답 수신
```

세 가지를 구분하면 이후 내용이 쉬워진다.

| 구분 | 역할 | 기억할 표현 |
|---|---|---|
| 서블릿 | 요청을 받아 동적으로 처리하는 자바 프로그램 | 실제 처리 담당 |
| 서블릿 컨테이너 | 서블릿 등록·생명 주기·요청 실행 관리 | 실행 환경이자 관리자 |
| URL 매핑 | 요청 주소와 서블릿 연결 | 주소를 보고 담당자 찾기 |

대표적인 컨테이너는 **톰캣**(Tomcat)이다.
톰캣은 웹 서버 기능도 포함하므로 단독으로 웹 서비스를 운영할 수 있다.

## 2. 서블릿은 왜 필요한가?
정적인 HTML은 준비된 내용을 그대로 보여 준다.
서블릿은 요청에 따라 프로그램을 실행하므로 **사용자나 상황에 따라 다른 결과**를 만들 수 있다.

- DB와 연동해 조회 결과를 제공한다.
- 외부 서비스와 연동해 필요한 정보를 가져온다.
- 사용자 입력을 받아 처리하고 결과를 응답한다.

예를 들어 상품 조회 요청이 오면, 서블릿이 요청에서 상품 번호를 읽고 DB 조회 결과를 응답할 수 있다.

**서블릿은 단독으로 실행하지 않는다.**
톰캣 같은 컨테이너가 서블릿을 관리하고 호출한다.

## 3. 서블릿 기본 구조
```java
@WebServlet("/hello")  // URL과 서블릿을 매핑한다.
public class HelloWorld extends HttpServlet {  // HttpServlet을 상속한다.
	@Override  // 필요한 doGet()을 오버라이딩한다.
	protected void doGet(
			HttpServletRequest  request,
			HttpServletResponse response
	) throws ServletException, IOException {
		// GET 요청 처리
	}
	
	@Override  // 필요한 doPost()를 오버라이딩한다.
	protected void doPost(
			HttpServletRequest  request,
			HttpServletResponse response
	) throws ServletException, IOException {
		doGet(request, response);
	}
}
```

HTTP 요청을 처리할 때는 보통 다음 순서로 작성한다.
1. `HttpServlet`을 상속한다.
2. 필요한 `doGet()` 또는 `doPost()`를 오버라이딩한다.
3. URL과 서블릿을 매핑한다.
4. 컨테이너에 배포한 후 해당 URL로 요청한다.

| 메서드                         | 처리하는 요청   | 강의에서의 대표 용도  |
| --------------------------- | --------- | ------------ |
| `doGet(request, response)`  | HTTP GET  | 조회           |
| `doPost(request, response)` | HTTP POST | 등록·입력 데이터 처리 |

조회와 등록은 대표적인 사용 예다.
**실제로 어떤 메서드가 호출되는지는 요청의 HTTP 메서드가 결정한다.**

두 메서드에는 다음 객체가 전달된다.

| 매개변수 | 타입 | 역할 |
|---|---|---|
| `request` | `HttpServletRequest` | 클라이언트가 보낸 요청 정보 읽기 |
| `response` | `HttpServletResponse` | 클라이언트에게 보낼 응답 구성 |

컨테이너가 이 타입을 구현한 객체를 준비해 메서드에 전달한다.

## 4. 서블릿 등록과 URL 매핑
클래스를 작성하는 것만으로는 요청 주소와 연결되지 않는다.
컨테이너에 **어떤 클래스가 어떤 URL을 처리하는지** 알려야 한다.

### 4.1. `web.xml` 사용
`web.xml`은 웹 애플리케이션의 **배포 서술자**(배포 설명자)다.
서블릿 등록·URL 매핑·인증 관련 설정 등을 기술한다.

아래 코드는 전체 파일 중 서블릿 등록 부분만 나타낸 것이다.
```xml
<?xml version="1.0" encoding="UTF-8"?>
<web-app>
	<servlet>
	    <servlet-name>HelloWorld</servlet-name>
	    <servlet-class>ch05.HelloWorld</servlet-class>
	</servlet>
	
	<servlet-mapping>
	    <servlet-name>HelloWorld</servlet-name>
	    <url-pattern>/hello</url-pattern>
	</servlet-mapping>
</web-app>
```
- `servlet-class`: 실행할 클래스의 패키지 포함 이름
- `servlet-name`: 등록과 매핑을 연결하는 이름
- `url-pattern`: 이 서블릿이 처리할 요청 경로

**두 곳의 `servlet-name`이 연결 고리**다.
위 설정은 `/hello` 요청을 `ch05.HelloWorld` 클래스에 연결한다.

### 4.2. `@WebServlet` 사용
서블릿 3.0부터는 애너테이션으로도 등록할 수 있다.

```java
@WebServlet(
    description = "Hello World Servlet",
    urlPatterns = "/hello"
)
public class HelloWorldServlet extends HttpServlet {
    // 요청 처리 메서드 작성
}
```

| 설정 | 의미 |
|---|---|
| `@WebServlet` | 해당 클래스를 서블릿으로 등록 |
| `description` | 서블릿에 대한 설명 |
| `urlPatterns` | 처리할 URL 패턴 |

`web.xml`은 설정 파일에서, 애너테이션은 클래스 코드에서 등록한다.
애너테이션이 간단하지만 상황에 따라 `web.xml`도 사용한다.

> **경로 보충**:
> 애플리케이션의 컨텍스트 경로가 `/shop`이면 `/hello` 매핑에 접근하는 주소는 `http://localhost:8080/shop/hello`처럼 된다.

## 5. `HttpServlet` 클래스 작성
`HttpServlet`는 **추상 클래스**다.

```text
Servlet 인터페이스
    ↑ 구현
GenericServlet 추상 클래스
    ↑ 상속
HttpServlet 추상 클래스
    ↑ 상속
직접 작성한 서블릿 클래스
```

`HttpServletRequest`와 `HttpServletResponse`는 인터페이스다.
[공식 HttpServlet 문서](https://jakarta.ee/specifications/servlet/6.0/apidocs/jakarta.servlet/jakarta/servlet/http/HttpServlet.html)

> `service()`를 직접 오버라이딩해야 하는가?
> 보통은 `HttpServlet`의 `service()`가 분기를 처리하므로, 개발자는 필요한 `doGet()`·`doPost()`를 구현한다.
> [공식 HttpServlet 문서](https://jakarta.ee/specifications/servlet/6.0/apidocs/jakarta.servlet/jakarta/servlet/http/HttpServlet.html)

## 6. 생명 주기 메서드
서블릿의 생명 주기는 **컨테이너가 관리**한다.
```text
서블릿 객체 생성 → init() → 요청마다 service() → 종료 시 destroy()
                                ↓
                      doGet() / doPost() 등
```

| 단계    | 메서드                     | 호출 시점·횟수             | 구현 목적                   |
| ----- | ----------------------- | -------------------- | ----------------------- |
| **초기화**   | `init()`                | 서블릿 인스턴스 초기화 시 한 번   | 초기 준비 작업                |
| **요청 처리** | `service()`             | 요청마다                 | HTTP 메서드에 맞는 처리 메서드로 분기 |
| **개별 처리** | `doGet()`, `doPost()` 등 | 해당 HTTP 요청 처리 시      | 실제 요청 처리 로직             |
| **종료**    | `destroy()`             | 정상적인 서블릿 종료 과정에서 한 번 | 자원 정리 등 종료 작업           |

### 6.1. 첫 요청과 이후 요청의 차이
자료의 기본 설명은 첫 요청 때 서블릿을 생성하는 흐름이다.

- **첫 요청**: 서블릿이 아직 없으면 객체 생성 → `init()` → `service()` → 요청 처리
- **이후 요청**: 이미 초기화된 서블릿의 `service()` → 요청 처리
- **종료·재배포**: 기존 서블릿 종료 시 `destroy()`, 새 인스턴스 초기화 시 다시 `init()`

**‘한 번’은 서블릿 인스턴스의 생명 주기를 기준으로 이해한다.**

> **보충**:
> 설정에 따라 컨테이너 시작 시 미리 초기화할 수도 있다.
> 요청 처리에는 스레드가 사용되며, 구현에서는 기존 스레드를 재사용할 수 있으므로 ‘요청마다 반드시 새로운 스레드 객체를 만든다’고 외우지는 않는다.

### 6.2. 동시에 여러 요청이 오면?
같은 서블릿 인스턴스에 여러 요청이 동시에 들어올 수 있다.
따라서 요청별 데이터를 인스턴스 변수에 넣으면 서로 영향을 줄 수 있다.

- 요청별 값은 메서드의 지역 변수 등으로 처리한다.
- 여러 요청이 공유하는 데이터는 동시 접근을 고려한다.

이 점은 [공식 HttpServlet 문서](https://jakarta.ee/specifications/servlet/6.0/apidocs/jakarta.servlet/jakarta/servlet/http/HttpServlet.html)에서도 강조한다.

## 7. `HttpServletRequest`
> 클라이언트가 보낸 정보 읽기

`HttpServletRequest`는 파라미터, 헤더, 쿠키, 요청 주소, HTTP 본문 등을 읽을 때 사용한다.

### 7.1. 파라미터 메서드
> 가장 중요하다.

| 메서드                          | 반환 타입      | 용도                    |
| ---------------------------- | ---------- | --------------------- |
| `getParameter("name")`       | `String`   | 이름에 해당하는 파라미터 값 하나 읽기 |
| `getParameterValues("name")` | `String[]` | 같은 이름으로 전달된 여러 값 읽기   |

| 요청 예              | 반환값     |
| ----------------- | ------- |
| `/hello`          | `null`  |
| `/hello?name=`    | `""`    |
| `/hello?name=Kim` | `"Kim"` |

예를 들어 `/hello?name=Kim` 요청에서:
```java
String name = request.getParameter("name");  // "Kim"
```

기억할 점은 두 가지다.
- **숫자처럼 보여도 반환값은 문자열**이다. 숫자 계산이 필요하면 변환해야 한다.
- 해당 이름의 파라미터가 없으면 `null`이다. 값이 있다고 가정하고 바로 처리하지 않는다.

여러 체크박스처럼 같은 이름으로 여러 값을 보내는 경우에는 `getParameterValues()`를 사용한다.

### 7.2. 요청 주소와 환경을 읽는 메서드
다음 요청을 기준으로 비교해 보자.
```text
http://www.example.com:8080/shop/list?category=book
```

| 메서드 | 반환 예 | 의미 |
|---|---|---|
| `getRequestURL()` | `http://www.example.com:8080/shop/list` | 요청 URL, 쿼리 문자열 제외 |
| `getRequestURI()` | `/shop/list` | 요청 경로, 쿼리 문자열 제외 |
| `getContextPath()` | `/shop` | 웹 애플리케이션의 컨텍스트 경로 |
| `getScheme()` | `http` | 요청 스킴 |
| `getServerName()` | `www.example.com` | 서버 이름 |
| `getServerPort()` | `8080` | 서버 포트 |
| `getMethod()` | `GET` | HTTP 요청 메서드 |
| `isSecure()` | `false` | HTTPS 같은 보안 채널 사용 여부 |
| `getLocale()` | 예: `ko_KR` | 클라이언트가 선호하는 로캘 |
| `getProtocol()` | 예: `HTTP/1.1` | 프로토콜 이름과 버전 |
| `getLocalAddr()` | 예: `127.0.0.1` | 요청을 받은 서버 측 IP 주소 |
| `getRemoteAddr()` | 예: `210.102.111.212` | 요청을 보낸 상대 측 IP 주소 |

URL과 URI의 쿼리 문자열 처리 설명은 [공식 HttpServletRequest 문서](https://jakarta.ee/specifications/servlet/6.0/apidocs/jakarta.servlet/jakarta/servlet/http/HttpServletRequest.html)를 기준으로 보충했다.
`getRequestURL()`의 반환 타입은 `StringBuffer`다.

## 8. `HttpServletResponse`
> 클라이언트에게 보낼 응답 만들기

`HttpServletResponse`는 응답의 데이터 타입, 상태 코드, 헤더, 쿠키, 본문 등을 구성할 때 사용한다.

| 메서드 | 역할 |
|---|---|
| `setContentType(type)` | 응답 데이터의 종류 지정 |
| `getWriter()` | 문자 응답을 작성하는 `PrintWriter` 얻기 |
| `sendRedirect(location)` | 브라우저가 지정한 주소로 새 요청을 보내도록 응답 |
| `addCookie(cookie)` | 응답에 쿠키 추가 |
| `addHeader(name, value)` | 응답 헤더 추가 |
| `encodeURL(url)` | 필요할 때 URL에 세션 ID를 포함해 세션 추적 지원 |
| `getHeaderNames()` | 현재 응답의 헤더 이름 조회 |

### 8.1. 한글 응답
```java
response.setContentType("text/html;charset=UTF-8");
response.getWriter().println("<h1>안녕하세요</h1>");
```

**문자 인코딩을 `getWriter()`보다 먼저 설정한다.**
`setContentType()`에서 `charset=UTF-8`까지 지정해야 이 예시처럼 한글 응답의 인코딩이 정해진다.
[공식 ServletResponse 문서](https://jakarta.ee/specifications/servlet/6.0/apidocs/jakarta.servlet/jakarta/servlet/servletresponse)

### 8.2. 리다이렉트
`sendRedirect()`는 브라우저에 다른 주소로 이동하라는 응답을 보낸다.
브라우저는 그 주소로 **새 HTTP 요청**을 보낸다.

```text
현재 요청 → 서버의 리다이렉트 응답 → 브라우저의 새 요청
```

## 9. 장단점과 보완 방법
| 구분  | 내용                                |

| 장점  | JVM을 통해 여러 서버 환경에서 실행 가능          |
| 장점  | 웹 애플리케이션의 데이터 공유 지원               |
| 장점  | 오픈소스 라이브러리와 개발 도구 활용              |
| 단점  | HTML을 출력문과 문자열 결합으로 작성하면 코드가 복잡해짐 |
| 단점  | 자바 코드 안의 HTML은 화면 수정이 어려움         |
| 단점  | 폼 데이터 처리 과정이 번거로움                 |

자료에서는 다음과 같은 보완 방법을 제시한다.
- **JSP 같은 템플릿 엔진**: 화면 구성과 출력을 담당한다.
- **프런트 컨트롤러 모델**: 공통 진입점에서 요청을 받아 필요한 처리로 연결한다.
- **스프링 프레임워크**: 보안·인증 등 여러 기능의 구현과 개발 생산성 향상에 활용한다.

학습할 때는 **서블릿은 요청 처리, 템플릿은 화면 구성**으로 역할을 나누어 기억하면 좋다.

## 1. TCP 개요 및 세그먼트 구조
### 1.1. TCP의 주요 특징
**1 대 1 통신 (Point-to-Point)**
- 단일 송신자와 단일 수신자 간의 통신만 지원한다.
- (멀티캐스트/브로드캐스트 불가)

**신뢰 기반·순서 기반 바이트 스트림 (Reliable, In-order Byte Stream)**
- 애플리케이션 데이터를 메시지 경계(boundary)가 없는 연속적인 바이트 흐름으로 취급하며, 손실 없이 순서대로 전달함을 보장한다.

**전이중 데이터 흐름 (Full-Duplex Data)**
- 하나의 연결이 성립되면 양방향으로 동시에 데이터를 주고받을 수 있다.

**연결 지향형 (Connection-Oriented)**
- 데이터를 교환하기 전에 **핸드쉐이킹(Handshaking)** 과정을 통해 제어 메시지를 주고받으며 양측의 연결 상태를 초기화한다.

**파이프라이닝 (Pipelining)**
- ACK를 기다리지 않고 여러 세그먼트를 연속해서 전송하며,
- 윈도우 크기는 **흐름 제어**와 **혼잡 제어**에 의해 결정된다.

**누적 ACK (Cumulative ACK)**
- 특정 순서 번호까지의 모든 바이트를 정상 수신했음을 한 번에 확인 응답한다.

**흐름 제어 (Flow Control)**
- 송신자가 수신자의 버퍼 처리 한계를 초과하여 데이터를 보내지 않도록 조절한다.

### 1.2. 세그먼트 크기: MSS와 MTU 비교
**MSS** (Maximum Segment Size; 최대 세그먼트 크기)
- 기준 계층: **TCP (전송 계층)**
- IP 헤더와 TCP 헤더를 **제외**하고, TCP 세그먼트 1개의 페이로드에 담을 수 있는 **순수 애플리케이션 데이터의 최대 크기**
- 기본값: IPv4 기준 `536` 또는 `1460` 바이트 (RFC 1122)
- 연결 설정 시 TCP 헤더의 `Options` 필드를 통해 상대방에게 전달

**MTU** (Maximum Transfer Unit; 최대 전송 단위)
- 기준 계층: **IP / 링크 계층**
- **IP 헤더 + TCP 헤더 + TCP 데이터(페이로드)**를 모두 합친 패킷 전체의 최대 길이
- 일반적으로 `1500` 바이트

### 1.3. TCP 세그먼트 헤더 구조
TCP 세그먼트는 **헤더(기본 20바이트 + 옵션)**와 **애플리케이션 데이터(페이로드)**로 구성된다.

```mermaid
packet-beta
	0-15: "출발지 포트 번호 (16비트)"
	16-31: "목적지 포트 번호 (16비트)"
	32-63: "시퀀스 번호 (32비트)"
	64-95: "ACK 번호 (32비트)"
	96-99: "데이터 오프셋 (4비트)"
	100-105: "예약됨 (6비트)"
	106: "URG"
	107: "ACK"
	108: "PSH"
	109: "RST"
	110: "SYN"
	111: "FIN"
	112-127: "윈도우 크기 (16비트)"
	128-143: "체크섬 (16비트)"
	144-159: "긴급 데이터 포인터 (16비트)"
	160-191: "옵션 및 패딩 (가변, 0~40바이트)"
```

- **`Source port #` / `Dest port #` (각 16비트)**: 다중화 및 역다중화를 위한 출발지·목적지 포트 번호
- **`Sequence number` (순서 번호, 32비트)**: 세그먼트 개수 단위가 아닌 **바이트 스트림 단위**로 카운팅하며, 해당 세그먼트에 담긴 데이터의 **첫 번째 바이트 번호**를 나타냄
- **`Acknowledgement number` (ACK 번호, 32비트)**: 상대방으로부터 **다음에 수신하기를 기대하는 바이트의 순서 번호** (직전까지 정상 수신한 마지막 바이트 번호 + 1)
- **`Header length` (4비트)**: 가변 길이인 `Options` 필드로 인해 달라지는 TCP 헤더의 전체 길이를 표시
- **제어 플래그 비트 (Flags)**:
	- `A (ACK)`: `Acknowledgement number` 필드의 값이 유효함을 표시
	- `S (SYN)`, `F (FIN)`, `R (RST)`: 연결 설정(SYN), 연결 종료(FIN), 연결 강제 초기화(RST) 등 연결 관리에 사용
	- `C`, `E`: 네트워크 혼잡 통지(Congestion Notification)에 사용
	- `U (URG)`, `P (PSH)`: 긴급 데이터(`Urg data pointer`와 함께 사용) 및 즉시 전달 지시
- **`Receive window` (`rwnd`, 16비트)**: **흐름 제어**를 위해 수신자가 현재 수용할 수 있는 수신 버퍼의 여유 바이트 크기
- **`Checksum` (16비트)**: 전송 중 데이터 오류 검출을 위한 인터넷 체크섬
- **`Options` (가변 길이)**: MSS 협상, 윈도우 스케일링, 타임스탬프 등 부가 정보

### 1.4. 순서 번호(`Seq`)와 ACK 번호의 동작 원리
- **피기백킹 (Piggybacking)**: 수신자가 송신자에게 보낼 데이터가 있을 때, 데이터와 함께 직전 수신 데이터에 대한 `ACK`를 하나의 세그먼트에 묶어 전송할 수 있습니다.
	- *예시 (Telnet)*:
		1. **Host A → Host B**: `Seq=42, ACK=79, data='C'` (1바이트 전송)
		2. **Host B → Host A**: 42번 바이트를 잘 받았으므로 다음 기대 번호인 `ACK=43`을 설정하고, 자신이 보낼 에코 데이터(`Seq=79, data='C'`)를 함께 전송
		3. **Host A → Host B**: 79번 바이트를 잘 받았으므로 `Seq=43, ACK=80` 전송
- **비순차(Out-of-order) 세그먼트의 처리**: 예상한 번호보다 큰 순서 번호의 세그먼트가 먼저 도착했을 때(중간 패킷 누락 시), 이를 즉시 버릴지 버퍼에 임시 보관할지는 **TCP 표준 규격에 정의되어 있지 않아 구현자(개발자)가 결정**합니다(실무에서는 대개 버퍼에 보관 후 누락분 도착 시 합침).

## 2. 신뢰적 데이터 전송 (RDT)
### 2.1. 왕복 시간(RTT) 추정과 타임아웃 설정
네트워크 상의 왕복 시간(RTT)은 고정되어 있지 않고 가변적이므로, 적절한 타임아웃(`TimeoutInterval`) 값을 동적으로 계산해야 한다.

- **타임아웃이 너무 짧으면**: 패킷이 지연되었을 뿐인데 조기 타임아웃이 발생하여 **불필요한 재전송**이 늘어남
- **타임아웃이 너무 길면**: 실제 세그먼트 손실이 발생했을 때 **복구(재전송) 대응이 늦어짐**

#### 타임아웃 계산 3단계 공식
1. **`SampleRTT` 측정**: 세그먼트를 전송한 시점부터 그에 대한 ACK를 받을 때까지 걸린 시간 측정
	- ⚠️ **주의**: 재전송된 세그먼트에 대한 ACK는 원본에 대한 것인지 재전송본에 대한 것인지 모호하므로 **측정에서 제외(무시)**합니다.
2. **`EstimatedRTT` (평균 RTT 추정)**: `SampleRTT`의 급격한 변동을 완화하기 위해 **지수적 가중 이동 평균(EWMA)**을 사용합니다(최근 샘플에 가중치를 두고 과거 값의 영향은 지수적으로 빠르게 감소).
	$$\text{EstimatedRTT} = (1 - \alpha) \cdot \text{EstimatedRTT} + \alpha \cdot \text{SampleRTT}$$
	*(권장 일반값: $\alpha = 0.125$)*
3. **`DevRTT` (RTT 변동폭 계산) 및 최종 `TimeoutInterval` 설정**: `SampleRTT`가 `EstimatedRTT`로부터 얼마나 벗어나는지 편차를 구해 **안전 마진(Safety Margin)**으로 더합니다.
	$$\text{DevRTT} = (1 - \beta) \cdot \text{DevRTT} + \beta \cdot |\text{SampleRTT} - \text{EstimatedRTT}|$$
	*(권장 일반값: $\beta = 0.25$)*
	$$\text{TimeoutInterval} = \text{EstimatedRTT} + 4 \cdot \text{DevRTT}$$

### 2.2. TCP 송신자 및 수신자 동작 규칙
#### TCP 송신자의 3대 이벤트 처리
1. **응용 계층으로부터 데이터 수신**:
	- 세그먼트 첫 바이트 번호를 `Seq`로 지정하여 세그먼트 생성 및 전송
	- 타이머가 꺼져 있다면 타이머 시작 (타이머는 **아직 ACK를 받지 못한 가장 오래된 세그먼트** 기준, 주기는 `TimeoutInterval`)
2. **타임아웃 발생**:
	- 타임아웃을 일으킨 세그먼트를 **재전송**하고 타이머를 **재시작**
3. **ACK 수신**:
	- 미확인 세그먼트에 대한 새로운 누적 ACK가 도착하면 송신 윈도우 기준점(`SendBase`)을 갱신
	- 아직 확인받지 못한(in-flight) 세그먼트가 남아 있다면 타이머를 다시 시작

#### TCP 수신자의 ACK 생성 규칙 (RFC 5681)
| 수신자 측 이벤트 (도착 상황) | TCP 수신자의 동작 |
| :--- | :--- |
| **예상한 순서 번호의 세그먼트 도착**<br>*(이전 세그먼트까지는 모두 ACK를 보낸 상태)* | **지연 ACK (Delayed ACK)**: 다음 순차 세그먼트가 올 때까지 최대 `500ms` 대기. 그 안에 다음 세그먼트가 오지 않으면 ACK 전송 |
| **예상한 순서 번호의 세그먼트 도착**<br>*(이미 지연 ACK 대기 중인 세그먼트가 1개 이상 있음)* | **즉시 누적 ACK 1개 전송**: 대기 중이던 세그먼트와 방금 도착한 세그먼트를 한 번에 확인 응답 |
| **예상 번호보다 큰 비순차 세그먼트 도착**<br>*(중간 세그먼트 유실로 간격/Gap 발생)* | **즉시 중복 ACK (Duplicate ACK) 전송**: 다음에 받기를 기대하는(빠진 구간의 첫 번째) 순서 번호를 담은 ACK를 즉시 재전송 |
| **빠졌던 간격(Gap)을 부분적 또는 완전히 채우는 세그먼트 도착** | 도착한 세그먼트가 간격의 가장 낮은 번호(시작점)부터 메운다면 **즉시 ACK 전송** |

### 2.3. 빠른 재전송
**배경**
- 타임아웃 주기는 상대적으로 길기 때문에,
- 패킷 손실 시 타임아웃이 만료될 때까지 기다리면 전송 지연이 커진다.

**동작 원리**
1. 중간 세그먼트가 유실되고 뒤이은 세그먼트들이 수신자에게 계속 도착하면, 수신자는 그때마다 유실된 바이트 번호를 요구하는 **중복 ACK(Duplicate ACK)**를 보낸다.
2. 송신자가 **동일한 순서 번호에 대한 중복 ACK를 3개 연속 수신**하면(최초 정상 ACK 1개 + 중복 ACK 3개), 해당 세그먼트가 손실되었다고 확신한다.
3. 송신자는 **타임아웃을 기다리지 않고 즉시 해당 세그먼트를 재전송**한다.

```mermaid
sequenceDiagram
	participant S as 송신자
	participant R as 수신자
	
	R-->>S: ACK=100 (처음 받은 ACK)
	R-->>S: ACK=100 (중복 ACK 1)
	R-->>S: ACK=100 (중복 ACK 2)
	R-->>S: ACK=100 (중복 ACK 3)
	
	Note over S: 3번의 중복 ACK 수신
	S->>R: Seq=100 세그먼트 빠른 재전송
```

## 3. TCP 흐름 제어
### 3.1. 목적
- 수신 측에서 네트워크 계층이 TCP 소켓 버퍼로 데이터를 밀어 넣는 속도가
- 응용 계층 프로세스가 버퍼에서 데이터를 읽어가는 속도보다 빠를 때 발생하는
- **수신 버퍼 오버플로우를 방지**한다.

```mermaid
flowchart LR
	subgraph Receiver["수신 측"]
		Net["네트워크 계층"] -->|"데이터 밀어 넣기 (빠름)"| Buf[("TCP 소켓 버퍼")]
		Buf -->|"데이터 읽어가기 (느림)"| App["응용 계층 프로세스"]
	end
```

### 3.2. 핵심 변수
`RcvBuffer`
- 수신 버퍼의 전체 크기
- (소켓 옵션으로 설정 가능하며 기본값은 보통 `4KB`, 운영체제가 자동 조정하기도 함)

`rwnd` (Receive Window)
- 수신 버퍼 내의 현재 **여유 공간 크기 (`free buffer space`)**

### 3.3. 동작 방식
1. 수신자는 세그먼트를 보낼 때마다 TCP 헤더의 `receive window` 필드에 현재 자신의 여유 공간인 `rwnd` 값을 담아 송신자에게 알린다.
2. 송신자는 아직 확인(ACK)받지 못한 전송 데이터양(`in-flight data`)이 수신자의 `rwnd` 값을 넘지 않도록 송신 데이터 크기를 제한한다.

## 4. TCP 연결 관리
### 4.1. 왜 3단계 핸드셰이크인가?
네트워크에서는 패킷 지연 변동, 손실로 인한 재전송, 순서 뒤바뀜이 발생한다.

만약 2단계(`연결 요청` → `연결 수락`)만으로 연결을 맺으면 다음과 같은 치명적 문제가 발생한다.

1. **반쪽 연결 (Half-open connection) 문제**
	- 클라이언트의 연결 요청(`req_conn(x)`)이 지연되어 재전송되었고, 정상 통신 후 연결이 종료되어 서버가 연결 기록을 지웠다고 가정한다.
	- 이후 뒤늦게 도착한 과거의 재전송 요청(`req_conn(x)`)을 서버가 받으면, 서버는 새로운 연결 요청으로 착각해 혼자만 연결(`ESTAB`)을 열어두고 자원을 낭비한다.

2. **중복 데이터 수신 문제**
	- 위 상황에서 과거에 재전송되었던 데이터(`data(x+1)`)까지 뒤늦게 서버에 도착하면, 서버는 이미 처리하고 끝난 중복 데이터를 새로운 데이터로 착각해 다시 수락(accept)하게 된다.

### 4.2. TCP 연결 설정 (3단계 핸드셰이크)
```mermaid
sequenceDiagram
	autonumber
	participant C as 클라이언트
	participant S as 서버
	
	Note over C,S: 연결 설정 시작
	C->>S: SYN (연결 요청)
	S->>C: SYN + ACK (요청 수락 및 연결 요청)
	C->>S: ACK (확인 응답)
	Note over C,S: 연결 성립 (ESTABLISHED)
```

|          단계           | 전송 세그먼트 내용                                                                | 상태 변화 및 의미                                                                                                                                                            |
| :-------------------: | :------------------------------------------------------------------------ | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
|  **1단계**<br>(`SYN`)   | `SYNbit = 1`<br>`Seq = x` *(클라이언트 초기 순서 번호)*                              | • **Client**: `SYNSENT` 상태로 전환<br>• 애플리케이션 데이터(페이로드)는 포함할 수 없음                                                                                                        |
| **2단계**<br>(`SYNACK`) | `SYNbit = 1`, `Seq = y` *(서버 초기 순서 번호)*<br>`ACKbit = 1`, `ACKnum = x + 1` | • **Server**: `LISTEN` → `SYN RCVD` 상태로 전환<br>• 서버가 연결 버퍼 및 변수를 할당하고 클라이언트 요청에 응답                                                                                     |
|  **3단계**<br>(`ACK`)   | `SYNbit = 0`<br>`ACKbit = 1`, `ACKnum = y + 1`                            | • **Client**: `SYNACK` 수신 시 서버 생존을 확인하고 `ESTAB` 전환 (버퍼/변수 할당)<br>• **Server**: `ACK` 수신 시 클라이언트 생존을 확인하고 `ESTAB` 전환<br>• 💡 **이 3번째 세그먼트부터는 실제 애플리케이션 데이터를 담아 전송 가능** |

### 4.3. TCP 연결 종료 (4단계 핸드셰이크)
```mermaid
sequenceDiagram
	autonumber
	participant C as 클라이언트
	participant S as 서버
	
	Note over C,S: 연결 종료 시작 (클라이언트가 먼저 종료 요청)
	C->>S: FIN (연결 종료 요청)
	S->>C: ACK (요청 확인)
	
	Note right of S: 서버가 남은 데이터를 마저 전송/정리
	
	S->>C: FIN (서버 측 종료 준비 완료)
	C->>S: ACK (확인 응답)
	
	Note left of C: TIME_WAIT 대기 후<br/>완전 종료 (CLOSED)
```

클라이언트와 서버 중 어느 쪽이든 먼저 `FINbit = 1` 세그먼트를 보내 연결 종료를 시작할 수 있다.
(아래는 클라이언트가 먼저 종료를 요청하는 일반적인 시나리오이다.)

1. **1단계 (`FIN`)**
	- 클라이언트가 `close()`를 호출하여 `FINbit = 1, seq = x` 전송
	- **Client 상태**: `ESTAB` → **`FIN_WAIT_1`**
		- *(더 이상 데이터 송신은 불가하지만, 서버로부터 데이터 수신은 가능)*

2. **2단계 (`ACK`)**
	- 서버가 `FIN`을 수신하고 `ACKbit = 1, ACKnum = x + 1` 전송
	- **Server 상태**: `ESTAB` → **`CLOSE_WAIT`**
		- *(아직 보낼 데이터가 남아 있다면 계속 전송 가능)*
	- **Client 상태**: `ACK` 수신 후 **`FIN_WAIT_2`**로 전환하여 서버의 종료 신호(`FIN`)를 대기

3. **3단계 (`FIN`)**
	- 서버도 남은 데이터 전송을 마치고 `FINbit = 1, seq = y` 전송
		- *(만약 서버가 2단계 시점에 이미 보낼 데이터가 없다면 2단계의 ACK와 3단계의 FIN을 하나로 결합해 보낼 수도 있음)*
	- **Server 상태**: `CLOSE_WAIT` → **`LAST_ACK`**
		- *(더 이상 데이터 송신 불가, 마지막 ACK 대기)*

4. **4단계 (`ACK`)**
	- 클라이언트가 서버의 `FIN`을 수신하고 `ACKbit = 1, ACKnum = y + 1` 전송
	- **Server 상태**: `ACK`를 수신하는 즉시 **`CLOSED`**로 전환
	- **Client 상태**: **`TIMED_WAIT`** 상태로 전환하여 **`2 × MSL (Max Segment Lifetime, 최대 세그먼트 수명)`** 시간 동안 대기한 뒤 **`CLOSED`**로 최종 종료
		- *(마지막 ACK가 유실되어 서버가 `FIN`을 재전송할 경우에 대비하고, 네트워크에 남아있는 이전 연결의 지연 패킷들이 소멸할 때까지 기다리기 위함)*

## 1. TCP를 이해하는 큰 흐름
TCP는 두 응용 프로그램 사이에서 **바이트들을 빠짐없이, 순서대로 전달하기 위한 연결 지향형 트랜스포트 프로토콜**이다.

TCP를 공부할 때는 다음 네 가지 질문을 연결해서 생각하면 된다.

| 질문 | TCP의 대응 | 핵심 용어 |
|---|---|---|
| 어떤 데이터를 보냈고, 어디까지 도착했는가? | 바이트마다 번호를 붙이고 수신 상태를 알린다. | Seq, ACK |
| 데이터나 ACK가 유실되면 어떻게 하는가? | 타임아웃 또는 중복 ACK를 보고 재전송한다. | RTT, 타이머, 빠른 재전송 |
| 수신자가 데이터를 감당하지 못하면? | 수신 버퍼의 여유 공간에 맞춰 전송량을 제한한다. | 흐름 제어, rwnd |
| 언제 통신을 시작하고 끝내는가? | 제어 세그먼트를 교환해 연결을 설정하고 종료한다. | SYN, ACK, FIN |

**핵심 연결**
- Seq로 데이터를 식별하고,
- ACK로 도착을 확인하며,
- 타이머로 손실에 대응하고,
- rwnd로 수신자를 보호한다.

*TCP 시퀀스 다이어그램*
```mermaid

	autonumber

	participant Server as 서버 (Server)
	
	rect rgb(240, 248, 255)

	Client->>Server: SYN (연결 요청)

	Server->>Client: FIN (종료 준비 완료)
```

## 2. TCP의 기본 성질
| 성질           | 의미                                       |
| ------------ | ---------------------------------------- |
| 일대일 통신       | 하나의 TCP 연결은 두 종단 사이의 통신이다.               |
| 연결 지향        | 데이터 교환 전에 핸드셰이크로 연결 상태와 초기 파라미터를 준비한다.   |
| 신뢰적·순서 보장 전송 | 손실에 재전송으로 대응하고, 응용에는 순서대로 바이트를 전달한다.     |
| 바이트 스트림      | 데이터는 연속된 바이트의 흐름이며, 응용 메시지 경계를 보존하지 않는다. |
| 전이중 통신       | 한 연결에서 양쪽이 동시에 데이터를 보낼 수 있다.             |
| 누적 ACK       | 연속해서 받은 바이트들을 하나의 ACK 번호로 확인한다.          |
| 파이프라이닝       | ACK를 기다리는 동안에도 허용된 범위 안에서 여러 세그먼트를 전송한다. |
| 흐름 제어        | 수신 버퍼의 여유 공간을 넘지 않도록 전송량을 제한한다.          |

### 2.1. 바이트 스트림에 메시지 경계가 없다는 뜻
응용이 `ABC`와 `DEF`를 따로 전송했어도, 수신 응용이 반드시 두 번에 나누어 읽는 것은 아니다.
`ABCDEF`를 한 번에 읽거나, `AB`와 `CDEF`로 나누어 읽을 수도 있다.

따라서 **응용 메시지의 구분은 응용 계층에서 처리해야 한다.**
TCP의 세그먼트 경계와 응용 메시지 경계는 일치할 필요가 없다.

### 2.2. 전이중 통신에서 기억할 점
A→B와 B→A에는 **각각 독립적인 순서 번호 공간**이 있다.
A가 보내는 세그먼트의 Seq는 A→B 데이터를, ACK는 반대 방향인 B→A 데이터의 수신 상태를 나타낸다.

## 3. MSS와 MTU
*cf. 프레임*
- 이더넷, IP, TCP, HTTP

### 3.1 MSS: TCP 데이터 부분의 최대 크기
**MSS (Maximum Segment Size)**
- TCP 세그먼트 하나에 담을 수 있는 **데이터(payload)의 최대 바이트 수**다.

- IP 헤더와 TCP 헤더는 MSS에 포함하지 않는다.
- 연결 설정 때 TCP 옵션으로 자신의 수신 MSS를 상대방에게 알릴 수 있다.
- 양쪽이 광고하는 MSS 값이 반드시 같을 필요는 없다.

### 3.2. MTU: 링크가 운반할 수 있는 패킷 크기의 한도
**MTU (Maximum Transfer Unit)**
- IP 패킷의 크기를 생각할 때 MTU에는 IP 헤더, TCP 헤더, TCP 데이터가 포함된다.
- Ethernet의 흔한 예는 1,500바이트다.

```
IP 패킷
┌───────────┬────────────┬───────────────────┐
│ IP 헤더   │ TCP 헤더   │ TCP 데이터        │
└───────────┴────────────┴───────────────────┘
                         ← MSS의 대상 →
←──────────────── MTU와 비교하는 크기 ───────→
```

IPv4 헤더 20바이트, TCP 헤더 20바이트이고 옵션이 없다고 가정하면:
```
MSS = 1500 - 20 - 20 = 1460바이트
```

> **강의 표현 보충**
> MTU는 TCP 자체의 고유 값이 아니며, 항상 1,500바이트인 것도 아니다.
> 강의의 1,460바이트는 위 조건에서 나오는 대표적인 MSS 예다.
> 536바이트와 1,460바이트를 모든 TCP 연결의 고정 기본값으로 외우지 말고, **MSS는 데이터 크기이고 MTU 및 헤더 크기에 영향을 받는다**는 관계를 이해하자.

## 4. TCP 세그먼트
TCP 세그먼트는 **헤더 + 응용 데이터**로 구성된다.

### 4.1. TCP 헤더
1. 출발지 포트 번호 (source port)
2. 목적지 포트 번호 (destination port)
3. ==시퀀스 번호== (sequence number): 첫 번째 데이터 바이트의 번호
4. ==ACK 번호== (acknowledgment number): 다음에 기대하는 바이트의 번호
5. 데이터 오프셋: 헤더의 길이 (20-60바이트; 어디서부터 데이터가 시작되는지)
6. 예약됨 (reserved)
7. 제어 비트 플래그
	- **ACK**: ACK 번호 필드가 유효함을 나타낸다.
	- **SYN**: 연결 설정에 사용한다.
	- **FIN**: 해당 방향으로 더 보낼 데이터가 없음을 알린다.
	- **RST**: 연결을 리셋할 때 사용한다.
	- **CWR / ECE**: 혼잡 통지와 관련된다.
8. ==윈도우 크기==: 수신자가 받아들일 수 있는 여유 공간
9. 체크섬 (checksum): 전송 중 오류 검출
10. 긴급 데이터 포인터 (urgent data pointer)
11. 옵션 및 패딩: 추가 파라미터로, MSS 같은 정보를 전달한다.

```mermaid
packet-beta

16-31: "목적지 포트 번호 (16비트)"
32-63: "시퀀스 번호 (32비트)"
64-95: "ACK 번호 (32비트)"

```

#### 시퀀스 번호
`Seq=100`, 데이터 길이 20바이트인 세그먼트가 전송하는 바이트 범위는 다음과 같다.
```
100, 101, 102, ..., 119
```

따라서 다음 데이터의 시작 번호는 `120`이다.
```
마지막 데이터 바이트 번호 = Seq + 데이터 길이 - 1
다음 데이터 시작 번호    = Seq + 데이터 길이
```

#### ACK 번호
`ACK=120`의 의미는 다음과 같다.

> 119번까지의 바이트를 빠짐없이 연속해서 받았으니,
> 다음에는 120번 바이트가 필요하다.

ACK가 120이라고 해서 120번 바이트까지 받았다는 뜻은 아니다.

**누적 ACK**
- 중간의 빈 구간을 건너뛰지 않는다.

수신자가 이미 99번까지 받았다고 하자.

| 도착한 데이터 | 수신 상태 | ACK |
|---|---|---|
| 100~119 | 빈 구간 없이 119까지 수신 | 120 |
| 140~159 | 120~139가 비어 있음 | 120 |
| 160~179 | 여전히 120~139가 비어 있음 | 120 |
| 120~139 | 뒤의 데이터도 보관했다면 179까지 연결됨 | 180 |

수신자가 뒤에 도착한 데이터를 버퍼링하는지는 구현에 따라 달라질 수 있다.
**비순차 데이터의 보관 여부와 관계없이, 누적 ACK는 연속 수신한 범위까지만 확인한다.**

### 4.2. Telnet 예제
```mermaid
sequenceDiagram
	participant A
	participant B
	
	A->>B: Seq=42, ACK=79, data='C'
	B->>A: Seq=79, ACK=43, data='C'
	A->>B: Seq=43, ACK=80, 데이터 없음
```

1. A는 자신의 42번 바이트로 문자 `C`를 보낸다.
2. B는 그 문자를 받았으므로 `ACK=43`을 보낸다. 동시에 자신의 79번 바이트로 `C`를 되돌려 보낸다.
3. A는 B의 79번 바이트를 받았으므로 `ACK=80`을 보낸다.

여기서 B의 두 번째 세그먼트는 **데이터 전송과 ACK 전달을 동시에 수행**한다.

> **번호 소비 규칙**
> 데이터는 길이만큼 순서 번호를 소비한다.
> 데이터가 없는 순수 ACK는 소비하지 않는다.
> 연결 제어의 **SYN과 FIN은 각각 1을 소비**한다.

## 5. RTT와 재전송 타임아웃
### 5.1. 타임아웃을 적절하게 잡아야 하는 이유
**RTT (Round-Trip Time)**
- 세그먼트를 전송하고 그 ACK가 돌아올 때까지 걸리는 시간이다.

| 타임아웃 설정 | 결과 |
|---|---|
| 너무 짧음 | 아직 도착 중인 ACK를 기다리지 못해 불필요하게 재전송한다. |
| 너무 김 | 실제 손실이 발생해도 복구가 늦어진다. |

RTT는 고정값이 아니므로 최근 측정값을 반영해 타임아웃을 조절해야 한다.

### 5.2. SampleRTT와 EstimatedRTT
**SampleRTT**
- 실제로 한 번 측정한 왕복 시간
- 재전송한 세그먼트는 어느 전송에 대한 ACK인지 모호하므로 RTT 표본 계산에서 제외한다.

**EstimatedRTT**
- 최근 표본을 가중 평균해 얻은 추정 RTT
- $\text{EstimatedRTT} ← (1-α) × \text{EstimatedRTT} + α × \text{SampleRTT}$
- 이는 **지수 가중 이동 평균**(EWMA)이다.
- 새 표본을 반영하면서도 일시적인 변동에 지나치게 흔들리지 않게 한다.
- 오래된 표본의 영향은 반복 갱신 과정에서 점점 작아진다.

계산 예:
```
기존 EstimatedRTT = 100ms
새 SampleRTT     = 140ms
α                = 0.125

새 EstimatedRTT = 0.875 × 100 + 0.125 × 140
                = 105ms
```

### 5.3. DevRTT와 TimeoutInterval
평균 RTT가 같아도 변동이 큰 연결에는 더 큰 안전 여유가 필요하다.

$\text{DevRTT} ← (1-β) × \text{DevRTT} + β × |\text{SampleRTT}-\text{EstimatedRTT}|$
```
TimeoutInterval = EstimatedRTT + 4 × DevRTT
```

예를 들어, 계산에 사용할 추정값이 다음과 같다면:
```
EstimatedRTT = 105ms
DevRTT       = 15ms

TimeoutInterval = 105 + 4 × 15 = 165ms
```

**기억할 관계**: 평균 RTT가 커지거나 RTT 변동폭이 커지면, 타임아웃도 커진다.

## 6. TCP의 신뢰적 데이터 전송
### 6.1. 송신자의 세 가지 핵심 이벤트
가장 오래된 미확인 데이터에 대한 타이머를 중심으로 송신자의 동작을 설명한다.

| 이벤트 | 송신자 동작 |
|---|---|
| 응용에서 데이터 도착 | Seq를 붙여 세그먼트를 만들고 전송한다. 타이머가 꺼져 있다면 시작한다. |
| 타임아웃 발생 | 가장 오래된 미확인 세그먼트를 재전송하고 타이머를 다시 시작한다. |
| 새 데이터를 확인하는 ACK 도착 | 확인 범위를 갱신한다. 미확인 데이터가 남으면 타이머를 다시 시작하고, 없으면 끈다. |

`SendBase`
- **아직 ACK로 확인되지 않은 가장 오래된 바이트의 번호**다.
- 예: `SendBase=92`일 때 `ACK=120`을 받으면, 119번까지 확인되므로 `SendBase`는 120으로 전진한다.

### 6.2. 수신자는 언제 ACK를 보내는가?
| 수신 상황                                  | ACK 동작                                           |
| -------------------------------------- | ------------------------------------------------ |
| 예상한 순서의 세그먼트가 도착했고, 이전 데이터의 ACK는 이미 보냄 | 잠시 지연해 다음 세그먼트를 기다린다. 그동안 다음 세그먼트가 없으면 ACK를 보낸다. |
| 순서대로 다음 세그먼트가 도착했고, 앞선 ACK를 아직 보내지 않음  | 두 세그먼트의 수신을 확인하는 누적 ACK를 즉시 보낸다.                 |
| 예상보다 큰 Seq가 도착해 빈 구간이 발견됨              | 다음에 필요한 번호를 담은 중복 ACK를 즉시 보낸다.                   |
| 빈 구간의 시작을 채우는 세그먼트가 도착함                | 갱신된 ACK를 즉시 보낸다.                                 |
### 6.3. 재전송 시나리오 세 가지
#### A. 데이터는 도착했지만 ACK가 손실됨
```mermaid
sequenceDiagram
	participant A
	participant B
	
	A->>B: Seq=92, 데이터 8바이트 (92~99 수신)
	B--xA: ACK=100 (도중 손실)
	Note over A: 타임아웃 발생
	A->>B: Seq=92, 데이터 8바이트 (재전송)
	B-->>A: ACK=100
```

송신자는 ACK를 못 받았다는 사실만으로 데이터 손실과 ACK 손실을 구분할 수 없다.
수신자는 중복 데이터를 응용에 다시 전달하지 않고 ACK를 보낸다.

#### B. 타임아웃이 너무 빨리 발생함
원래 데이터와 ACK가 정상적으로 이동 중이어도 타이머가 먼저 만료되면 불필요한 재전송이 발생한다.
수신자는 이미 받은 연속 데이터 범위를 반영한 누적 ACK를 보낸다.

#### C. 뒤의 누적 ACK가 앞의 ACK 손실을 보완함
```mermaid
sequenceDiagram
	participant A
	participant B
	
	A->>B: Seq=92, 데이터 8바이트
	A->>B: Seq=100, 데이터 20바이트
	B--xA: ACK=100 (손실)
	B-->>A: ACK=120 (도착)
```

`ACK=120`은 119번까지 모두 받았다는 뜻이므로, `ACK=100`을 따로 다시 받을 필요가 없다.
타임아웃 전에 ACK=120이 도착했다면 이 ACK 손실 때문에 재전송할 필요도 없다.

## 8. 연결 설정
> 왜 3-way handshake인가?

### 8.1. 연결 전에 준비할 것
연결 설정 과정에서는 다음을 확인하거나 준비한다.

- 양쪽에 연결 의사가 있는가?
- 서로의 메시지가 도달하는가?
- 각 방향의 초기 순서 번호는 무엇인가?
- MSS 등 연결에 필요한 파라미터는 무엇인가?

### 8.2. 2-way 방식이 겪는 문제
네트워크에는 지연, 손실, 재전송, 순서 뒤바뀜이 있다.
이전 연결의 복제된 요청이 아주 늦게 도착할 수 있다.

서버가 요청을 받자마자 연결을 확정하는 2-way 방식을 가정하면:
1. 클라이언트가 연결 요청을 재전송한다.
2. 정상 연결은 이미 끝난다.
3. 네트워크에 남아 있던 오래된 연결 요청이 서버에 도착한다.
4. 서버가 이를 새 요청으로 오해하고 연결을 만든다.

결과는 **클라이언트가 없는 half-open connection**이다.
과거 데이터까지 뒤늦게 도착하면 중복 데이터를 새 데이터처럼 받아들이는 문제도 생길 수 있다.

**핵심**: 서버는 자신의 응답을 현재 클라이언트가 실제로 받았는지 마지막 확인을 받아야 한다.

### 8.3. TCP의 3단계 교환
클라이언트의 초기 순서 번호를 `x`, 서버의 초기 순서 번호를 `y`라고 하자.

```mermaid
sequenceDiagram
	autonumber
	클라이언트->>서버: SYN=1, Seq=x
	서버->>클라이언트: SYN=1, ACK=1, Seq=y, ACKnum=x+1
	클라이언트->>서버: ACK=1, Seq=x+1, ACKnum=y+1
```

| 단계        | 전달하는 의미                              |
| --------- | ------------------------------------ |
| ① SYN     | 클라이언트가 연결을 요청하고 자신의 초기 순서 번호 x를 알린다. |
| ② SYN+ACK | 서버가 x를 확인하고, 자신의 초기 순서 번호 y를 알린다.    |
| ③ ACK     | 클라이언트가 서버의 y를 받았음을 확인한다.             |

SYN은 순서 번호 1개를 소비하므로 ACK 번호가 각각 `x+1`, `y+1`이다.
세 번째 ACK에는 클라이언트 데이터가 함께 실릴 수도 있다.

### 8.4. 연결 설정 상태 변화
```
클라이언트: CLOSED → SYN_SENT → ESTABLISHED
서버:       LISTEN → SYN_RCVD → ESTABLISHED
```

- 클라이언트는 SYN+ACK를 받고 ACK를 보내며 연결이 성립한다.
- 서버는 마지막 ACK를 받고 연결이 성립한다.
- 강의 그림의 `ESTAB`는 `ESTABLISHED`의 축약이다.

### 8.5. 숫자로 확인하기
`x=1000`, `y=5000`이라면, 데이터 없는 기본 교환은 다음과 같다.
```mermaid
sequenceDiagram
	autonumber
	클라이언트->>서버: SYN, Seq=1000
	서버->>클라이언트: SYN+ACK, Seq=5000, ACK=1001
	클라이언트->>서버: ACK, Seq=1001, ACK=5001
```

## 9. 연결 종료
> 두 방향을 각각 닫는다.

### 9.1. FIN
**FIN** (Finish; 종료)
- “이 방향으로 더 보낼 데이터가 없다”는 뜻이다.

- TCP는 전이중이므로 한쪽이 FIN을 보내도 반대 방향의 데이터 전송은 계속될 수 있다.
- 클라이언트와 서버 중 어느 쪽이든 먼저 종료를 시작할 수 있다.

### 9.2. 기본 종료 절차
가정: 클라이언트가 먼저 종료한다.
아래의 `x`, `y`는 **종료 시점의 다음 순서 번호**이며, 앞 절의 초기 순서 번호와는 별개다.
```mermaid
sequenceDiagram
	autonumber
	participant C as 클라이언트
	participant S as 서버
	
	C->>S: FIN=1, Seq=x
	S-->>C: ACKnum=x+1
	Note over S: 서버는 남은 데이터를 보낼 수 있음
	S->>C: FIN=1, Seq=y
	C-->>S: ACKnum=y+1
	Note over C: TIME_WAIT 후 종료
```

- FIN도 순서 번호 1개를 소비한다.
- FIN에 대한 ACK는 상대의 FIN을 대신하지 않는다.
- 종료에는 보통 네 번의 교환이 등장하지만, ACK와 FIN을 합칠 수 있어 **항상 정확히 네 세그먼트인 것은 아니다.**
- 양쪽이 동시에 FIN을 보내는 경우도 처리할 수 있다.

### 9.3. 종료 상태 변화
일반적인 순차 종료 예:
```
먼저 종료하는 쪽:
ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED

나중에 종료하는 쪽:
ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED
```

| 상태 | 의미 |
|---|---|
| FIN_WAIT_1 | 내 FIN에 대한 ACK 등을 기다린다. |
| FIN_WAIT_2 | 내 FIN은 확인되었고, 상대의 FIN을 기다린다. |
| CLOSE_WAIT | 상대 FIN을 받았고, 내 응용의 종료를 기다린다. |
| LAST_ACK | 내 FIN을 보냈고, 마지막 ACK를 기다린다. |
| TIME_WAIT | 마지막 ACK를 보낸 뒤 일정 시간 기다린다. |

### 9.4. TIME_WAIT와 2 × MSL
마지막 ACK를 보내는 쪽이 **2 × MSL(Maximum Segment Lifetime)** 동안 기다린다.
표준 상태명은 `TIME_WAIT`이며, 강의 그림에는 `TIMED_WAIT`로 표기되어 있다.

이 대기의 의미를 이해하기 위한 보충 설명:
- 마지막 ACK가 유실되어 상대가 FIN을 재전송하면 다시 ACK할 수 있게 한다.
- 이전 연결에서 지연된 세그먼트가 사라질 시간을 확보한다.

## 임시
| 혼동                                 | 정확한 이해                                 |
| ---------------------------------- | -------------------------------------- |
| Seq는 몇 번째 세그먼트인지 나타낸다.             | 해당 세그먼트의 첫 데이터 바이트 번호다.                |
| ACK=120이면 120번까지 받았다.              | 119번까지 연속 수신했고 120번을 기다린다.             |
| 뒤의 데이터가 도착하면 ACK도 무조건 커진다.         | 중간에 빈 구간이 있으면 누적 ACK는 그 구간의 시작에 머문다.   |
| ACK 하나가 손실되면 반드시 재전송한다.            | 더 큰 누적 ACK가 제때 오면 재전송이 필요 없을 수 있다.     |
| 빠른 재전송은 동일 ACK를 총 3번 받으면 한다.       | 처음 ACK 이후 중복 ACK 3개가 기준이다.             |
| rwnd는 세그먼트 하나의 최대 크기다.             | 수신 여유 공간을 알려 미확인 데이터의 총량을 제한한다.        |
| MSS에 IP/TCP 헤더도 포함된다.              | MSS는 TCP 데이터만의 최대 크기다.                 |
| SYN/FIN은 데이터가 없으니 순서 번호를 소비하지 않는다. | 각각 1을 소비한다.                            |
| FIN을 받으면 양방향 통신이 즉시 모두 끝난다.        | FIN을 보낸 방향부터 종료되며, 반대 방향은 계속 전송할 수 있다. |
| 연결 종료는 언제나 네 세그먼트다.                | FIN과 ACK를 합칠 수 있다.                     |

8. 초기 순서 번호가 클라이언트 100, 서버 900이다. SYN+ACK의 ACK 번호와 마지막 ACK의 ACK 번호는?

11. 첫 번째 데이터에 대한 ACK는 손실되었지만 더 뒤의 누적 ACK가 타임아웃 전에 도착했다. 앞 데이터를 반드시 재전송해야 하는가?

정답
1. **349, 350.** 300부터 50바이트이므로 300~349를 전송한다.
2. **849번까지 연속 수신했고, 다음으로 850번 바이트를 기대한다.**
3. **ACK=200.** 200부터 빈 구간이 있으므로 누적 ACK가 전진하지 못한다.
4. **Seq=200에서 시작하는 미확인 세그먼트.** 중복 ACK 3개를 받았으므로 빠른 재전송한다.
5. **85ms.** `0.875 × 80 + 0.125 × 120 = 85`.
6. **180ms.** `100 + 4 × 20 = 180`.
7. **rwnd=3,000바이트, 추가 전송 가능량=1,000바이트.** 다른 전송 제한은 고려하지 않은 값이다.

9. **701.** FIN이 순서 번호를 1 소비한다.

11. **아니다.** 더 뒤의 누적 ACK가 앞 데이터까지 확인한다면 별도 재전송이 필요 없다.

체크리스트
- [ ] TCP가 바이트 스트림이며 메시지 경계를 보존하지 않는다는 뜻을 설명할 수 있다.
- [ ] MSS와 MTU를 구분하고, 조건이 주어지면 MSS를 계산할 수 있다.
- [ ] Seq와 데이터 길이로 다음 Seq 및 ACK를 계산할 수 있다.
- [ ] 전이중 연결의 두 순서 번호 공간을 구분할 수 있다.
- [ ] 누적 ACK가 ACK 손실을 보완하는 과정을 설명할 수 있다.
- [ ] EstimatedRTT, DevRTT, TimeoutInterval의 역할과 공식을 알고 있다.
- [ ] 타임아웃 재전송과 빠른 재전송의 발생 조건을 구분할 수 있다.
- [ ] rwnd가 미확인 데이터의 총량을 제한한다는 점을 이해한다.
- [ ] 2-way 방식의 문제와 3-way handshake의 세 메시지를 설명할 수 있다.
- [ ] SYN과 FIN은 각각 1을, 순수 ACK는 0을 소비한다는 규칙을 적용할 수 있다.
- [ ] 연결 설정·종료의 대표 상태 변화를 따라갈 수 있다.
- [ ] FIN의 방향성과 TIME_WAIT의 의미를 설명할 수 있다.

**GraphQL** (그래프QL)
- 페이스북(현 Meta)에서 2012년에 개발하고 2015년에 오픈소스로 공개한 API를 위한 데이터 쿼리 언어(Query Language)이자, 이를 실행하는 런타임이다.
- 기존의 대표적인 API 아키텍처인 REST API의 한계를 해결하기 위해 등장했으며,
- 클라이언트가 웹 서버로부터 효율적으로 데이터를 가져오는 데 최적화되어 있다.

> 클라이언트가 주도권을 가지고 필요한 데이터만 골라 받을 수 있게 해주는 효율적인 API 표준
> 모든 프로젝트에 무조건 GraphQL이 좋은 것은 아니며, 데이터 구조가 복잡하고 다양한 클라이언트 기기를 지원해야 하는 환경에서 특히 유용하게 쓰인다.

## 1. GraphQL의 핵심 특징
- **원하는 데이터만 정확하게 요청 (No Over-fetching / Under-fetching)**
	- **Over-fetching**: 필요하지 않은 데이터까지 한꺼번에 받아와 대역폭을 낭비하는 현상이다. GraphQL은 클라이언트가 필요한 필드만 지정해서 요청할 수 있어 이 문제를 해결한다.
	- **Under-fetching**: 필요한 데이터를 얻기 위해 여러 번의 API 요청을 보내야 하는 현상이다. GraphQL은 단 한 번의 요청으로 연관된 여러 데이터를 묶어서 가져올 수 있다.
- **단일 엔드포인트 (Single Endpoint)**
	- REST API는 리소스마다 다른 URL(예: `/users`, `/posts`, `/comments`)을 사용하지만, GraphQL은 보통 단 하나의 엔드포인트(예: `/graphql`)만 사용한다. 하나의 요청 안에 원하는 쿼리를 작성해 보낸다.
- **강력한 타입 시스템 (Schema & Type)**
	- 서버에서 사용할 수 있는 데이터의 구조를 스키마(Schema)로 정의한다. 이 스키마는 서버와 클라이언트 간의 일종의 계약 역할을 하며, 요청이 유효한지 사전에 검증할 수 있게 해준다.

## 2. GraphQL의 주요 작업(Operations)
GraphQL에서는 크게 세 가지 종류의 요청을 지원한다.

1. **Query (조회)**: 데이터를 읽어올 때 사용한다. (REST의 `GET`과 유사)
2. **Mutation (수정/생성/삭제)**: 데이터를 추가, 수정, 삭제할 때 사용한다. (REST의 `POST`, `PUT`, `DELETE`와 유사)
3. **Subscription (구독)**: 웹소켓(WebSocket) 등을 통해 실시간으로 데이터 변화를 감지하고 받아올 때 사용한다.

## 3. REST API와의 간단한 비교
| 비교 항목       | REST API              | GraphQL                         |
| :---------- | :-------------------- | :------------------------------ |
| **엔드포인트**   | 여러 개 (리소스별로 구분)       | 한 개 (`/graphql`)                |
| **데이터 크기**  | 서버가 정의한 대로 고정된 응답     | 클라이언트가 요청한 필드만 맞춤 응답            |
| **오버/언더페칭** | 구조상 발생하기 쉬움           | 클라이언트가 조절하여 해결 가능               |
| **캐싱**      | HTTP 표준 캐싱 메커니즘 활용 용이 | HTTP POST를 주로 사용하여 별도의 캐싱 전략 필요 |

## 4. 장점과 단점
**장점**
- **네트워크 효율성**: 모바일 환경 등 대역폭이 제한된 상황에서 불필요한 데이터 전송을 줄여준다.
- **유연한 프론트엔드 개발**: 프론트엔드 개발자가 필요한 화면 구성에 맞춰 백엔드 수정 요청 없이 직접 필요한 데이터를 쿼리로 작성할 수 있다.
- **자동 문서화**: 스키마를 기반으로 API 문서가 자동으로 생성되어(예: GraphQL Playground, GraphiQL 도구 활용), 협업이 원활해진다.

**단점**
- **캐싱의 복잡성**: REST API는 URL 단위로 HTTP 캐싱을 쉽게 적용할 수 있지만, GraphQL은 단일 엔드포인트를 사용하므로 클라이언트 측 라이브러리(Apollo Client 등)나 복잡한 설정을 통해 캐싱을 해결해야 한다.
- **서버 부하 위험**: 클라이언트가 임의로 너무 깊은 구조(Nested)의 쿼리를 요청할 경우, 서버에 과도한 부하가 걸릴 수 있어 별도의 깊이 제한(Depth Limit) 설정이 필요할 수 있다.
- **학습 곡선**: 기존 REST 아키텍처에 익숙한 상태에서 새롭게 스키마 정의, 타입 시스템, 쿼리 작성법 등을 배워야 하는 부담이 있다.
